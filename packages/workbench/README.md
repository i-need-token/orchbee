# @orchbee/workbench

Shared product-semantic React shell for Orchbee applications.

## Scope

Workbench registers its product operations in the application-owned `ActionRuntime`. Sidebar controls, shortcuts, tab-strip commands, panel buttons, and menus invoke those registrations; the registered handlers are the only writers for their semantic results. Each mounted terminal viewport creates a child scope in that same runtime and owns the stable minimal terminal catalog: Copy, Paste, Select All, Find navigation, prompt and retained-history navigation, last-command output viewing and copying, visible Hints, permitted link activation, Clear, and Reset. The injected surface registers implementations into that scope and supplies only revision-pinned semantic context for prepared context-menu invocation. Continuous separator resize updates the canonical panel layout as it changes and retains the last valid layout when interaction ends or is canceled. Panel drag preview remains reversible interaction state, while the final drag result invokes the corresponding Action.

The package owns a full-height, horizontally resizable two-panel shell. The left sidebar defaults to `250px` and is constrained to `200px`–`400px`; the right panel fills the remaining width and renders the active standalone or Workspace terminal context through `@orchbee/tab-strip`. The horizontal shell chrome is `36px` high: its `28px` sidebar control is centered in that row, and both the sidebar content inset and native drag surface use the same boundary. The sidebar control and `Mod+B` shortcut hide or restore the sidebar. The control remains mounted at one fixed shell position in both states. While the sidebar is hidden, a transparent leading position inside the tab-strip surface reserves its footprint so the control never overlaps the first tab or paints a separate background. The localized sidebar provides a standalone `Terminal` location, `Search`, an expandable Project and Workspace hierarchy, and a bottom-anchored `Settings` action. Project rows control disclosure without changing the active terminal context. Workspace rows switch to their independent Tab and Panel context; returning to Terminal restores the existing standalone context.

Right-clicking blank tab-strip space exposes a localized orientation action. The Workbench switches the strip and content layout between a top horizontal strip and a left vertical strip while tabs, groups, and the new-tab control keep their existing context menus.

The shell composes primitives from `@orchbee/ui` without owning PTY processes, filesystem or Git effects, settings destinations, authentication, routing, or agent orchestration lifecycles. Workbench owns the unified search state and presentation, while semantic owners remain responsible for searchable read models and Action registrations. The machine-readable scope contract lives in [`project.json`](project.json).

Workbench composition is explicitly `preview` or `managed`. Both receive an application-owned terminal-presentation identity allocator and one stable initial presentation ID. A managed composition additionally receives operation/removal ID allocators and a narrow command dispatcher; Workbench never allocates a Host terminal ID or uses one for topology or lifecycle mutation. The terminal-surface seam exposes an opaque Host terminal identity only to the bell-effect coordinator described below. Dynamic presentation IDs are opaque and must not be reused after a presentation is removed.

A managed application may seed the standalone context with recovered presentations. Each seed retains its application-owned PresentationId and launch CWD and is projected as one Tab; Workbench still does not infer or persist Project, Workspace, group, split, process, or Host identity. The runtime routes every provision, exit, and close result by PresentationId across all terminal contexts and rejects missing, duplicate, or stale targets without mutating another presentation.

Applications may inject a `terminalSurface` component. Workbench mounts it only for terminal presentations in the displayed Tab and visible Panel layout, passing the presentation model plus the viewport's application-owned Action runtime/scope, a narrow semantic-context registration seam, a bell-effect admission function, and an `autoFocus` projection, never a Host capability. Inactive Tabs, other Workspaces, background Projects, and inactive child terminals do not mount the surface. Workbench sets `autoFocus` only on the displayed terminal in the active Tab's remembered focused Panel. The injected surface claims its real terminal input when that projection becomes true, when a true target mounts, or when its recovered renderer becomes ready. A new Tab therefore focuses its first Panel terminal, returning to a Tab focuses that Tab's remembered Panel terminal, and splitting focuses the new Panel terminal. Closing the focused Panel selects the most recently focused surviving Panel; only an empty surviving history falls back to the previous visual leaf and then the next. Closing a non-focused Panel preserves and restores the focused terminal. Right-click retains the element that was focused before the menu opened and restores it when the menu closes, unless a selected structural command transfers focus to another terminal. This lets Desktop bind attachment and renderer lifetime to actual viewport demand while preserving Workbench ownership of logical topology and product focus.

One mounted Workbench panel-workspace lifetime owns one `WorkbenchTerminalBellEffectCoordinator`.
Every surface reports only an opaque terminal identity and positive Host bell sequence. The
coordinator retains mergeable sequence intervals per terminal, so duplicate, stale, reconnected,
and replayed attachment deliveries are rejected without losing a distinct sequence that arrives
out of order. Exactly the first admitted delivery may create the visual product effect and invoke
application capabilities. Workbench performs no audio or operating-system notification itself;
those remain two independent, default-absent application capabilities.

The stable headed `terminal-parity/PR-11-bell` witness composes multiple production terminal
surfaces with one Workbench coordinator and proves duplicate/reconnect suppression, interleaved
sequence admission, and independent optional-effect failures. The stable headed
`terminal-parity/IN-09-action-scope`, `terminal-parity/IN-11-context`, and
`terminal-parity/IN-12-actions` witnesses compose the minimal catalog in its containing Workbench
scope and prove native handling for unclaimed or unavailable Apple Command chords, pinned semantic
context with execution-time revalidation, synchronous availability, typed results, no added
confirmation, and localized feedback. These controlled Canvas fixtures capture application effects;
they do not claim native audio, operating-system notification, clipboard, or URL-handler delivery,
and they do not make Workbench a terminal-state authority.

Applications whose address is the authoritative Client View input may inject a `WorkbenchNavigationPort`. Workspace, standalone-context, and Tab-selection Actions then delegate navigation before Workbench mutates active Client View state; the application updates browser history and applies the resulting route back to the runtime. Without this port, Workbench retains its local in-memory navigation behavior. Workbench does not parse paths or own Router history.

Runtime-neutral terminal-presentation identities, lifecycle contracts, and boundary schemas are also available from `@orchbee/workbench/terminal-presentation`. Platform applications use that narrow entry point instead of importing the React Workbench graph into Main or preload runtimes.

## Experience catalog

Workbench keeps reviewed interaction and business-component Manifests in [`docs/experience`](docs/experience). The records describe their intended and excluded use, invariants, composition dependencies, implementation roots, and Storybook inspection states without turning private components into public exports. Discover them from the repository root with `pnpm experience:find --owner @orchbee/workbench`, then inspect a selected record with `pnpm experience:show <id>` before composing a new complex Workbench interface.

## Project and Workspace

The maintained in-memory model, ownership, fallback, CWD, duplication, and correctness contract lives in [`docs/project-workspace.md`](docs/project-workspace.md).

`WorkbenchProjectWorkspaceRuntime` owns the standalone terminal context plus one independent Tab model and Panel workspace per Workspace. Project and Workspace operations use stable Action IDs. The Project create control opens the common Folder acquisition menu. An application may inject the narrow `projectFolderAcquisition` capability for selecting one existing Folder. Desktop supplies that capability through its native picker and returns one host-normalized, validated path; Browser and Gateway omit it and retain the manual path-entry adaptation without claiming that the path exists. A selected path atomically creates the Project, its first Folder, its Primary Workspace, and the Workspace terminal projection. Project management reuses the same capability for `Add Folder`; Workbench rechecks the latest Project identity and exact duplicate paths before committing a late result. Cancellation and bounded failures perform no Project mutation, and only one selection may be active in one mounted Workbench. `New Folder…` remains visible but disabled because no composition currently performs filesystem mutation. Creating a Workspace starts one shell projection in its primary Project Folder. Preview duplication copies Tab groups, Panel layout, names, launch-configuration selection, and recorded launch CWD into fresh identities while resetting process-derived Tab, Group, and presentation state. Managed composition does not expose Project or Workspace duplication because it cannot silently clone a real process. Terminal projections keep launch CWD separate from host-reported current CWD. Directory refresh preserves stable identity, ordering, and primary references. Deleting a Workspace disposes only its Orchbee terminal context. Removing a Project disposes its Orchbee metadata and contexts and never claims to delete its folders or Git worktrees.

The package accepts host-normalized Directory descriptors and browser-entered paths and performs no filesystem, Git, PTY, or persistence effect itself. Desktop owns the current native existing-Folder selection and validation adapter; filesystem mutation, ongoing Directory observation, and Git effects remain application-owned future work.

## Unified search

The maintained behavior, ownership, transition, and correctness model lives in [`docs/unified-search.md`](docs/unified-search.md).

The sidebar Search control and the platform All-search binding—`Mod+Shift+F` on Apple and `Mod+Shift+K` on Standard—open one upper-viewport modal with the `All` filter and an empty query. `Mod+Shift+P` opens the same surface with the `Actions` filter. Each global open starts a new in-memory session; switching among `All`, `Agents`, `Actions`, and `Settings` preserves the current query, while closing discards the session. File search is intentionally absent.

The current local provider projects Actions by requesting subtree discovery from the mounted application `ActionRuntime`. It keeps every runtime-owned prepared or unbound invocation intact, groups results by localized Action category, explains disabled capabilities, displays the composing application's current shortcut label for Workbench and descendant terminal Actions, and invokes a selected ready result through `executePrepared(...)`. The tab-strip-orientation Action demonstrates nested input: selecting the command opens an in-surface horizontal/vertical picker, binds the selected value through `prepareInvocation(...)`, and then executes that same scope-bound token. The Settings provider projects the stable root Settings destination through `workbench.settings.open`.

`All` shows curated recommended Actions plus Settings before a query, then searches the complete local catalog after typing. Matching normalizes Unicode, case, and repeated whitespace and ranks exact localized titles, title prefixes, title-token prefixes, localized keywords, canonical English titles, and fuzzy subsequences in deterministic tiers. The `Agents` filter is present as the accepted navigation slot but remains empty because no agent-owned searchable read model or navigation Action is currently composed. The provider coordinator accepts bounded synchronous or asynchronous providers and rejects stale completions. File search, Agent fallback, persistent MRU, and user-editable keybindings remain outside the current implementation.

The dialog keeps DOM focus in its combobox. Up and Down move `aria-activedescendant` through inspectable results, Enter opens or runs the highlighted row, Escape returns from a nested picker or closes the surface, and pointer movement updates the same visual highlight. Input, filters, and footer remain fixed while grouped results scroll. Closing occurs before a selected Action begins; it does not cancel or assume ownership of that Action's asynchronous lifecycle.

### Search modeling record

- **Problem and inputs:** A person needs to discover and invoke product capabilities without knowing a menu location or shortcut. Trusted inputs are a reviewed open filter, the mounted Action scope, localized Action descriptors, and pointer or keyboard events. Query text is local user input. Missing Action input remains an unbound runtime token and is never guessed.
- **Data and ownership:** `WorkbenchSearchState` is the sole owner of the open session, filter, query revision, query, highlight, and nested parent snapshot. Semantic owners remain authoritative for Action availability and effects. Projected results carry stable provider, group, result, Action, and scope identity plus a runtime-owned prepared or unbound invocation.
- **Outputs:** Opening renders and focuses one modal session; filter and query changes produce a deterministic local projection; a disabled selection announces its reason without invoking; an unbound supported result enters a nested picker; a final enabled selection reaches at most one Action execution. Escape and outside dismissal commit no Action.
- **Transitions:** Open resets to the requested preset. Query changes increment the revision. Filter changes retain query text. Result changes retain a still-visible highlight and otherwise select the first enabled result, falling back to the first inspectable row. Nested Back restores the complete parent filter, query, revision, and highlight snapshot. Close retains only the next monotonic session identity.
- **Invariants:** A rendered highlight always names one current visible row; hidden Actions never render; disabled or unsupported unbound rows never execute; prepared input is bound only through the originating runtime token; one accepted row reaches at most one `executePrepared(...)` call; and closing or nested cancellation performs no domain mutation.
- **Dependencies and exclusions:** React owns the mounted dialog lifecycle and focus adapter; `@orchbee/actions` owns registration, discovery, preparation, availability, confirmation, and execution; `@orchbee/i18n` owns product copy; and design tokens own geometry and appearance. Network, storage, telemetry, process state, Agent data, and async provider coordination are excluded until their semantic owners expose the required contracts.
- **Verification:** Pure tests cover open/close, query and filter transitions, highlight movement, nested restoration, matching tiers, deterministic grouping, Settings de-duplication, and argument filtering. Runtime projection tests cover prepared and unbound results. Component tests cover combobox focus, Actions filtering, nested orientation input, Action execution, and close. Storybook supplies open All and Chinese Actions states; browser verification exercises both shortcuts, four filters, keyboard and pointer selection, nested input, dismissal, and both tab-strip orientations.

## Panel workspace

Panel separators use axis-specific local CSS cursors while the resize primitive's document-global cursor injection remains disabled. Crossing a separator may change the cursor only while that separator is the pointer target, so leaving the target, cancelling a pointer, or losing capture cannot strand a resize cursor over unrelated terminal content.

The product terminal context menu captures the exact focused element before opening. Closing it after a non-structural command, including Clear, returns focus to that element; a successful split suppresses restoration so the new Panel's terminal auto-focus transfer wins.

Each terminal tab owns an in-memory panel workspace below its tab strip. A new tab starts with one full-size panel and one special primary terminal. The single-panel primary view omits panel chrome. When the terminal application does not own mouse input, right-clicking the terminal viewport exposes a product-curated terminal set—Open Link when applicable, Copy, Paste, Select All, Find, Show Last Command Output, and Clear—before a deliberate structural set: New Tab, New Child Terminal, panel maximization, a four-direction Split submenu, and Close Terminal. Find Next, Find Previous, Scroll to Bottom, and Reset remain discoverable in Action search without lengthening the frequent pointer menu. A link Action appears only when the surface captures an exact link target at menu-open time. Commands render a trailing shortcut only when the composing application supplies a current effective binding. Menu close carries the clicked panel as an explicit Action target; keyboard close uses the active Tab's focused panel. Both resolve through the same contextual close Action. A child terminal occupies the same viewport as its primary terminal; child terminals appear in a real `40px` bottom strip, while the primary terminal never appears in that strip. Activating a child adds a `32px` header with a return action, geometrically centered terminal title, and close action.

Once a tab has multiple panels, every panel displays the header. Its panel-options menu contains Maximize Panel or Minimize Panel and projects the same current binding as the viewport menu and Action search. Maximizing projects `100/0` layouts along the target's split ancestry and hides sibling branches while keeping the complete Panel React tree and every terminal surface mounted; minimizing restores the canonical weights without replacing terminal DOM identity. During either transition, every affected split withholds the focused terminal's `autoFocus` projection until its resizable primitive has synchronized the projected layout, then the same mounted terminal reclaims input focus and remeasures its surface before accepting further input. Splitting a maximized panel first restores the tree and then applies the split. Exactly one panel is focused; that panel retains the normal terminal surface while every other panel receives a non-interactive inactive mask. Primary-pointer or keyboard focus inside a panel transfers focus and the mask to that panel; secondary-pointer context intent alone does not. The active Tab projects its remembered focused Panel's displayed primary or child terminal as the sole terminal `autoFocus` target. Tab activation, initial Tab creation, child-terminal activation, Panel splitting, Panel movement, and focused-Panel closure therefore restore or transfer real terminal-input focus through the injected surface without coupling Workbench to the surface's DOM. Dragging a primary-terminal panel header lifts a scaled visual snapshot cloned from that panel's current DOM, removes the source from a reversible layout projection, and immediately reflows the remaining grid. The snapshot preserves current panel chrome and terminal presentation without mounting a second React terminal instance. A header showing an active child terminal is not draggable. Moving over another panel's directional edge projects the complete final grid with an empty framed panel at the destination. Dropping replaces that placeholder with the complete source panel and splits the target above, below, left, or right without replacing any terminal identity or state. The center of a target is intentionally inactive so a release without a directional placeholder cancels and restores the canonical grid. Contextual close resolves one target: the displayed child terminal, otherwise a primary panel when another panel survives, otherwise the active Tab. In preview composition, closing an active child affects only that child and returns to the primary terminal; closing a primary view affects the panel and all of its children. In managed composition, the same intent first marks every affected presentation as closing and emits one exact close command per presentation. Topology remains present until every close completes, but an accepted active-Tab close immediately selects the nearest later Tab not already pending close, then the nearest earlier one. Repeated keyboard closes therefore target distinct Tabs without waiting for Host disposal. A localized confirmation is required for preview, restoring, or reconciling presentations and for a provisioning or `running` presentation whose transient close activity is `active` or `unknown`. A provisioning or `running` presentation classified as `idle` closes directly. Panel closure counts the primary and child presentations it affects. Tab closure traverses every panel in every requested tab and counts all primary and child presentations before the Tab Strip action can commit. Application lifetime aggregates that same predicate across every context and tab; it does not infer protection from the broader non-stopped session count. The confirmation count includes only affected presentations that require protection. A partial failure retains the failed presentation and already-closed siblings for explicit retry, without rollback. The last panel in a tab is not closable through the panel lifecycle because the tab lifecycle owns that case.

An active-Tab identity change cancels any presenter-owned Panel drag before paint and restores the source Tab's canonical layout, so a source preview cannot leak into the newly active Tab.

A managed terminal's identity-checked natural exit is an unconfirmed terminal-level removal intent. An exiting child removes only that child and, when displayed, returns the Panel to its primary terminal. An exiting primary with children closes only the exited presentation; after Host disposal completes, the active child is promoted to primary, or the first child when none is active, without stopping any surviving child. An exiting primary without children closes its Panel when another Panel survives and otherwise closes its Tab; closing the final Tab does not close the native application window. Exit code and signal do not change this policy, while `terminal-failed` remains inspectable. The exit transition enters the existing managed removal protocol atomically, so an explicit removal already in progress wins, topology remains until every required close completes, and a disposal failure retains the exact target for retry. Natural exit does not add a configurable keep or restart mode.

Terminal process rendering and retained-output search execution remain terminal-surface capabilities. Find is exposed through the terminal Action scope and its available shortcut without occupying panel-header chrome; Find Next and Find Previous become enabled synchronously only while the mounted find controller has a non-empty query.

Committed projected-terminal metadata enters Workbench through `applyTerminalMetadataObservation(...)`. A terminal's natural OSC title remains separate from the durable launch fallback and the optional durable custom Tab title. Display resolution is custom title, then the focused terminal's latest natural title, then the final non-empty path segment of its current CWD or launch CWD, then the fallback. Product-created fallbacks are the localized unnumbered Terminal label, so a new Tab shows launch-directory context immediately without coupling its title to an identity sequence. Later natural-title changes remain recorded beneath a custom title, and clearing the custom title reveals the latest natural title immediately. Host-reported OSC 7 CWD is accepted only after the application supplies its trusted terminal-machine hostname and the shared policy validates and decodes the URI; an invalid observation cannot replace the last accepted current CWD. The same observation carries transient close activity as `idle`, `active`, or `unknown`. A product-created managed presentation begins `idle` solely as evidence that Orchbee has accepted no local input for that fresh shell; hydrated and preview presentations begin `unknown`. Accepted local non-focus activity immediately invalidates either application-fresh or Host-observed `idle` to `unknown` before close Action evaluation. An `idle` frame already in flight at invalidation remains `unknown` until the terminal client completes its causal snapshot barrier. That barrier proves only that the replacement frame follows invalidation; it proves neither Host acceptance nor shell consumption. A later causally eligible current-state projection may report `active`, `idle`, or `unknown`, including restoring fresh `idle` after Host-accepted input. Observed `active` or `unknown`, including a platform query failure, always restores conservative confirmation. The value is neither persisted nor treated as terminal lifecycle authority.

### Modeling record

- **Problem and inputs:** A person or future command adapter needs deterministic local panel composition, terminal-input continuity, and natural-exit cleanup without coupling geometry or DOM input internals to terminal-process ownership. Trusted inputs are the immutable `TabModel` snapshot, semantic UI events, identity-checked terminal lifecycle results, generated managed close identities, and the injected surface's renderer-readiness lifecycle. A missing active tab renders no panel workspace and has no terminal focus target. The shared-document projection persists hierarchy and terminal lifecycle intent, while focus, maximization, active child, and weights project into Client View; malformed storage handling remains an application-boundary concern.
- **Data:** `PanelWorkspaceState` owns an ordered workspace per tab ID. Each workspace has one canonical `PanelLayoutNode` tree, one focused panel ID, one unique least-to-most-recent Panel focus history whose tail is that focused ID, and at most one maximized panel ID. A leaf owns exactly one primary `TerminalPresentation`, an ordered one-level child list, and zero or one active child presentation ID. Every split owns exactly two ordered children; each child carries a stable globally unique layout slot ID, independent from Panel and Split identity, plus a non-negative percentage weight. Each terminal presentation records its Workbench-owned opaque ID, durable fallback title, transient nullable natural title, nullable launch/current CWD, transient `idle`/`active`/`unknown` close activity, and a discriminated lifecycle. Each Tab title policy records its durable fallback and optional custom title. `pendingRemovals` records the exact child, primary-promotion, Panel, or Tab removal set while asynchronous close results are outstanding; a primary-promotion removal selects an eligible surviving child only at atomic commit.
- **Outputs:** `transitionPanelWorkspace` returns the complete next state plus `applied`, `unchanged`, or a named rejection and zero or more typed provision, close, or Tab-ready commands. `resolveDirectionalPanelFocus` derives one neighboring Panel ID or `null` from a canonical layout, source Panel, and direction; it never mutates focus itself. The presenter projects `autoFocus` only for the active Tab's focused Panel and displayed primary or child terminal; the injected surface turns that projection into a real input-focus effect after mount or renderer readiness. A maximize or minimize projection temporarily removes that effect while any affected split has not synchronized its exact `100/0` or canonical layout, then reasserts it after the final synchronous layout commit so the surface remeasures at the committed Panel size. A natural exit either atomically enters one managed removal, is an equivalent no-op for the same exit already being removed, or rejects a stale/conflicting result without allocating a second removal. The pure transition and resolver perform no process, DOM, storage, time, random, or network effects. Provisioning and runtime failures retain the presentation and its owning topology for inspection or retry.
- **Transitions:** Tab reconciliation preserves workspaces by tab ID and creates or removes only the changed tab projections. Four-direction split, adjacent resize, focus, primary/child selection, child creation/close, panel move/close, maximize/minimize, custom-title set/clear, and complete terminal-metadata observation are the maintained semantic events. Managed provision completion/failure/retry, natural process exit with its Workbench-generated close request, close completion/failure/retry, and Tab-close requests are explicit identity-correlated events. Natural child exit begins a child removal. Natural primary exit begins a primary-promotion removal when children survive, a Panel removal when another Panel survives, and otherwise a Tab removal. Promotion commits only after disposal of the exited primary reaches `closed`; it selects the eligible active child, falls back to the first eligible child, and waits when every child is targeted by another pending removal. Every split replaces the targeted Panel leaf with a new binary `50/50` split, including when the new split repeats its parent orientation; the parent slot and parent weight remain unchanged. Closing or lifting one leaf replaces only its immediate split parent with the surviving sibling, so ancestor split identities, slots, and weights remain unchanged. Panel move applies that local removal before inserting the same leaf around the target, and never allocates a panel or terminal identity. The drag projection applies that same pure tree transformation without committing it, allowing cancellation to restore the untouched canonical tree. Moving an already adjacent Panel back to its current side is an intentional no-op that preserves split identity, slot identity, and resized proportions. Every semantic focus transfer moves its Panel to the focus-history tail. Closing a non-focused Panel removes only that history member and preserves focus; closing the focused Panel selects the newest surviving history member, with previous-then-next visual order only as an empty-history fallback. Tab activation reuses that Tab's focused Panel; a newly reconciled, hydrated, or cloned Tab starts with only its focused Panel in history; split and move transitions focus and record the inserted or moved Panel; displayed child selection and primary promotion retain the owning Panel as the focus owner. Accepting an active managed Tab close marks its removal first, then changes the Client View selection to the nearest later non-pending Tab or the nearest earlier one; if every Tab is pending, selection remains until completion removes it. A managed removal changes membership only after every target reaches `closed` and evaluates focus history at that commit; a Tab emits `tab-close-ready` last and remains until `TabModel` reconciliation confirms deletion. New primary and child terminals inherit the displayed source terminal's nullable CWD.
- **Invariants:** Every tab has at least one panel; panel, split, and presentation IDs are unique; focused and maximized IDs resolve within their tab; focus history is non-empty, contains only unique live Panel IDs, and ends with the focused ID; active child IDs resolve within their panel and never equal its primary ID; the active Tab has exactly one displayed terminal `autoFocus` target while no active Tab has none, except during a maximize or minimize layout commit when the logical target remains unique but the effect is withheld; every split has exactly two children, layout slot IDs remain globally unique, child weights total exactly `100` within numeric tolerance, and a resize changes only that split's two children. Repeated split orientations remain nested because split ancestry owns later close and resize behavior. Maximization changes only rendered layout, hidden state, and the temporary focus-effect gate; it never changes topology, canonical split weights, logical focus, terminal-surface mount state, or terminal DOM identity. The focus effect becomes eligible again only after every split on the visible ancestry reports the requested primitive layout synchronized. Closing or lifting a panel removes its immediate parent split, promotes the surviving sibling into the unchanged ancestor slot, removes the closed ID from history, and retains a deterministic MRU-then-visual focus target. Pending removals are non-empty, never overlap, resolve to live topology, and match only `closing`, `close-failed`, or `closed` lifecycle states bearing that removal ID. While any non-pending Tab survives, accepting a close never leaves a pending Tab active. A pending primary-promotion removal keeps the exited primary in place until atomic commit, and promotion never selects a child targeted by another pending removal.
- **Decisions:** Splitting the right half of `[50, 50]` preserves the outer `[50, 50]` split and creates an inner `[50, 50]`, whose rendered widths are `[50, 25, 25]`; closing either inner leaf restores the outer two equal halves. Split creation remains valid even when the resulting viewport is narrower than `30px`; this keeps semantic split commands deterministic instead of letting a rendering constraint reject the model. Directional focus projects the weighted layout tree into normalized rectangles. A candidate must lie completely in the requested direction and share a positive perpendicular-axis span with the source. The resolver selects the smallest directional edge gap, then the smallest perpendicular center distance, then stable visual leaf order. A missing source, a singleton layout, zero candidates, or navigation while a Panel is maximized is an unavailable no-op; navigation never wraps. The resolver itself does not mutate history, while its successful semantic focus event does. Focus history is unique MRU state scoped to one live Tab: hydration and duplication initialize only the current focused Panel, retained runtime Tabs preserve still-valid entries across shared-document application, and neither shared document nor Client View serializes it. During separator resize, both children are constrained to at least `30px` along the active axis; nested splits therefore protect Panel dimensions at their own local boundary. Every accepted resize candidate updates the canonical layout immediately; completion, pointer cancellation, and lost capture retain the last accepted layout rather than restoring the starting layout. Maximize and minimize convergence uses the existing mounted surface and `autoFocus` seam; remounting, synthetic global resize events, and automatic replay of a rejected Host resize are excluded. Separators keep a single opaque one-CSS-pixel color through intersections. Panel header and child-strip space is never overlaid on the terminal viewport. Natural exit always removes the exited presentation regardless of exit code or signal, but never reclassifies `terminal-failed` as exit. Child exit removes only that child. Primary exit promotes the active child or first child instead of terminating survivors; only a primary with no children escalates to Panel or Tab removal. The final Tab may close while the native Workbench window remains. Previous/next focus cycling, directional resize shortcuts, manual close confirmation, development-topology migration, and the planned configurable keep/restart exit modes are excluded.
- **Ownership and dependencies:** Workbench is the sole writer of the panel layout, Tab-title projection, logical terminal-presentation identity/lifecycle state, remembered focused Panel, and surface `autoFocus` projection. `TabModel` remains authoritative for tab order and active tab. The application injects identity allocation, a trusted terminal-machine hostname for OSC 7 normalization, returned managed-command dispatch, and the terminal-surface adapter; that adapter owns renderer readiness and the real input-focus call but cannot select a different semantic target. The application cannot supply executable, environment, Host terminal, or attachment identities through this model. The resizable primitive owns raw pointer input, native keyboard behavior, separator focus and accessibility, and candidate layout production. Workbench does not reinterpret those input bindings; it owns topology validation, adjacent-pair projection, the `30px` policy, and the only semantic layout write. Resize is not registered as an Action. Hosts remain authoritative for PTY/process lifecycle, real CWD discovery, terminal rendering, and eventual CLI/agent command transport. Future header metadata such as panel status, Node version, Git branch, and change counts is deliberately excluded until an owning data contract exists; the current three-zone header preserves a composition point for it.
- **Reference scope:** Focus selection, binary split insertion and sibling promotion on close, default natural-exit closure, and prompt-based close reclassification follow Ghostty revision `91f66da24527fa02d92b5fd0b41cd020f553a64c`; directional focus and focused-Panel close recovery also compare Warp revision `086dade63ff7327426d6276d57f85b3f2f313af0`. The adopted split-topology projection is Ghostty's `SplitTree` rule from `macos/Sources/Features/Splits/SplitTree.swift`: inserting at a leaf replaces it with a binary split at ratio `0.5`, and removing one child replaces the immediate parent with its surviving sibling without changing ancestor ratios. The adopted directional projection is the shared Apple `Command+Option+Arrow` and Standard `Control+Alt+Arrow` default, no wrapping at an outer edge, spatial selection from the weighted split layout, and focus through the existing Panel Action. Ghostty contributes normalized spatial slots and stable nearest-candidate ordering; Warp contributes immediate split-tree candidates constrained by perpendicular rectangle overlap. Close recovery adopts Warp's per-`PaneGroup` unique MRU `pane_history`, retain-then-append focus update, selection before removal, and reverse scan for a surviving candidate. Orchbee deliberately scans surviving history at every length instead of adopting Warp's positional fallback when history has at most two entries. Warp's recent-focus tie-break for directional navigation, Ghostty's diagonal non-overlap fallback, previous/next cycling, zoom-preserving navigation, native responder mechanics, visual focus effects, split equalization, and undo are outside parity scope. The remaining adopted Ghostty projection is per-Tab last-focused surface memory, first-surface fallback, unconditional focus of a new split, immediate surface close after a non-waiting child-process exit, and reevaluation of current `Terminal.cursorIsAtPrompt()` state instead of permanent input memory, as implemented by `src/Surface.zig`, `src/terminal/Terminal.zig`, `macos/Sources/Features/Terminal/BaseTerminalController.swift`, and `TerminalController.swift`. Orchbee's one-level child terminals have no Ghostty equivalent. ### Tab presentation handoff modeling record

- **Problem and non-goals:** Switching between populated Tabs can expose an empty terminal when an incoming layout commits before its asynchronously mounted visible terminals have painted. The handoff preserves a continuous meaningful presentation without keeping inactive Tab trees, attachments, canvases, or renderers resident. Persistent output storage, a second VT authority, synchronous WebGPU pixel readback on the activation path, and a guarantee that a never-presented target already has current pixels are excluded.
- **Inputs and data:** Trusted inputs are the active `TabModel` identity, the complete displayed-terminal identities in the target topology, the visually contributing required subset projected from maximization and canonical positive-weight branches, monotonic handoff epochs, and display-ready or activation-ready reports carrying the exact epoch, target Tab identity, and presentation identity. A maximized workspace requires only that exact Panel's displayed terminal; a normal workspace recursively excludes every zero-weight branch. `TerminalTabPresentationHandoffState` owns one settled displayed Tab, one preparation with an outgoing layer, or one target-only activation barrier; pending states retain the current required identities plus separate display-ready and activation-ready ledgers for the current target. The React integration retains at most one read-only outgoing workspace projection keyed by the displayed Tab identity, including after canonical Tab removal, and never treats that projection as current topology or an Action target. Readiness ledgers may include current-target reports that arrived before an identity became required. Reports with an old epoch, the wrong target Tab, or a duplicate identity are no-ops.
- **Outputs and commit:** A settled state renders one interactive Tab layer. A preparation renders the frozen outgoing layer above one inert incoming layer and projects no terminal `autoFocus`. After every required target presentation reports meaningful cached, live, stopped, or honest failure content, the target becomes the sole visible but still inert layer. Only a live first frame, stopped presentation, or terminal failure contributes activation readiness; after every required target reaches that second barrier, Workbench makes the target interactive and restores the sole `autoFocus` projection. A target with no required injected terminal surfaces commits immediately.
- **Transitions and cancellation:** Changing the active Tab starts a new epoch, freezes the currently presented terminal surfaces, and prepares the newest target. A second Tab change supersedes the prior target, keeps the same visible outgoing layer, and rejects every late report from the old epoch or target Tab. Changing the required subset within the same target Tab retains the epoch and its readiness ledgers, then deterministically derives preparation, activation, or settlement from the newest subset; this covers maximize, minimize, split, close, resize-to-zero, and displayed-child changes without stranding the barrier or accepting another Tab's reports. Returning to the still-presented Tab resumes through the same preparation contract instead of granting input to a frozen surface. A managed close freezes the painted active surface and retires its interaction ownership before canonical topology changes. Removing the outgoing Tab from canonical topology detaches but does not clear its transient presentation layer; the newest available target becomes the presentation owner only after its display barrier commits. Closing the final Tab has no surviving target and clears the presentation normally.
- **Invariants:** A transparent or empty incoming terminal is never the top committed layer while an outgoing layer exists, including after that outgoing Tab leaves canonical topology; neither preparation nor a target-only activation barrier has an interactive terminal layer; activation readiness implies display readiness; only exact current-epoch, current-target reports contribute readiness; required identities are unique but readiness ledgers may be supersets of them; hidden maximized siblings and zero-weight branches cannot block a commit; a detached outgoing projection is read-only and cannot re-enter canonical topology or publish Action intent; outgoing attachments and input ownership retire before their frozen pixels are used as presentation; and a display snapshot never supplies attachment identity, input authority, resize ownership, transport commands, frame acknowledgement, metadata publication, or durable Workbench state.
- **Terminal and application dependencies:** `@orchbee/terminal` owns immutable display-only packed snapshots and one reference-counted, document-scoped WebGPU device/pipeline runtime; each live renderer continues to own its canvas, atlas, buffers, and fallback, while the final renderer lease retires the shared device. The Web application owns a `32 MiB` byte-accounted least-recently-used snapshot cache and maps surface display readiness into the Workbench callback. Cache admission may reject an oversized snapshot, and a miss retains the frozen outgoing layer until live content or an honest failure is available. The cache performs no storage or IPC effect and is cleared with the client runtime.
- **Memory, failure, and recovery:** Inactive Tabs retain neither React terminal DOM nor GPU surfaces. The bounded cache retains packed presentation data only; one frozen outgoing renderer may survive transiently until commit, supersession, or disposal. A shared-device loss affects every WebGPU surface using that device, which independently enters the existing typed recovery path against the next shared generation; Canvas 2D remains the fallback. Cache rejection, eviction, unavailable WebGPU, attachment failure, and snapshot absence degrade to the outgoing-frame barrier rather than a blank commit.
- **Decisions and alternatives:** Keeping all Tab surfaces mounted was rejected because it retains attachment, DOM, atlas, and GPU cost per inactive terminal. Capturing a raster on Tab activation was rejected because synchronous `drawImage` or readback can stall the interaction path and pixel snapshots scale with viewport area. Painting only a background was rejected because it still presents lost terminal content. The selected semantic snapshot plus shared-runtime and atomic-layer handoff keeps steady-state ownership equivalent to the current inactive-Tab policy while moving bounded work off the activation critical path.
- **Correctness and verification:** Pure projector examples cover maximized and nested-maximized workspaces plus normal positive- and zero-weight branches. Pure transition examples cover initial settlement, one- and multi-presentation display and activation readiness, duplicate, stale, and wrong-target reports, activation-before-display reordering, supersession from either barrier, same-target subset shrink and expansion with early current-target reports, return to the frozen source, cache miss, no-surface targets, and outgoing removal. The `TerminalTabPresentationHandoff` TLA+ model checks bounded reordered readiness, same-target retargeting, topology removal, and supersession for continuous meaningful presentation, no early visual commit, no stale or wrong-target commit, activation-after-display, and exclusive interaction. React integration covers active-Tab closure retaining the detached outgoing layer, the maximized-Panel Tab-return regression, and cross-Tab drag cancellation. Terminal tests cover immutable structural sharing, drawn-revision capture, display-only authority, shared WebGPU acquisition/loss, and per-renderer resource disposal. Web tests cover managed-close frame freezing without reacquisition, byte-budget LRU eviction, freeze/cache/resume ordering, cached and uncached dual readiness, and recovery. The controlled Desktop trace waits on named attachment and rendered-generation checkpoints and asserts that rapid switching or closing the active Tab never exposes an empty committed layer or retires the shared control; it excludes the manual native-window focus test, other browser engines, operating-system compositor timing, and unbounded device-memory claims.
- **Reference and rollback:** Ghostty revision `91f66da24527fa02d92b5fd0b41cd020f553a64c` and Warp revision `086dade63ff7327426d6276d57f85b3f2f313af0` informed the lifetime comparison only; Orchbee does not claim source or pixel parity. This change has no schema migration or durable data. Reverting the handoff state, snapshot seam/cache, and shared runtime together restores the prior remount behavior; Canvas fallback and uncached live-first-frame recovery remain available throughout rollout.

## Use

Import the UI compatibility stylesheet once before the Workbench stylesheet at the application composition boundary:

```ts
import '@orchbee/ui/styles.css';
import '@orchbee/tab-strip/styles.css';
import '@orchbee/workbench/styles.css';
```

Render the shell at the same boundary:

```tsx
import {
	Workbench,
	type WorkbenchHostActionCallback,
	type WorkbenchLayoutStorage,
	type WorkbenchNavigationPort,
	WorkbenchProjectWorkspaceRuntime,
	type WorkbenchShortcutPlatform,
	type WorkbenchTerminalFontSizeChangeCallback,
	type WorkbenchTerminalSurface,
} from '@orchbee/workbench';
import { ActionRuntime } from '@orchbee/actions';

export function ProductInterface({
	actionRuntime,
	layoutStorage,
	navigation,
	onSettings,
	onTerminalFontSizeChange,
	projectWorkspaceRuntime,
	shortcutPlatform,
	terminalSurface,
}: {
	readonly actionRuntime: ActionRuntime;
	readonly layoutStorage: WorkbenchLayoutStorage;
	readonly navigation?: WorkbenchNavigationPort;
	readonly onSettings: WorkbenchHostActionCallback;
	readonly onTerminalFontSizeChange?: WorkbenchTerminalFontSizeChangeCallback;
	readonly projectWorkspaceRuntime: WorkbenchProjectWorkspaceRuntime;
	readonly shortcutPlatform: WorkbenchShortcutPlatform;
	readonly terminalSurface?: WorkbenchTerminalSurface;
}) {
	return (
		<Workbench
			actionRuntime={actionRuntime}
			layoutStorage={layoutStorage}
			navigation={navigation}
			onSettings={onSettings}
			onTerminalFontSizeChange={onTerminalFontSizeChange}
			projectWorkspaceRuntime={projectWorkspaceRuntime}
			shortcutPlatform={shortcutPlatform}
			terminalSurface={terminalSurface}
		/>
	);
}
```

Create one `ActionRuntime` and one `WorkbenchProjectWorkspaceRuntime` for each mounted application composition and dispose application-owned resources with that composition. Initialize the Project/Workspace runtime with the system CWD and localized first terminal title. Its in-memory terminal-creation Action preserves the requested Tab group and optional insertion index. Optional host callbacks such as Settings and application-wide terminal font-size changes still return a structured `ActionResult`, may return it asynchronously, observe `context.signal` before commit, and call `context.markCommitted()` immediately before their authoritative mutation.

When storage is provided, Workbench restores `orchbee:workbench:left-panel-width:v1`, `orchbee:workbench:left-panel-visibility:v1`, and `orchbee:workbench:tab-strip-orientation:v1`. It parses complete JSON records with feature-owned strict Zod schemas, saves width only after a completed user resize, and saves visibility or tab-strip orientation only after the corresponding semantic toggle action. Missing, malformed, unavailable, or out-of-range storage falls back to a visible `250px` sidebar and a horizontal tab strip without blocking rendering. The repository-wide ownership and key contract lives in [`docs/frontend/browser-storage.md`](../../docs/frontend/browser-storage.md).

Workbench owns the in-memory Tab and Panel context projection; the composing application remains authoritative for PTY and terminal-process lifecycle effects. A managed composition dispatches typed presentation commands and feeds their typed results back through `applyTerminalPresentationEvent(...)`. Tab close is delegated: Workbench marks every contained presentation closing, retains topology while results are pending, and removes the Tab from `TabModel` only after every exact close completes. A desktop host may pass `createCrossWindowDragRuntime` to connect the strip's pointer lifecycle to host-owned live-window discovery, compatibility checks, native window movement, capture, and move-loop behavior. Workbench and the browser application do not fabricate those operating-system capabilities.

Workbench exposes a runtime-theme revision coordination contract across Workbench, Terminal Host,
and the projected client. Workbench owns supersession and publication eligibility; the contract
keeps Host-owned terminal defaults/palette/cursor and client-owned pixels, overlays, cursor, and
application surface on one matching complete revision. Its model, retry rules, bounded evidence,
and Host/client refinement are maintained in
[`docs/terminal-theme-revision.md`](docs/terminal-theme-revision.md).
The Host compare-and-set, complete recovery state, projected-terminal frame staging, renderer
preflight, and application-wide synchronous publication barrier are implemented. A revision becomes
visible only after every mounted participant can commit the exact Host-tagged frame and complete
client snapshot.

### Shared document and Client View boundary

`@orchbee/workbench/document` separates the canonical revisioned `WorkbenchSharedDocument` from one page's disposable `WorkbenchClientView`. Project, Workspace, Tab/Group membership, durable fallback and custom Tab titles, Panel/Split structure, terminal-presentation placement, and durable lifecycle intent are shared. Active and selected navigation, disclosure, focus, maximization, active child presentation, and Split weights are client-local. Per-Tab MRU Panel focus history exists only in the live Workbench runtime and initializes from the Client View's focused Panel; it is outside both serialized contracts. Natural terminal titles, current CWD, viewport demand, scroll, search, selection, copy, GPU state, and `AttachmentId` remain outside both contracts.

A managed `WorkbenchProjectWorkspaceRuntime` projects these contracts through `getSharedDocument(...)` and `getClientView()`, hydrates them through `initialDocument` and `initialClientView`, and can apply a broadcast document through `applySharedDocument(...)` without dispatching process effects. `subscribeDocument(...)` supplies the application durability coordinator; its shared fingerprint is unchanged by Client View-only transitions. After the application establishes its persistence barrier, `reconcileDurableTerminalPresentations()` replays persisted provision, close, and stop operations and converts retain intent into restore-only commands.

An application-lifetime owner can capture `getRestartableTerminalPresentationIds()` before sealing terminal creation, durably stop those exact sessions, and then call `stageStoppedTerminalSessionsForRestart(...)`. Restart staging replaces only the captured stopped presentations with fresh PresentationIds and provision operation identities while preserving their placement, title, and launch CWD. It updates the shared-document projection without dispatching provision commands into the retiring runtime; the next application runtime performs those effects through ordinary durable reconciliation. Already-stopped and closing presentations are not captured or restarted.

The package performs no storage or IPC effect. A composing application parses the contracts at its boundary and owns private storage, shared revisions, write ordering, recovery diagnostics, and eventual Terminal lifecycle effects. The version-1 parser defaults an omitted `customTitle` to `null` while retaining no reader or alias for the unshipped topology schema. The maintained model, invariants, and evidence are defined in [`docs/shared-workbench-document.md`](docs/shared-workbench-document.md).

Workbench owns twenty-seven stable shortcut declarations: Actions search, New Tab, application-wide terminal font-size increase/decrease/reset, nine positional Tab selections, previous- and next-Tab selection, contextual Close Terminal, All search, Settings, sidebar toggle, panel maximization, split right, split below, and directional Panel focus. Font size defaults are `⌘=`, `⌘-`, and `⌘0` on Apple and `Ctrl+=`, `Ctrl+-`, and `Ctrl+0` on Standard; the composing application owns the appearance mutation through one optional host callback. The positional defaults are `⌘1` through `⌘9` on Apple and `Ctrl+1` through `Ctrl+9` on Standard. Each resolves its one-based input against the active context's canonical `TabModel.tabs` order, including the pinned prefix and members of collapsed groups, then executes the prepared `tabs.tab.select` Action; a missing position falls through and position nine is never an alias for the last Tab. Previous and next selection follows that same canonical order, wraps across its boundaries only when at least two Tabs exist, and is unavailable for an empty, singleton, or missing-active-Tab snapshot. Apple adjacent defaults are `⇧⌘[` and `⇧⌘]`; Standard adjacent defaults are `Ctrl+PageUp` and `Ctrl+PageDown`. Apple directional defaults are `⌥⌘←/→/↑/↓`; Standard directional defaults are `Ctrl+Alt+←/→/↑/↓`. The other Apple defaults are `⇧⌘P`, `⌘T`, `⌘W`, `⇧⌘F`, `⌘,`, `⌘B`, `⇧⌘Enter`, `⌘D`, and `⇧⌘D`. The other Standard defaults are `Ctrl+Shift+P/T/W/K/B/Enter/D`, `Ctrl+,`, and `Ctrl+Shift+E` for split below; unshifted terminal control sequences continue to the PTY. A composing application injects one complete current Workbench binding table keyed by shortcut identity, publishes whether Workbench is the active shortcut scope, and may inject a read-only effective label map for terminal-owned Actions. While active, Workbench resolves its bindings from one capture listener on its owning document, independently of which Workbench region or the document body has focus. An inactive or unmounted Workbench does not participate; Web makes it inactive while the full-screen Settings surface is open. The same binding values drive matching, menus, tooltips, and Action-search labels, including the distinct All and Actions inputs of `workbench.search.open`. The tab context menu projects the current New Tab and contextual Close Terminal labels; commands without a binding leave the trailing shortcut slot empty. A shortcut is consumed only when its Action is currently enabled; unmatched and unavailable bindings continue to the focused surface without suppression. Successful New Tab execution makes its first Panel terminal the sole `autoFocus` target, including creation from an empty Tab model. Directional focus is unavailable for a missing neighbor or while a Panel is maximized, so those chords also fall through without suppression.
