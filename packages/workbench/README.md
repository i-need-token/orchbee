# @orchbee/workbench

Private package entries export only symbols consumed in this repository, enforced by Knip `includeEntryExports`. Internal contracts, generated assets and independent conformance evidence retain their owners; their presence does not automatically expand the public entry. New clients add exports for admitted uses.

The `document` and `runtime` package subpaths emit JavaScript and
declarations under `dist/workbench/`, preserving their source-relative layout for dependency
analysis; `runtime` builds from `src/workbench/model/`. Consumers use the package subpaths; the
build paths do not introduce a separate public import surface.

Shared product-semantic React shell for Orchbee applications.

## Scope

Workbench registers its product operations in the application-owned `ActionRuntime`. Sidebar controls, shortcuts, tab-strip commands, panel buttons, and menus invoke those registrations; the registered handlers are the only writers for their semantic results. Each mounted terminal viewport creates a child scope in that same runtime and owns the stable minimal terminal catalog: Copy, Paste, Select All, Find navigation, prompt navigation, retained-history navigation, complete retained-history viewing and copying, last-command output viewing and copying, visible Hints, permitted link activation, Clear, and Reset. The injected surface registers implementations into that scope and supplies only revision-pinned semantic context for prepared context-menu invocation. Continuous separator resize updates the canonical panel layout as it changes and retains the last valid layout when interaction ends or is canceled. Panel drag preview remains reversible interaction state, while the final drag result invokes the corresponding Action.

The package owns a full-height, horizontally resizable two-panel shell. The left sidebar defaults to `250px` and is constrained to `200px`–`400px`; the right panel fills the remaining width and renders the active standalone or Workspace terminal context through `@orchbee/tab-strip`. The horizontal shell chrome is `36px` high: its `28px` sidebar control is centered in that row, and both the sidebar content inset and native drag surface use the same boundary. The sidebar control and `Mod+B` shortcut hide or restore the sidebar. The control remains mounted at one fixed shell position in both states. While the sidebar is hidden, a transparent leading position inside the tab-strip surface reserves its footprint so the control never overlaps the first tab or paints a separate background. The localized sidebar fixes full-row `New workspace` and `Search` actions at the top, in that order, and anchors `Settings` at the bottom. Icons and labels align left; the whole row supports pointer and keyboard activation. New workspace uses the existing immediate independent-Workspace creation flow, while Search opens the existing All-search surface. A separate fixed `Workspaces` heading reports the complete Workspace count without controls. The list scrolls independently below it, including the standalone `Terminal` location and expandable Project/Workspace hierarchy; the existing optional Create Project menu follows the list instead of sharing the heading. Narrow sidebars retain single-line action labels and the same full-row targets. Project rows control disclosure without changing the active terminal context. Workspace rows switch to their independent Tab and Panel context; returning to Terminal restores the existing standalone context. When an active Workspace's Project is collapsed, that Project row becomes the visible selected projection; expanding it returns the selected surface to the Workspace row.

Right-clicking blank tab-strip space exposes a localized orientation action. The Workbench switches the strip and content layout between a top horizontal strip and a left vertical strip while tabs, groups, and the new-tab control keep their existing context menus.

When the displayed terminal context has no Tabs, Workbench renders a blank content region without a centered creation control. The Tab Strip new-tab control, shortcut, menus, and Action remain available. Workbench never interprets an empty context as terminal-creation intent, so closing the last Tab does not recreate one; application startup policy remains owned by the composing application.

The shell composes primitives from `@orchbee/ui` without owning PTY processes, filesystem or Git effects, settings destinations, authentication, routing, or agent orchestration lifecycles. Workbench owns the unified search state and presentation, while semantic owners remain responsible for searchable read models and Action registrations. The machine-readable scope contract lives in [`project.json`](project.json).

Workbench composition is explicitly `preview` or `managed`. Both receive an application-owned terminal-presentation identity allocator and one stable initial presentation ID. A managed composition additionally receives operation/removal ID allocators and a narrow command dispatcher; Workbench never allocates a Host terminal ID or uses one for topology or lifecycle mutation. The terminal-surface seam exposes an opaque Host terminal identity only to the bell-effect coordinator described below. Dynamic presentation IDs are opaque and must not be reused after a presentation is removed.

A managed application may seed the standalone context with recovered presentations. Each seed retains its application-owned PresentationId and launch CWD and is projected as one Tab; Workbench still does not infer or persist Project, Workspace, group, split, process, or Host identity. The runtime routes every provision, exit, and close result by PresentationId across all terminal contexts and rejects missing, duplicate, or stale targets without mutating another presentation.

Applications may inject a `terminalSurface` component. Workbench mounts it only for terminal presentations in the displayed Tab and visible Panel layout, passing the presentation model plus the viewport's application-owned Action runtime/scope, a narrow semantic-context registration seam, a bell-effect admission function, and an `autoFocus` projection, never a Host capability. Inactive Tabs, other Workspaces, background Projects, and inactive child terminals do not mount the surface. Workbench sets `autoFocus` only on the displayed terminal in the active Tab's remembered focused Panel. The injected surface claims its real terminal input when that projection becomes true, when a true target mounts, or when its recovered renderer becomes ready. A new Tab therefore focuses its first Panel terminal, returning to a Tab focuses that Tab's remembered Panel terminal, and splitting focuses the new Panel terminal. Closing the focused Panel selects the most recently focused surviving Panel; only an empty surviving history falls back to the previous visual leaf and then the next. Closing a non-focused Panel preserves and restores the focused terminal. Right-click retains the element that was focused before the menu opened and restores it when the menu closes, unless a selected structural command transfers focus to another terminal. This lets Desktop bind attachment and renderer lifetime to actual viewport demand while preserving Workbench ownership of logical topology and product focus.

One mounted Workbench panel-workspace lifetime owns one `WorkbenchTerminalBellEffectCoordinator`.
Every surface reports only an opaque terminal identity and positive Host bell sequence. The
coordinator retains mergeable sequence intervals per terminal, so duplicate, stale, reconnected,
and replayed attachment deliveries are rejected without losing a distinct sequence that arrives
out of order. Exactly the first admitted delivery may create the visual product effect and invoke
application capabilities. Workbench performs no audio or operating-system notification itself;
those remain two independent, default-absent application capabilities.

The stable headed `terminal-parity/PR-11-bell` witness composes multiple production terminal
surfaces with one Workbench coordinator and proves duplicate/reconnect suppression, interleaved
sequence admission, and independent optional-effect failures. The stable headed
`terminal-parity/IN-09-action-scope`, `terminal-parity/IN-11-context`, and
`terminal-parity/IN-12-actions` witnesses compose the minimal catalog in its containing Workbench
scope and prove native handling for unclaimed or unavailable Apple Command chords, pinned semantic
context with execution-time revalidation, synchronous availability, typed results, no added
confirmation, and localized feedback. These controlled Canvas fixtures capture application effects;
they do not claim native audio, operating-system notification, clipboard, or URL-handler delivery,
and they do not make Workbench a terminal-state authority.

Applications whose address is the authoritative Client View input may inject a `WorkbenchNavigationPort`. Workspace, standalone-context, and Tab-selection Actions then delegate navigation before Workbench mutates active Client View state; the application updates browser history and applies the resulting route back to the runtime. Without this port, Workbench retains its local in-memory navigation behavior. Workbench does not parse paths or own Router history.

Terminal-presentation identities, lifecycle contracts, and boundary schemas come from `@orchbee/workbench-client-protocol`. `@orchbee/workbench/terminal-presentation` exposes only runtime-theme revision coordination, without the React Workbench graph.

## Keyboard focus routing

Workbench owns semantic focus routing among its ordinary product regions. `Mod+F6` and
`Mod+Shift+F6` invoke configurable next- and previous-region Actions; direct Actions focus the
active terminal, Tab Strip, or visible sidebar. The ring contains only currently available regions
in this order: active terminal, Tab Strip, visible sidebar. A hidden sidebar and a missing terminal
are skipped. Temporary dialogs, menus, search, Settings, and other exclusive keyboard surfaces are
not members of the ring and retain their narrower focus scopes.

The Tab Strip is one composite focus stop. Its remembered roving item is the active Tab on first
entry and the last still-live keyboard-focused item on re-entry. A collapsed group header is the
visible representative for its hidden active Tab; hidden group children never receive focus.
Orientation-relative arrows wrap at the boundaries and move focus without activating; Home and End move to the first and last
visible item; Enter and Space activate a focused Tab or toggle a focused group; and Shift+F10 or the
Menu key opens the exact focused item's context menu. The new-Tab button follows the composite in
sequential focus order. Closing, grouping, collapsing, or moving the focused item preserves focus
on the same visible identity when possible and otherwise chooses the nearest visible item, then the
active Tab or its collapsed-group representative, then the new-Tab button.

On a new positive sidebar focus request, focus the visible current location, then the visible
active Project representing a collapsed Workspace, then the standalone Terminal fallback. Focusing
never activates a location or expands a Project. Only the existing Project scroll region may move:
measure its content viewport using `clientTop` and `clientHeight`, and clamp the nearest-edge
vertical adjustment to its scroll range. Fully visible rows and oversized rows already spanning
the viewport do not move; other oversized rows align their nearer edge. Zero-height geometry does not scroll. The standalone Terminal is a list destination and follows
the same contained reveal rules. Repeated request tokens and later data changes alone do nothing.
The existing sidebar focus Hook tests cover these decisions; navigation Stories provide the
controlled browser fixtures for visible focus, unchanged navigation, and unchanged outer scrolling.

### Focus routing modeling record

- **Problem and scope:** A keyboard-oriented person whose real PTY input owns focus needs a bounded way to leave the terminal, operate the Tab Strip or sidebar, and return to the exact active terminal without a pointer. A person who pointer-clicks either the sidebar Terminal entry or a Workspace row expects the destination terminal input to receive focus after navigation. This change includes five public Workbench focus Actions, the two configurable region-cycle bindings, pointer-click terminal-location activation, Tab Strip roving focus and keyboard context-menu entry, a terminal-surface focus-request projection, localization, Browser binding persistence, and controlled Browser/Desktop evidence. Keyboard activation of Terminal or Workspace buttons, shortcut and programmatic location changes, sidebar tree disclosure, keyboard reordering, shortcut-rules v2, Settings deep links, screen-reader parity, and the manual-only native-window focus test do not request focus through the pointer-click workflow.
- **Inputs and data:** Trusted inputs are the mounted Workbench region registry, visible-sidebar state, active location, exact destination location, active Tab and displayed-terminal identity, Tab Strip orientation and visible item order, a monotonically increasing terminal focus-request token, normalized semantic keyboard commands, a normalized pointer-versus-non-pointer terminal-location activation origin, the matching activation Action result, and the current terminal projection. DOM focus and click events are untrusted presentation inputs and may update focus intent only after the target and pointer origin are validated. `WorkbenchFocusRegion` is `terminal`, `tab-strip`, or `sidebar`; `WorkbenchFocusState` owns the current ordinary region plus the last live Tab Strip item. `WorkbenchTerminalLocationActivationState` owns at most one initiating-client pointer intent and its exact target location while `TabModel` and Project/Workspace state remain authoritative for active Tab and location identity.
- **Model and transitions:** `resolveWorkbenchFocusTarget` is a synchronous pure resolver over direction, current region, and available registered regions. Next follows terminal → Tab Strip → sidebar → terminal; previous is the inverse; both skip unavailable regions and reject a cycle with no different target. Direct focus resolves exactly one requested region. Unknown or stale current focus anchors either direction at the active terminal when available, then the Tab Strip, then the sidebar. `transitionWorkbenchTerminalLocationActivation` starts a request only for normalized pointer activation, accepts reordered Action settlement and exact destination-terminal projection observations, emits one focus command only after both are ready, replaces an older pointer intent with the latest click, and cancels on failure, disposal, a non-pointer activation, or a different non-target location. Tab Strip roving is manual activation across visible Tabs and group headers: orientation-relative arrows wrap and Home/End change only its remembered focus item; Enter or Space delegates a Tab to `tabs.tab.select` or toggles a group; context-menu keys delegate the exact focused item; structural changes reconcile the remembered item by same visible identity, the collapsed-group representative for a hidden active Tab, nearest visible neighbor, active Tab, then new-Tab control.
- **Outputs, failures, and no-ops:** A successful region resolution emits one typed focus request for one registered target and consumes its shortcut. A pointer terminal-location activation invokes the existing standalone or Workspace-location Action and emits one terminal focus request only after that invocation completes or is unchanged and the exact destination's active Presentation is available. Terminal focus increments the request token; the injected terminal surface retains a newer request for the exact active presentation and fulfills it after that presentation is mounted and ready. Keyboard Button activation, shortcuts, Workspace creation activation, and programmatic location changes perform their existing operation without this focus request. Missing, hidden, stale, disabled, failed, cancelled, superseded, exclusive-surface, or absent targets emit no click-owned focus command. A present but not-yet-ready terminal remains pending; repeating a direct focus on the already focused target is an intentional unchanged result and does not fabricate another region transition.
- **Invariants and ownership:** At most one ordinary Workbench region owns semantic focus. Pointer-click focus never precedes successful exact-location activation or the exact destination terminal projection, never targets a different terminal from the destination active Tab's remembered focused Panel, and is emitted at most once for the latest live click. Non-pointer activation never creates pointer focus intent, and stale Action completion cannot revive a replaced or disposed intent. Exactly one visible Tab Strip Tab or group header has `tabIndex=0`; every other composite item has `-1`; hidden collapsed-group children never receive focus; Tab focus alone never changes active Tab identity; activation uses the existing location or Tab Action; and terminal `autoFocus` cannot steal focus while the Tab Strip owns keyboard focus. Workbench owns activation-origin normalization, target-location validation, region selection, request sequencing, and the terminal target; `@orchbee/tab-strip` owns its composite focus projection; Project/Workspace state and `TabModel` own location and Tab selection/order; the injected terminal-surface adapter owns the real input-focus call but cannot retarget it; Web owns effective bindings and durable overrides.
- **Compatibility, delivery, and rollback:** The accepted defaults are `Mod+F6` and `Mod+Shift+F6`, preserving unmodified function keys for PTY/TUI input. Browser overrides migrate from v20 to v21 by copying every valid prior override, dropping entries equal to current defaults, and rejecting post-migration conflicts; the v20 record remains untouched for rollback and older builds intentionally cannot read v21-only edits. Delivery is ordered as this contract, the terminal-location pointer-activation state model, pure resolver and reconciliation tests, Tab Strip semantics, Workbench/terminal-surface integration, then Web persistence and controlled system evidence. Removing Workspace rows from the pointer-origin adapter restores their previous focus-neutral behavior independently; reverting the v21 catalog and migration, focus Actions/state, Tab Strip projection, terminal-location state model, and terminal focus-request field together restores the earlier keyboard behavior without durable-data deletion.
- **Verification and limits:** Deterministic resolver tests cover both directions, hidden/missing regions, unknown and stale focus, singleton rejection, direct focus, repeat no-op, and exclusive-surface fallthrough. The terminal-location pointer-activation model and Hook tests cover standalone and Workspace targets, result-before-projection, projection-before-result, unavailable destination, failure, supersession, non-pointer activation, disposal, and exactly-once focus. Tab Strip component tests enter through the sole natural Tab stop and cover both orientations, Home/End, manual activation, context-menu keys, new-Tab order, removal/group collapse reconciliation, and focus retention. Workbench tests cover pointer-click focus after routed standalone and Workspace publication, focus-neutral keyboard activation, Action availability, shortcut consumption only after a resolved target, focus restoration, and suppression of terminal auto-focus while the Tab Strip owns focus. Web migration/catalog/localization tests cover v20→v21 preservation, conflicts, settings projection, and rollback. Controlled Browser and Desktop real-PTY traces exercise terminal → Tab Strip → menu → terminal and reverse routing, plus pointer Workspace navigation into its exact terminal input; the native-window focus-stealing system test remains explicitly excluded unless separately authorized.

The pure Project, Directory, Workspace, placement, CWD, and transition contracts are available from
`@orchbee/workbench/project-workspace`. Application owners may use this non-React subpath for one
authoritative mutation without importing the visual Workbench or its runtime graph.

The headless `WorkbenchProjectWorkspaceRuntime` and its `WorkbenchTerminalPresentationComposition`
type are available from `@orchbee/workbench/runtime`. Its runtime import closure contains no
React, DOM, or stylesheet module and takes Tab state from `@orchbee/tab-strip/model`, so Electron
Main can own a runtime without importing the React Workbench root. Its declarations still reference
the Tab Strip root's `TabStripNewTabRequest` type.

Exact-target terminal-intent creation lives in the internal `semantic-commands` subsystem, which
has no package subpath. The Workbench terminal creation Action passes a local route to
`executeWorkbenchTerminalCreate`, which delegates one terminal creation to the existing Workbench
runtime. Creation preserves active Client View selection when one exists; an empty target uses the
sole created Tab as the Tab model's required validity fallback. A product Action may separately
select only the exact returned Tab. The composing application supplies the committed revision and
remains responsible for durable commitment and process reconciliation.

## Project and Workspace

The maintained in-memory model, ownership, fallback, CWD, duplication, and correctness contract lives in [`docs/project-workspace.md`](docs/project-workspace.md).

`WorkbenchProjectWorkspaceRuntime` owns standalone terminals and independent Workspaces with stable Tab/Panel contexts. Workspace menus move to an existing or new Project, or ungroup atomically. Dissolve Project retains its Workspaces; Close All Workspaces is a separate explicit action; ordinary close affects only one Workspace. Async Worktree creation/adoption uses current source membership, preserves known Git results, reopens associated Workspaces and lets only the latest live initiating navigation intent select the result. Preview duplication uses fresh terminal identities; managed process cloning remains unavailable.

The package accepts host-normalized Directory descriptors and browser-entered paths and performs no filesystem, Git, PTY, or persistence effect itself. Desktop owns native existing-Folder selection, validation and bounded creation of one absent child through the [Folder acquisition contract](../../apps/desktop/docs/project-folder-acquisition.md). Ongoing Directory observation and Git effects remain outside this capability.

## Unified search

The maintained behavior, ownership, transition, and correctness model lives in [`docs/unified-search.md`](docs/unified-search.md).

The sidebar Search control and the platform All-search binding—`Mod+Shift+F` on Apple and `Mod+Shift+K` on Standard—open one upper-viewport modal with the `All` filter and an empty query. `Mod+Shift+P` opens the same surface with the `Actions` filter. Each global open starts a new in-memory session; switching among `All`, `Agents`, `Actions`, and `Settings` preserves the current query, while closing discards the session. File search is intentionally absent.

The current local provider projects Actions by requesting subtree discovery from the mounted application `ActionRuntime`. It keeps every runtime-owned prepared or unbound invocation intact, groups results by localized Action category, explains disabled capabilities, displays the composing application's current shortcut label for Workbench and descendant terminal Actions, and invokes a selected ready result through `executePrepared(...)`. The tab-strip-orientation Action demonstrates nested input: selecting the command opens an in-surface horizontal/vertical picker, binds the selected value through `prepareInvocation(...)`, and then executes that same scope-bound token. The Settings provider projects the stable root Settings destination through `workbench.settings.open`.

`All` shows curated recommended Actions plus Settings before a query, then searches the complete local catalog after typing. Matching normalizes Unicode, case, and repeated whitespace and ranks exact localized titles, title prefixes, title-token prefixes, localized keywords, canonical English titles, and fuzzy subsequences in deterministic tiers. The `Agents` filter is present as the accepted navigation slot but remains empty because no Agent-owned searchable read model is composed; the Workspace overview's exact navigation Action requires an internal Session row input and is deliberately not a searchable catalog item. The provider coordinator accepts bounded synchronous or asynchronous providers and rejects stale completions. File search, Agent fallback, persistent MRU, and user-editable keybindings remain outside the current implementation.

The dialog keeps DOM focus in its combobox. Up and Down move `aria-activedescendant` through inspectable results, Enter opens or runs the highlighted row, Escape returns from a nested picker or closes the surface, and pointer movement updates the same visual highlight. Input, filters, and footer remain fixed while grouped results scroll. Closing occurs before a selected Action begins; it does not cancel or assume ownership of that Action's asynchronous lifecycle.

### Search modeling record

- **Problem and inputs:** A person needs to discover and invoke product capabilities without knowing a menu location or shortcut. Trusted inputs are a reviewed open filter, the mounted Action scope, localized Action descriptors, and pointer or keyboard events. Query text is local user input. Missing Action input remains an unbound runtime token and is never guessed.
- **Data and ownership:** `WorkbenchSearchState` is the sole owner of the open session, filter, query revision, query, highlight, and nested parent snapshot. Semantic owners remain authoritative for Action availability and effects. Projected results carry stable provider, group, result, Action, and scope identity plus a runtime-owned prepared or unbound invocation.
- **Outputs:** Opening renders and focuses one modal session; filter and query changes produce a deterministic local projection; a disabled selection announces its reason without invoking; an unbound supported result enters a nested picker; a final enabled selection reaches at most one Action execution. Escape and outside dismissal commit no Action.
- **Transitions:** Open resets to the requested preset. Query changes increment the revision. Filter changes retain query text. Result changes retain a still-visible highlight and otherwise select the first enabled result, falling back to the first inspectable row. Nested Back restores the complete parent filter, query, revision, and highlight snapshot. Close retains only the next monotonic session identity.
- **Invariants:** A rendered highlight always names one current visible row; hidden Actions never render; disabled or unsupported unbound rows never execute; prepared input is bound only through the originating runtime token; one accepted row reaches at most one `executePrepared(...)` call; and closing or nested cancellation performs no domain mutation.
- **Dependencies and exclusions:** React owns the mounted dialog lifecycle and focus adapter; `@orchbee/actions` owns registration, discovery, preparation, availability, confirmation, and execution; `@orchbee/i18n` owns product copy; and design tokens own geometry and appearance. Network, storage, telemetry, process state, Agent data, and async provider coordination are excluded until their semantic owners expose the required contracts.
- **Verification:** Pure tests cover open/close, query and filter transitions, highlight movement, nested restoration, matching tiers, deterministic grouping, Settings de-duplication, and argument filtering. Runtime projection tests cover prepared and unbound results. Component tests cover combobox focus, Actions filtering, nested orientation input, Action execution, and close. Storybook supplies open All and Chinese Actions states; browser verification exercises both shortcuts, four filters, keyboard and pointer selection, nested input, dismissal, and both tab-strip orientations.

## Panel workspace

Panel separators use axis-specific local CSS cursors while the resize primitive's document-global cursor injection remains disabled. Crossing a separator may change the cursor only while that separator is the pointer target, so leaving the target, cancelling a pointer, or losing capture cannot strand a resize cursor over unrelated terminal content.

The product terminal context menu captures the exact focused element before opening. Closing it after a non-structural command, including Clear, returns focus to that element; a successful split suppresses restoration so the new Panel's terminal auto-focus transfer wins.

Each terminal tab owns an in-memory panel workspace below its tab strip. A new tab starts with one full-size panel and one special primary terminal. The single-panel primary view omits panel chrome. When the terminal application does not own mouse input, right-clicking the terminal viewport exposes a product-curated terminal set—Open Link when applicable, Copy, Paste, Select All, Find, Show Last Command Output, Show Scrollback, and Clear—before a deliberate structural set: New Tab, New Tab in Current Directory, New Child Terminal, panel maximization, a four-direction Split submenu, and Close Terminal. Find Next, Find Previous, Scroll to Bottom, and Reset remain discoverable in Action search without lengthening the frequent pointer menu. A link Action appears only when the surface captures an exact link target at menu-open time. Commands render a trailing shortcut only when the composing application supplies a current effective binding. Menu close and current-directory creation carry the clicked panel as an explicit Action target; keyboard variants use the active Tab's focused panel. Each revalidates through its contextual Action. A child terminal occupies the same viewport as its primary terminal; child terminals appear in a real `40px` bottom strip, while the primary terminal never appears in that strip. Activating a child adds a `32px` header with a return action, geometrically centered terminal title, and close action.

A composing application may inject the narrow `AgentSnapshotSource` owned by `@orchbee/agent`. Workbench subscribes without copying or mutating canonical Agent state, resolves each exact `TerminalPresentationId`, and places a curated provider identity plus localized semantic status in the panel header's leading region. It deduplicates Sessions attached to several panes and aggregates every presentation in a Tab into a stable identity icon plus one non-ended `TabStatusAdornment`. The Project sidebar separately projects live Sessions across every Workspace terminal context without mounting inactive surfaces. A Workspace with live Sessions replaces its layout mark with one provider mark, two fixed-order marks overlapped by one quarter, or the provider-neutral Agent mark for three or more providers; the adjacent number always counts deduplicated live Sessions rather than provider types. Its independent disclosure is closed by default, only one may be open, and the detail contains flat Agent rows rather than a second Tab or terminal tree. Each row shows curated provider and status text plus its Tab, Panel, and primary or child terminal location, and exact navigation revalidates the latest Session before selecting and focusing that destination. Retained ended state is excluded everywhere, restoring the ordinary Tab or Workspace identity immediately. The generic Tab Strip receives only host-owned React presentation and remains unaware of Agent providers. A non-ended Agent makes the panel header visible even in the otherwise chrome-free single-panel primary view; an empty source or ended-only projection preserves the existing panel layout. Freshness and semantic status are expressed by localized text or an accessible label plus a glyph, never by color alone. The centered terminal title remains independent. The complete sidebar contract is in [`docs/project-workspace.md`](docs/project-workspace.md).

An optional `WorkbenchAgentNotificationObserver` receives only exact attention, successful outcome, and failed outcome events after their canonical snapshot update. Workbench resolves all navigable attachments against the current Tab/Panel tree and marks an event visible only when an attached local Tab, split pane or selected child presentation and its inner mux pane are visible. Hidden events carry curated, localized, content-free notification copy and a navigation-only activation callback that selects the exact Tab and pane. The injected observer owns user preference, existing platform permission, deduplication, and the final system effect; Workbench never requests permission and does not turn a notification click into an Agent response or approval. Activity, Search results, provider events, Agent actions, and delivery while transport is disconnected remain outside this slice.

Once a tab has multiple panels, every panel displays the header. Its panel-options menu contains Maximize Panel or Minimize Panel and projects the same current binding as the viewport menu and Action search. Maximizing projects `100/0` layouts along the target's split ancestry and hides sibling branches while keeping the complete Panel React tree and every terminal surface mounted; minimizing restores the canonical weights without replacing terminal DOM identity. During either transition, every affected split withholds the focused terminal's `autoFocus` projection until its resizable primitive has synchronized the projected layout, then the same mounted terminal reclaims input focus and remeasures its surface before accepting further input. Splitting a maximized panel first restores the tree and then applies the split. Exactly one panel is focused; that panel retains the normal terminal surface while every other panel receives a non-interactive inactive mask. Primary-pointer or keyboard focus inside a panel transfers focus and the mask to that panel; secondary-pointer context intent alone does not. The active Tab projects its remembered focused Panel's displayed primary or child terminal as the sole terminal `autoFocus` target. Tab activation, initial Tab creation, child-terminal activation, Panel splitting, Panel movement, and focused-Panel closure therefore restore or transfer real terminal-input focus through the injected surface without coupling Workbench to the surface's DOM. Dragging a primary-terminal panel header lifts a scaled visual snapshot cloned from that panel's current DOM, removes the source from a reversible layout projection, and immediately reflows the remaining grid. The snapshot preserves current panel chrome and terminal presentation without mounting a second React terminal instance. A header showing an active child terminal is not draggable. Moving over another panel's directional edge projects the complete final grid with an empty framed panel at the destination. Dropping replaces that placeholder with the complete source panel and splits the target above, below, left, or right without replacing any terminal identity or state. The center of a target is intentionally inactive so a release without a directional placeholder cancels and restores the canonical grid. Contextual close resolves one target: the displayed child terminal, otherwise a primary panel when another panel survives, otherwise the active Tab. In preview composition, closing an active child affects only that child and returns to the primary terminal; closing a primary view affects the panel and all of its children. In managed composition, the same intent first marks every affected presentation as closing and emits one exact close command per presentation. Topology remains present until every close completes, but an accepted active-Tab close immediately selects the nearest later Tab not already pending close, then the nearest earlier one. Repeated keyboard closes therefore target distinct Tabs without waiting for Host disposal. A localized confirmation is required for preview, restoring, or reconciling presentations and for a provisioning or `running` presentation whose transient close activity is `active` or `unknown`. A provisioning or `running` presentation classified as `idle` closes directly. Panel closure counts the primary and child presentations it affects. Tab closure traverses every panel in every requested tab and counts all primary and child presentations before the Tab Strip action can commit. Application lifetime aggregates that same predicate across every context and tab; it does not infer protection from the broader non-stopped session count. The confirmation count includes only affected presentations that require protection. A partial failure retains the failed presentation and already-closed siblings for explicit retry, without rollback. The last panel in a tab is not closable through the panel lifecycle because the tab lifecycle owns that case.

An active-Tab identity change cancels any presenter-owned Panel drag before paint and restores the source Tab's canonical layout, so a source preview cannot leak into the newly active Tab.

The active Tab can open a dedicated live broadcast input bar through Actions search or either Panel menu when every displayed terminal is running and write-ready. It captures every canonical Panel's displayed Presentation as one immutable target set, keeps the targets visible behind pointer shields, owns exclusive keyboard focus, and stops before later input when that snapshot becomes stale. Text and physical key taps are delivered in FIFO order through each injected terminal surface; multi-PTY fan-out is explicitly non-atomic, and a partial failure stops without retry or rollback. Paste, file drop, hidden Presentations, maximized layouts, other Tabs or Windows, and remote control are excluded. The maintained behavior, ownership, transition and correctness contract lives in the [Panel broadcast input record](docs/panel-broadcast-input.md).

A managed terminal's identity-checked natural exit is an unconfirmed terminal-level removal intent. An exiting child removes only that child and, when displayed, returns the Panel to its primary terminal. An exiting primary with children closes only the exited presentation; after Host disposal completes, the active child is promoted to primary, or the first child when none is active, without stopping any surviving child. - **Decisions, compatibility, and recovery:** Both platforms default to physical `Ctrl+Shift+]` for next and `Ctrl+Shift+[` for previous, avoiding Apple `Shift+Command+[` and `Shift+Command+]` Tab-selection bindings. The commands wrap in canonical leaf order but remain unavailable while maximized, matching Orchbee's existing directional-focus gate instead of changing a hidden Panel. Web expands its strict shortcut catalog from `v17` to `v18`; valid nonconflicting `v17` overrides migrate, remain as a rollback snapshot, and a collision with either new default follows the existing whole-record invalidation and warning policy. Settings supports rebind and reset, not an unbound state. No layout or shared-document migration, feature flag, or process recovery is required; reverting the integrated change restores the prior catalog and lets the preserved `v17` record resume authority.
- **Verification:** Deterministic resolver tests cover nested order, both wrap boundaries, inverse direction, singleton, and stale source; generated valid trees check live membership and inverse behavior. Action tests cover availability, exact descendant delegation, execution-time revalidation, maximization, and fallthrough. Shortcut, catalog, Settings, localization, and `v17` migration tests cover both platforms, exact modifiers, custom bindings, conflict recovery, and rollback retention. Existing Panel focus integration verifies MRU and terminal-input continuity; full repository verification supplies the integration gate. The resolver is synchronous and introduces no new state or independently ordered result, so TLA+ is not selected.

### Panel equalization modeling record

- **Problem and scope:** After repeated same-axis splitting or manual resizing, a person needs one discoverable command to redistribute the active Tab's Panels into equal shares along every split axis. Trusted inputs are the active Tab identity, one exact live Panel target, the canonical `PanelLayoutNode` tree, and an Action invocation source. The change includes one whole-Tab Action, Panel menus, Action search, Apple and Standard shortcuts, shortcut settings, and persisted-override migration. Automatic equalization after close, separator double-click, changing keyboard resize mode's `R` reset, cross-Tab equalization, and process or terminal-content changes are excluded.
- **Model and transition:** `resolvePanelEqualization` recursively computes an axis-unit count for each child: a Panel is one unit, a same-orientation split contributes the sum of its descendants' units, and a perpendicular split contributes one unit on the current axis. Each split receives child weights proportional to those units and recursively equalizes its children. `panels-equalized` revalidates the exact Tab and Panel, rejects maximized, singleton, or stale targets, commits one complete root when weights differ, and otherwise returns an intentional unchanged result. The operation is synchronous and has no cancellation, rollback, command, process, DOM-measurement, storage, time, random, or network phase.
- **Invariants:** Equalization preserves every Panel, terminal presentation, split, and slot identity; child order, split orientation, topology, membership, counters, focus history, focused Panel, and maximization state do not change. Every child weight remains finite and non-negative, every split totals `100` within the existing tolerance, every same-axis leaf unit receives the same normalized extent, and applying equalization twice is idempotent with structural identity retained on the second application. A perpendicular subtree occupies one unit on its parent's axis and is independently equalized on its own axis.
- **Decisions and ownership:** Workbench remains the only canonical layout writer. `workbench.panel.active.equalize` resolves the active target and lowers to the exact `workbench.panel.equalize` Action used by menus and Action search; shortcut and menu adapters never write weights. The Action is available only for a live multi-Panel Tab that is not maximized. An already equal layout consumes an available invocation and reports unchanged, while singleton, maximized, and stale invocations remain unavailable and keyboard routing falls through. Apple defaults to `Control+Command+=` and Standard defaults to `Ctrl+Alt+=`; `Ctrl+Shift+E` remains the Standard Split Below binding. Browser shortcut overrides move from `v15` to `v16`; valid `v15` customizations migrate unless one conflicts with the new default chord. Keyboard resize mode's `R` continues to reset every binary split to equal child weights, which is intentionally distinct from proportional Panel equalization.
- **Verification:** Deterministic examples cover same-axis, mixed-axis, post-removal, singleton, and idempotency cases; fixed-seed generated trees check proportional weights, identity, membership, topology, and repeat stability; stateful and bounded reducer exploration includes the semantic event; Action tests cover exact-target revalidation and unchanged results; menu, shortcut, localization, `v15` migration, and settings tests cover every invocation projection. Headed Desktop trace `FS-14` checks three-column geometry, menu and Action-search discovery, shortcut prevention only while available, terminal identity, and input-focus continuity. TLA+ is not selected because the operation is one synchronous single-owner transition with no independently ordered completion.

### Current-directory Tab creation modeling record

- **Problem and scope:** A person working below a Workspace root needs a discoverable way to open another Tab at the directory reported by the terminal they are actually viewing. The feature includes `workbench.terminal.create-current-directory`, Action search, the terminal context menu, one configurable Apple and Standard shortcut, localized Settings projection, and persisted-override migration. Ordinary New Tab behavior, splits and child terminals, environment cloning, foreground-process cloning, SSH state, and remote-shell directory discovery are unchanged.
- **Target and transition:** Availability resolves the active terminal context and active Tab, then an explicit invoked Panel or the Tab's focused Panel. It captures that displayed primary or child presentation together with `terminalContextId`, `tabId`, `panelId`, and `presentationId`; the launch directory is the latest non-empty trusted `currentCwd`, falling back to that presentation's `launchCwd`. Creation synchronously revalidates every identity and resolves the latest CWD from that same presentation before preparing the new Tab. A missing Tab, Panel, CWD, Host capability, or changed identity is unavailable and creates nothing; ordinary creation continues to resolve the Workspace or standalone default.
- **Invariants and ownership:** Workbench remains the only Tab and terminal-presentation writer, while the Host remains authoritative for observed CWD and process launch. The menu and shortcut never copy environment, executable, command, output, attachment, or lifecycle state. Successful creation allocates a distinct Tab, Panel, and Presentation, focuses that terminal through the existing handoff, and preserves the source terminal identity and session. Captured CWD is transient Action input and never enters the shared document or browser storage.
- **Decisions and compatibility:** Apple defaults to `Option+Command+Enter` and Standard defaults to `Ctrl+Alt+Enter`; the existing ordinary New Tab bindings remain `Command+T` and `Ctrl+Shift+T`. Browser shortcut overrides migrate from `v16` to `v17`; valid prior customizations migrate unless they conflict with the added chord. Rollback leaves the `v16` record intact, and an older build intentionally cannot read edits made only in `v17`.
- **Verification:** Pure resolver tests cover displayed-child precedence, fallback, missing data, exact revalidation, and newer same-terminal metadata; runtime, Action, menu, shortcut, localization, Settings, and `v16` migration tests cover projections. Headed Desktop trace `FS-15` verifies OSC 7 delivery, menu and Action-search discovery, shortcut consumption, real-PTY `pwd`, source terminal continuity, focus, and Settings. TLA+ is not selected because capture and creation are one synchronous revalidated operation with no independently ordered completion.

### Tab presentation handoff modeling record

- **Problem and non-goals:** Switching a populated Tab or Workspace, or discretely replacing one Tab's Panel layout through split, close, move, swap, maximize, restore, or displayed-child selection, can expose a new container around a canvas that still represents the prior geometry. The handoff preserves one continuous meaningful presentation until the target geometry has actually painted, without keeping inactive Tab trees, attachments, canvases, or renderers resident. Continuous window or separator resizing, animation or cross-fade, operating-system compositor guarantees, persistent output storage, a second VT authority, synchronous WebGPU pixel readback, and a guarantee that a never-presented target already has current pixels are excluded.
- **Inputs and data:** Trusted inputs are the active presentation scope and `TabModel` identity, a deterministic layout revision, the visually contributing displayed-terminal identities, monotonic handoff epochs, and display-ready or activation-ready reports carrying the exact epoch, target Tab identity, and presentation identity. The layout revision includes the presentation scope, Tab, Panel and split identities, topology and child order, split orientation, maximized Panel, child-terminal membership, and displayed-terminal selection; it excludes focus, terminal metadata and lifecycle fields, ordinary positive weights, and drag previews. A maximized workspace requires only that exact Panel's displayed terminal; a normal workspace recursively excludes zero-weight branches. `TerminalTabPresentationHandoffState` owns one settled displayed revision, one preparation with an outgoing revision, or one target-only activation barrier. The React integration retains at most one read-only outgoing workspace snapshot keyed by its layout revision, including after canonical Tab removal or same-Tab replacement. Reports with an old epoch, wrong target Tab, or duplicate identity are no-ops.
- **Outputs and commit:** A settled state renders one interactive revision. Preparation renders the frozen outgoing revision above one inert incoming revision and projects no terminal `autoFocus`. An incoming terminal is not mounted until every ancestor Panel group reports its target maximization layout settled. Display readiness means that meaningful cached or live pixels, stopped content, or honest failure content fills the target and, for a canvas presentation, the painted Host frame's columns, rows, physical cell dimensions, and current surface measurement agree. After every required target reports display readiness, the target becomes the sole visible but still inert layer. Only a geometry-matching live frame, stopped presentation, or terminal failure contributes activation readiness; after every required target reaches that barrier, Workbench makes the target interactive and restores the sole `autoFocus` projection. A target with no required injected terminal surfaces commits immediately.
- **Transitions and cancellation:** A different Tab, Workspace scope, or layout revision starts a new epoch, freezes the currently presented terminal surfaces, and prepares the newest target even when the Tab identity is unchanged. A second change supersedes the prior target, keeps the last committed outgoing revision, and rejects every late report from the old epoch or target. Returning to that outgoing revision reuses and resumes its frozen layer through the same barriers instead of duplicating it or granting input early. A change that does not alter the layout revision updates the settled snapshot without a handoff. A managed close freezes the painted active surface and retires interaction ownership before canonical topology changes. Removing the outgoing Tab from canonical topology detaches but does not clear its transient presentation layer; closing the final Tab has no surviving target and clears the presentation normally.
- **Invariants:** A transparent, empty, or stale-geometry incoming canvas is never the top committed layer while an outgoing layer exists; preparation and activation barriers are inert; activation readiness implies geometry-safe display readiness; only exact current-epoch and current-target reports contribute readiness; required identities are unique; hidden maximized siblings and zero-weight branches cannot block a commit; at most the outgoing and newest target revisions are mounted; same-revision return uses one layer; a detached outgoing projection is read-only and cannot publish Action intent; outgoing attachments and input ownership retire before frozen pixels are used; and a display snapshot never supplies attachment identity, input authority, resize ownership, transport commands, frame acknowledgement, metadata publication, or durable Workbench state.
- **Terminal and application dependencies:** Workbench owns layout-revision projection, handoff state, layer stacking, and interaction admission. `@orchbee/terminal` owns immutable display-only packed snapshots, exact comparison between its most recently painted metadata and current measured surface geometry, and one reference-counted document-scoped WebGPU device/pipeline runtime. The Web adapter resolves display and activation readiness only from geometry-current canvas frames or non-canvas terminal outcomes, owns a `32 MiB` byte-accounted least-recently-used snapshot cache, and never invents PTY geometry. Terminal Host remains authoritative for VT state, PTY sizing, frame geometry, and content.
- **Memory, failure, and recovery:** Inactive Tabs retain neither React terminal DOM nor GPU surfaces. During a handoff, one frozen outgoing renderer and the newest target may coexist; supersession disposes the abandoned target. The bounded cache retains packed presentation data only. Cache rejection, eviction, unavailable WebGPU, attachment failure, snapshot absence, or a frame whose geometry is obsolete keeps the outgoing barrier until a geometry-current frame or honest failure is available. Shared-device loss follows the existing typed recovery path; Canvas 2D remains the fallback.
- **Decisions and alternatives:** Keeping all Tab surfaces mounted was rejected because it retains attachment, DOM, atlas, and GPU cost per inactive terminal. Predictively resizing or scaling the old canvas was rejected because it creates a second layout authority or visibly distorts text before Host reflow. Capturing a raster at activation was rejected because synchronous `drawImage` or readback can stall interaction and scales with viewport area. Painting only a background still presents lost content. The selected layout-revision transaction reuses the existing semantic snapshot and freeze/resume boundaries while requiring proof of target geometry before the atomic layer swap.
- **Correctness and verification:** Pure revision examples cover same-Tab topology, ordering, maximization and displayed-child changes; exclude focus, metadata, ordinary weights and drag previews; and separate Workspace scopes. Pure transition examples cover same-Tab revision replacement, cross-Tab and cross-scope switching, geometry-safe display and activation readiness, duplicate, stale and wrong-target reports, supersession from either barrier, return to the frozen revision, no-surface targets, and outgoing removal. The deterministic `projectTerminalTabPresentationLayers` tests own zero-layer clearing, the at-most-two mounted-layer bound, and same-revision keyed reuse. React integration covers same-Tab maximize/restore, layout-settlement gating, active-Tab closure, and Workspace-scope replacement; deterministic revision cases cover split, close, move, swap, and displayed-child replacement. Terminal and Web tests cover painted-versus-measured geometry mismatch, cached-snapshot matching, delayed live geometry, failure, and freeze/cache/resume ordering. Controlled Desktop traces sample every animation frame around the discrete transitions and reject a committed layer whose canvas grid differs from its current viewport; they exclude the manual native-window focus test, continuous resizing, other browser engines, operating-system compositor timing, and unbounded device-memory claims.
- **Rollback:** This change has no schema migration, storage rollout, or durable data. Reverting the layout-revision handoff and geometry-ready adapter restores the prior eventual-resize behavior; Canvas fallback and uncached live-first-frame recovery remain available throughout rollout.

## Use

Import the UI compatibility stylesheet once before the Workbench stylesheet at the application composition boundary:

```ts
import '@orchbee/ui/styles.css';
import '@orchbee/tab-strip/styles.css';
import '@orchbee/workbench/styles.css';
```

Render the shell at the same boundary:

```tsx
import {
	Workbench,
	type WorkbenchHostActionCallback,
	type WorkbenchLayoutStorage,
	type WorkbenchNavigationPort,
	WorkbenchProjectWorkspaceRuntime,
	type WorkbenchShortcutPlatform,
	type WorkbenchTerminalFontSizeChangeCallback,
	type WorkbenchTerminalSurface,
} from '@orchbee/workbench';
import { ActionRuntime } from '@orchbee/actions';

export function ProductInterface({
	actionRuntime,
	layoutStorage,
	navigation,
	onSettings,
	onTerminalFontSizeChange,
	projectWorkspaceRuntime,
	shortcutPlatform,
	terminalSurface,
}: {
	readonly actionRuntime: ActionRuntime;
	readonly layoutStorage: WorkbenchLayoutStorage;
	readonly navigation?: WorkbenchNavigationPort;
	readonly onSettings: WorkbenchHostActionCallback;
	readonly onTerminalFontSizeChange?: WorkbenchTerminalFontSizeChangeCallback;
	readonly projectWorkspaceRuntime: WorkbenchProjectWorkspaceRuntime;
	readonly shortcutPlatform: WorkbenchShortcutPlatform;
	readonly terminalSurface?: WorkbenchTerminalSurface;
}) {
	return (
		<Workbench
			actionRuntime={actionRuntime}
			layoutStorage={layoutStorage}
			navigation={navigation}
			onSettings={onSettings}
			onTerminalFontSizeChange={onTerminalFontSizeChange}
			projectWorkspaceRuntime={projectWorkspaceRuntime}
			shortcutPlatform={shortcutPlatform}
			terminalSurface={terminalSurface}
		/>
	);
}
```

Create one `ActionRuntime` and one `WorkbenchProjectWorkspaceRuntime` for each mounted application composition and dispose application-owned resources with that composition. Initialize the Project/Workspace runtime with the system CWD and localized first terminal title. Its in-memory terminal-creation Action preserves the requested Tab group and optional insertion index. Optional host callbacks such as Settings and application-wide terminal font-size changes still return a structured `ActionResult`, may return it asynchronously, observe `context.signal` before commit, and call `context.markCommitted()` immediately before their authoritative mutation.

When storage is provided, Workbench restores `orchbee:workbench:left-panel-width:v1`, `orchbee:workbench:left-panel-visibility:v1`, and `orchbee:workbench:tab-strip-orientation:v1`. It parses complete JSON records with feature-owned strict Zod schemas, saves width only after a completed user resize, and saves visibility or tab-strip orientation only after the corresponding semantic toggle action. Missing, malformed, unavailable, or out-of-range storage falls back to a visible `250px` sidebar and a horizontal tab strip without blocking rendering. The repository-wide ownership and key contract lives in [`docs/frontend/browser-storage.md`](../../docs/frontend/browser-storage.md).

Workbench owns the in-memory Tab and Panel context projection; the composing application remains authoritative for PTY and terminal-process lifecycle effects. A managed composition dispatches typed presentation commands and feeds their typed results back through `applyTerminalPresentationEvent(...)`. Tab close is delegated: Workbench marks every contained presentation closing, retains topology while results are pending, and removes the Tab from `TabModel` only after every exact close completes. A desktop host may pass `createCrossWindowDragRuntime` to connect the strip's pointer lifecycle to host-owned live-window discovery, compatibility checks, native window movement, capture, and move-loop behavior. Workbench and the browser application do not fabricate those operating-system capabilities.

Workbench exposes a runtime-theme revision coordination contract across Workbench, Terminal Host,
and the projected client. Workbench owns supersession and publication eligibility; the contract
keeps Host-owned terminal defaults/palette/cursor and client-owned pixels, overlays, cursor, and
application surface on one matching complete revision. Its model, retry rules, bounded evidence,
and Host/client refinement are maintained in
[`docs/terminal-theme-revision.md`](docs/terminal-theme-revision.md).
The Host compare-and-set, complete recovery state, projected-terminal frame staging, renderer
preflight, and application-wide synchronous publication barrier are implemented. A revision becomes
visible only after every mounted participant can commit the exact Host-tagged frame and complete
client snapshot.

### Shared document and Client View boundary

The canonical revisioned `WorkbenchSharedDocument` from `@orchbee/workbench-client-protocol` is separate from one page's disposable `WorkbenchClientView`, exported by `@orchbee/workbench/document`. Project, Workspace, Tab/Group membership, durable fallback and custom Tab titles, Panel/Split structure, terminal-presentation placement, and durable lifecycle intent are shared. Active and selected navigation, disclosure, focus, maximization, active child presentation, and Split weights are client-local. Per-Tab MRU Panel focus history exists only in the live Workbench runtime and initializes from the Client View's focused Panel; it is outside both serialized contracts. Natural terminal titles, current CWD, viewport demand, scroll, search, selection, copy, GPU state, and `AttachmentId` remain outside both contracts.

A managed `WorkbenchProjectWorkspaceRuntime` projects these contracts through `getSharedDocument(...)` and `getClientView()`, hydrates them through `initialDocument` and `initialClientView`, and can apply a broadcast document through `applySharedDocument(...)` without dispatching process effects. `subscribeDocument(...)` supplies the application durability coordinator; its shared fingerprint is unchanged by Client View-only transitions. After the application establishes its persistence barrier, `reconcileDurableTerminalPresentations()` replays persisted provision, close, and stop operations and converts retain intent into restore-only commands.

An application-lifetime owner can capture `getRestartableTerminalPresentationIds()` before sealing terminal creation, durably stop those exact sessions, and then call `stageStoppedTerminalSessionsForRestart(...)`. Restart staging replaces only the captured stopped presentations with fresh PresentationIds and provision operation identities while preserving their placement, title, and launch CWD. It updates the shared-document projection without dispatching provision commands into the retiring runtime; the next application runtime performs those effects through ordinary durable reconciliation. Already-stopped and closing presentations are not captured or restarted.

The package performs no storage or IPC effect. A composing application parses the contracts at its boundary and owns private storage, shared revisions, write ordering, recovery diagnostics, and eventual Terminal lifecycle effects. The canonical shared document and Client View both use version 1. Grouping and launch-resource namespaces are independent, and Client View selects by Workspace identity. These strict current contracts do not migrate historical document versions. Malformed documents and views are rejected. The maintained model, invariants, and evidence are defined in [`docs/shared-workbench-document.md`](docs/shared-workbench-document.md).

Workbench owns fifty-three stable shortcut declarations: Actions search, next- and previous-Workbench-region focus, ordinary New Tab, New Tab in Current Directory, application-wide terminal font-size increase/decrease/reset, nine positional Tab selections, previous- and next-Tab selection, active-Tab backward and forward movement, Set Tab Title, contextual Close Terminal, All search, Settings, sidebar toggle, panel maximization, proportional Panel equalization, keyboard Panel resize, split right, split below, directional, cyclic, positional, and visible Panel focus, visible Panel swap, and directional Panel movement. Current-directory creation defaults to `⌥⌘Enter` on Apple and `Ctrl+Alt+Enter` on Standard; it resolves the exact displayed terminal and falls through when no trusted CWD is available. Font size defaults are `⌘=`, `⌘-`, and `⌘0` on Apple and `Ctrl+=`, `Ctrl+-`, and `Ctrl+0` on Standard; the composing application owns the appearance mutation through one optional host callback. The positional defaults are `⌘1` through `⌘9` on Apple and `Ctrl+1` through `Ctrl+9` on Standard. Each resolves its one-based input against the active context's canonical `TabModel.tabs` order, including the pinned prefix and members of collapsed groups, then executes the prepared `tabs.tab.select` Action; a missing position falls through and position nine is never an alias for the last Tab. Previous and next selection follows that same canonical order, wraps across its boundaries only when at least two Tabs exist, and is unavailable for an empty, singleton, or missing-active-Tab snapshot. Apple adjacent defaults are `⇧⌘[` and `⇧⌘]`; Standard adjacent defaults are `Ctrl+PageUp` and `Ctrl+PageDown`. Active-Tab movement uses `Ctrl+Shift+,` and `Ctrl+Shift+.` defaults on both platforms, wraps inside the active Tab's pinned or unpinned partition, and delegates the authoritative mutation to the prepared `tabs.tab.move` Action. Set Tab Title defaults to `⇧⌘I` on Apple and `Ctrl+Alt+Shift+T` on Standard, opens the exact active or invoked Tab, and delegates durable title policy to Workbench. Keyboard Panel resize defaults to `⌘R` on Apple and `Ctrl+Shift+R` on Standard, opening the same exact-target modal used by menus and Action search. Panel equalization defaults to `⌃⌘=` on Apple and `Ctrl+Alt+=` on Standard and recursively redistributes the active Tab by same-axis Panel units without changing topology or focus. Apple directional focus defaults are `⌥⌘←/→/↑/↓`; Standard directional focus defaults are `Ctrl+Alt+←/→/↑/↓`. Cyclic focus uses explicit `Ctrl+Shift+]` and `Ctrl+Shift+[` on both platforms, follows canonical Panel-leaf order within the active Tab, and wraps only when multiple Panels exist. Positional Panel focus uses `Ctrl+Shift+1` through `Ctrl+Shift+9` and `Ctrl+Shift+0` on both platforms, maps `0` to semantic position ten in the active Tab's canonical depth-first Panel-leaf order, consumes a valid current-position target as unchanged, and falls through for missing, maximized, stale, or out-of-range targets without clamping. Visible focus and swap use `Ctrl+Shift+F7` and `Ctrl+Shift+F8` on both platforms; two-Panel layouts select the sole other Panel immediately, while larger layouts enter the exclusive labeled selector. Directional movement adds Shift, producing `⌥⇧⌘←/→/↑/↓` on Apple and `Ctrl+Alt+Shift+←/→/↑/↓` on Standard. The other Apple defaults are `⇧⌘P`, `⌘F6`, `⇧⌘F6`, `⌘T`, `⌘W`, `⇧⌘F`, `⌘,`, `⌘B`, `⇧⌘Enter`, `⌘R`, `⌘D`, and `⇧⌘D`. The other Standard defaults are `Ctrl+Shift+P/T/W/K/B/Enter/R/D`, `Ctrl+F6`, `Ctrl+Shift+F6`, `Ctrl+,`, and `Ctrl+Shift+E` for split below; unshifted terminal control sequences continue to the PTY. A composing application injects one complete current Workbench binding table keyed by shortcut identity, publishes whether Workbench is the active shortcut scope, and may inject a read-only effective label map for terminal-owned Actions. While active, Workbench resolves its bindings from one capture listener on its owning document, independently of which Workbench region or the document body has focus. An inactive or unmounted Workbench does not participate; Web makes it inactive while the full-screen Settings surface is open. The same binding values drive matching, menus, tooltips, and Action-search labels, including the distinct All and Actions inputs of `workbench.search.open`. The terminal context menu projects the current ordinary and current-directory New Tab labels; the Tab menu continues to project ordinary New Tab, Set Tab Title, and contextual Close Terminal. Commands without a binding leave the trailing shortcut slot empty. A shortcut is consumed only when its Action is currently enabled; unmatched and unavailable bindings continue to the focused surface without suppression. Successful New Tab execution makes its first Panel terminal the sole `autoFocus` target, including creation from an empty Tab model. Directional focus and movement are unavailable for a missing neighbor or while a Panel is maximized; cyclic focus and visual selection are unavailable for a singleton or maximized layout; equalization is unavailable for singleton or maximized layouts, so those chords also fall through without suppression.

Agent state and unread activity are separate presentation dimensions. Tabs and sidebar rows share canonical `@orchbee/agent` facts and the six-state mapping: working/thinking uses a stationary white-to-gray breathing `●`, needs-attention a pulsing yellow `●`, succeeded a green `●`, failed/canceled/interrupted a red `●`, idle a gray `○` and unknown a gray `•`. Working breathes over two seconds without changing shape; attention changes intensity every 500 ms. Both animations become static under reduced motion. The dark palette follows the shared Agent colors in `@orchbee/design-tokens`; light mode retains its contrast-aware mapping. Freshness stays in localized text without replacing the semantic symbol. The independent right blue dot uses a Client-local acknowledgement owner: initial baseline is seen; changes to status, generation, lifecycle or freshness reopen unread, while attachment/provider metadata does not. After a browser paint opportunity, only display-ready presentations in the active terminal layer of a visible focused window without an exclusive surface acknowledge the exact observed snapshot. Selection alone, pending display handoffs, hidden tabs, maximized siblings, other Clients and stale paints cannot clear it. Focus and reading keep completion green. Accepted terminal editing input projects only the exact completed outcome as idle in this Client; focus, scrolling, navigation and rejected input do not. New outcomes and attachment generations revoke the override. Canonical state, pending requests, outcomes and notification inputs remain unchanged. There is no durable or cross-user read policy; the existing canonical aggregate order is retained.

## Development

Workbench's Vitest configuration schedules no more than four file workers and no more than the
parallelism available to the Node.js process. It prints the detected parallelism and configured
worker cap once when loading the test configuration so constrained CI runs remain diagnosable.
This affects execution scheduling only; test selection, assertions, the default five-second
timeout, and existing per-test overrides remain unchanged.

```sh
pnpm --filter @orchbee/workbench... build
pnpm --filter @orchbee/workbench typecheck
pnpm --filter @orchbee/workbench test
pnpm --filter @orchbee/workbench test:exports
```
