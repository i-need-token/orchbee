## 身份和版本控制

每个协议标识正好是 16 个非零字节。 JSON 将其呈现为 32 个不带分隔符的小写十六进制字符。全零字节保留用于不存在的信封标识，并且在需要标识时被拒绝。

| 身份                       | 所有者和寿命                                                                 |
| -------------------------- | ---------------------------------------------------------------------------- |
| `HostEpoch`                | 每个主机进程随机；范围每个主机拥有的参考                                     |
| `CreationId`               | 应用程序创建的持久身份；一个幂等密钥，同时其终端仍由一个主机纪元保留         |
| `TerminalId`               | 随机主机身份保留直至明确处置                                                 |
| `ClientId`                 | 有线提供的诊断代理身份；它不会独立于活动的物理会话授予权限                   |
| `AttachmentId`             | 一个物理连接拥有的附件承载协商的功能                                         |
| `TerminalThemeOperationId` | 应用程序为一个终端主题比较和设置操作创建的幂等性身份                         |
| `CorrelationId`            | `Hello` 之后的每个请求和响应都需要；全零信封字节意味着仅握手消息或事件不存在 |

当前协议版本精确为 `0.0.20`。`Hello`、`HelloAccepted` 与每个传输信封都携带该精确版本。不同的主版本、次版本或补丁版本均被拒绝；该预发布契约不包含任何协商范围、兼容模式或历史消息结构。打包 OBTF 帧格式精确为 `0.0.3`；OBPB 投影缓冲区格式精确为 `0.0.2`；OBRW 行窗口格式精确为 `0.0.3`；OBKG 图形扩展格式精确为 `0.0.2`。对应解码器只接受这些精确格式。虽然这些契约的主版本为 `0`，仓库只保留当前尚未发布的契约，不为开发修订保留变更日志。首次公开发布时契约版本变为 `1.0.0`；此后每项外部可观察契约变化都要更新所属语义版本，并在 [`../docs/version-history.md`](../docs/version-history.md) 记录。Host 构建版本是用于标识可执行文件的独立语义版本；`HelloAccepted.hostVersion` 仅将其用于诊断，不要求构建版本与协议版本一同递增。

## 控制合约

低速率控制有效负载是 UTF-8 JSON，由信封界定，并使用消息的 Zod 模式进行解析。未知键和重复的 JSON 对象成员名称（包括转义等效名称）将被拒绝。无效的 UTF-8、无效的 JSON、JSON 字符串中未配对的 UTF-16 代理、重复的环境名称、无效的身份和超出范围的大小在状态突变之前失败。 TypeScript 请求生产者使用消息种类选择的 `encodeControlRequest` 边界；调用者无法将请求类型与不同的有效控制模式配对。本机请求使用者在分派之前将相同的有效负载解码为键入的主机命令。

`TerminalProfile` 携带显式 `defaultCursorShape`（`block`、`underline` 或 `bar`）和 `defaultCursorBlinking` 值。当解码较旧的持久配置文件形状时，这两个字段都具有兼容性默认值（`block` 和 `false`）；当前的编码器实现了它们。这些是启动默认值，而不是不可变的光标状态：终端转义序列可能会覆盖两者，直到 RIS 或应用程序重置恢复配置文件值。

`TerminalTheme` 是一个完整的运行时颜色值，包含 `colorScheme`、无符号 24 位 `defaultForegroundRgb` 和 `defaultBackgroundRgb`、可空无符号 24 位 `defaultCursorRgb` 以及恰好 256 个无符号 24 位`palette` 条目。 `TerminalThemeState` 添加了规范的十进制文本 uint64 `revision` 和可为空的 `operationId`。修订版 `0` 是启动基线，是唯一具有空操作标识的合法状态；每一个积极的修改都带有其做出的身份。运行时主题不包括光标形状/闪烁、覆盖、应用程序令牌、内容修订或生成。

消息注册表还拥有每种类型是否可以是请求、响应、事件或声明的组合；每个合法角色中的有效负载编码；以及每个请求的成功响应类型。 TypeScript 连接代码派生这些事实，而不是接受它们作为调用站点参数。本机生产镜像注册表并在记录传递之前拒绝错误的角色或编码。生成的一致性语料库会比较每个镜像字段，而不仅仅是数字类型集。

`Hello` 和 `HelloAccepted` 最多携带 64 个 `supportedOptionalFeatures` 名称，每个名称非空，最多 64 个 UTF-8 字节。可选功能名称与其解码后的 JSON 字符串值进行比较；因此，Unicode 代码点可以使用多个字节，同时保持在字节范围内。

`TerminalLaunch` 包含一个文字可执行文件和一个参数数组； 它从不包含 shell 连接的命令字符串。 `currentDirectory: null` 表示继承 Host 启动上下文。 环境条目是一个增量：`value: null` 删除变量或使变量不存在，而 `""` 设置显式空值。 名称不能包含`=`. 启动字符串不能包含 U+0000，因为可执行文件、参数、目录、名称和值字段跨越操作系统进程边界。 产品秘密和值仍然是有效负载数据，并且被排除在正常诊断之外。

四个启动几何字段构成封闭选择。`columns`、`rows`、`cellPixelWidth` 与 `cellPixelHeight` 要么全是合法正整数，要么全是 `null`；混合几何属于畸形输入。数值几何要求立即启动，无头调用方与测试调用方必须提供。空几何会保留延迟终端标识并准备启动，但不隐式提供网格。后续 `StartTerminal` 携带完整 `TerminalGeometry`；线协议契约不定义超时或 80x24 可视回退。

环境名称在线路上是唯一的，与写入的完全相同：名称与写入相同的两个条目将被拒绝，而仅大小写不同的名称（例如 `Path` 和 `PATH`）仍然是不同的线路名称。环境名称是目标操作系统环境标识符，主机在准备启动时应用目标 OS 的身份规则：在 POSIX 目标上，名称区分大小写，因此 `Path` 和 `PATH` 是不同的变量；在 Windows 上，名称不区分大小写，因此相同的两个条目是重复的，并且主机在任何进程或 PTY 效果之前拒绝 `CreateTerminal`，并键入 `invalid-field` 失败。 `CreationId` 启动指纹使用与目标身份规则相同的归一化，因此等效折叠输入会产生稳定的、平台一致的摘要。

`TerminalConfiguration` 当前包含 `scrollbackBytes`。内置默认值为 10,000,000 个十进制字节；零会禁用保留回滚；安全上限为 1,000,000,000 个十进制字节。`TerminalLaunch` 携带显式配置或 `null`；首次创建时，`null` 解析为 Host 当前终端默认值。未解析的启动值参与 `CreationId` 摘要，因此即使 Host 默认值后来变化，幂等重试仍保持稳定。`SetTerminalDefaults` 只影响后续终端。`UpdateTerminalConfiguration` 会变更一个保留终端。增加回滚预算可以保留历史；减少预算会淘汰满足边界所需的最旧行。行被淘汰时，Host 会推进内容修订与生成，并使历史锚点、选择/导出状态与投影基准失效。清单摘要会报告有效配置及其独立配置修订，以及完整的当前运行时主题状态及其独立主题修订。

JSON 内的规范无符号 64 位整数使用十进制文本，除了值 `0` 之外，没有符号、空格、指数或前导零。打包二进制使用小端无符号整数。

## 运行时绑定

每个连接在任何其他请求之前恰好发送一个 `Hello`。 `Hello` 和 `HelloAccepted` 协商 `frameBytes`、`inputBytes` 和 `rowWindowBytes`。每个握手后请求都携带非零的`CorrelationId`和当前的`HostEpoch`；每个响应都保留相关性。事件没有相关性。过时的纪元、重复的 `Hello` 和预握手操作在没有状态突变的情况下失败。

命名响应类型是权威的：`HelloAccepted`、`ProtocolRejected`、`TerminalStartAccepted`、`AttachmentCapabilities`、`InputAccepted`、`ResizeAccepted`、 `ProjectionDemandAccepted`、`TerminalDefaultsAccepted`、`TerminalConfigurationAccepted`、`TerminalControlAccepted`和`TerminalThemeResult`回答其相应的请求类型。其他成功的操作会以其请求类型进行响应。 `TypedFailure`可以回答任何请求并保留其相关性。

| 操作                              | 成功的有效载荷                                                                                                                                                               |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ListTerminals`                   | 有效终端摘要的一代范围页面                                                                                                                                                   |
| `CreateTerminal`                  | `TerminalIdentity`                                                                                                                                                           |
| `StartTerminal`                   | 精确的终端标识、接受的完整几何形状以及 `started` 或 `already-started` 过渡                                                                                                   |
| `SetTerminalDefaults`             | 有效的默认配置和默认修订                                                                                                                                                     |
| `UpdateTerminalConfiguration`     | 终端标识、有效配置和修订、内容修订/生成以及逐出行计数                                                                                                                        |
| `ApplyTerminalTheme`              | 终端和请求操作标识、`applied`、`already-applied` 或 `stale` 转换以及完整的当前操作/修订/主题状态                                                                             |
| `TerminateTerminal`               | 目标 `TerminalId`                                                                                                                                                            |
| `ForceTerminateTerminal`          | 目标 `TerminalId`                                                                                                                                                            |
| `DisposeTerminal`                 | 目标 `TerminalId`                                                                                                                                                            |
| `AttachTerminal`                  | 附件与终端标识、授予的 input/read/resize 能力、初始能力修订 `1`，以及调整大小租约事实                                                                                        |
| `DetachTerminal`                  | 目标 `AttachmentId`                                                                                                                                                          |
| `UpdateAttachmentInputCapability` | 附件与终端标识、完整当前能力、当前正数能力修订，以及调整大小租约事实                                                                                                         |
| `ClaimResizeLease`                | 附件与终端标识、完整且未改变的能力与能力修订，以及已提交的调整大小租约事实                                                                                                   |
| 原始或语义输入                    | 附件身份、准确的功能修订以及致力于有序入口的编码终端字节计数                                                                                                                 |

`RuntimeFailure.stage` 是主终端故障的判别式； `kind`是其所需的更粗的类别，不是一个独立的字段。其合法配对为`admit-terminal-reply/terminal-reply`、`apply-resize/resize`、`dispatch-termination/process-control`、`observe-process/process-observation`、`read-output/pty-read`、`synchronize-worker/worker-integrity`和`write-input/pty-write`。其他每一对都是畸形的。 `ProcessObservation.kind = unavailable` 始终携带 `observe-process/process-observation` 对。 `FailureContainment.kind = blocked` 相反携带一对上下文清理：`contain-process/process-control`、`release-output/pty-read` 或 `release-process-identity/process-observation`。清理对的格式错误为主要故障，并且主要对在任一上下文位置上格式错误。

`ListTerminals` 接受 `{ cursor, maximumTerminals }`。 `cursor` 是首页的 `null` 或包含来自先前响应的规范十进制 `inventoryGeneration` 和 `offset` 值。 `maximumTerminals` 是 `1-128`。响应重复 `inventoryGeneration`，最多返回请求的摘要数量，并提供下一代范围的游标或 `null`。创建和部署高级会员生成；生命周期、几何、修订和退出更改不会。一代不匹配会返回 `stale-inventory-cursor`，因此一次遍历永远不会合并两个成员资格。每个页面都保持在 64 KiB 控制范围内，并且协议没有设置终端总数限制。

`awaiting-start` 库存摘要包含空 `columns` 和 `rows`、无退出、故障、遏制或过程观察以及 `terminateRequested: false`。启动阶段带有正网格几何形状。启动后精确的 `StartTerminal` 重放将返回 `transition: already-started` 的原始标识和几何图形；不同的几何形状是不可重试的 `start-conflict` 类型。生成失败是一种类型化的可重试失败，既不发布成功的启动响应，也不发布 `TerminalStarted` 事件；这些效果的生命周期所有权仍然属于 Terminal Host。

`TerminateTerminal` 和 `ForceTerminateTerminal` 是不同的请求类型。线材允许Desktop直接发力；主机拥有的生命周期决定当前阶段是否接受请求并保证强制包含优雅的意图。这两个请求都不会处理保留的身份。 Desktop 拥有升级计时，并在请求处置之前等待 `TerminalExited` 或 `TerminalFailed`。丢失的身份和无效的当前状态请求将被报告为类型化失败，而不会被编解码器重新解释。

该线路不会暴露主机的物理代理会话身份。主机将附件绑定到其一个活动代理会话，并通过该会话解析每个 `AttachmentId`。 `ClientId`是诊断元数据，不合并、转让、独立授予权限。

每个附件至少请求输入、读取或调整大小权限之一。仅当也请求并授予调整大小权限时，调整大小租约才是合法的。空的请求能力绑定和没有调整大小权限的调整大小租约在附件准入时格式错误。仅输入附件降级后，完整的当前能力值可以全部为 false。

kind `25` 的 `ClaimResizeLease` 只携带一个附件标识。运行中且具有 resize 能力的附件可以
claim terminal 的唯一 lease；当前 owner 的重放是幂等的。一次成功 transfer 会返回完整且未改变的
`AttachmentCapabilities`，先发布前 owner 的 `resizeLease: false` `ResizeLeaseChanged` fact，
再发布 claimant 的 `resizeLease: true` fact；成功 response 位于两个 event 之后。遭拒 claim
保留此前 owner、geometry、capability revision 与已准入 capability value。Non-owner 的
`ResizeTerminal` 会被拒绝，绝不会隐式 claim。

`ResizeLeaseChanged` 是仅事件的完整所有权事实，包含确切的附件和终端身份以及 `resizeLease`；它从来都不是一个切换。当分离调整大小所有者提升现有观察者时，主机会在成功分离响应之前提交该观察者的事件。消费者在更改可能颁发 `ResizeTerminal` 的人员之前，根据其附件范围验证这两个身份；演示测量本身仍然是客户本地的，并且不需要租用。

`ApplyTerminalTheme` 是终端范围的，不需要附件。它携带 `terminalId`、`operationId`、`expectedThemeRevision` 和一个完整的 `terminal` 主题。主机在生命周期和比较和设置之前检查精确的当前操作重放：相同的操作 ID 和主题返回 `already-applied` 而没有突变，而具有不同主题数据的相同 ID 返回不可重试的 `theme-operation-conflict`。预期修订版本不是当前版本的不同操作会返回 `stale`，而不会发生突变。接受的操作应用完整的延迟或启动运行时状态，然后推进独立主题修订一次；其结果转换为 `applied`。

每个`TerminalThemeResult`都会回显请求操作和终端身份，并包含完整的权威`current`状态。对于`applied`和`already-applied`，`current.operationId`等于回显请求操作；对于 `stale`，则有所不同。运行时应用程序替换了主机拥有的动态颜色默认值并清除了先前的 OSC 颜色覆盖；稍后的终端 OSC 操作可能会覆盖这些默认值，而它们的重置表单、RIS 和应用程序重置将返回到最新的运行时主题。丢失的结果是未知的结果：客户端在变基之前首先通过库存进行协调，并且永远不会从客户端本地覆盖推断权限。

`ClearTerminal`和`ResetTerminal`各自仅携带有输入能力的`AttachmentId`；它们是语义主机请求，而不是终端输入有效负载。 Clear 会擦除并返回活动的 Ghostty 屏幕，而无需重置模式。 Reset执行Ghostty的完全重置并返回主屏幕。 `TerminalControlAccepted` 返回附件、解析的终端、精确操作以及生成/修订结果。丢失的响应是未知结果，并且不授权重播。

每个附件均以能力修订版 `1` 开头。`AttachmentCapabilities` 在完整的当前能力值旁报告该正数规范 uint64 修订，其中可以包含仅输入附件降级后的全 false 值。`UpdateAttachmentInputCapability` 类型 `24` 携带附件、正数修订和下一个输入位。Host 仅应用更改输入位的精确 `current + 1` 修订；精确的当前修订和值是幂等重放。同修订不同值或下一修订不变值是 `capability-revision-conflict`；旧修订或缺口是 `stale-capability-revision`。读取和调整大小能力在此协议版本中仍是不可变的已准入值。

`WriteInput` 是一个原始字节有效负载，恰好包含 16 个非零 `AttachmentId` 字节、一个正的小端 uint64 功能修订版，然后是一个协商的 `inputBytes` 终端字节。硬终端字节最大值为 1 MiB，因此最大原始有效负载为 1 MiB 加 24 个字节。附件及具体修改解决当前输入权限； `TerminalId` 从未出现在此有效负载中。 `InputAccepted` 呼应修订版，意味着完整的终端字节后缀已提交到有序有界主机队列一次。它是仅队列准入的，并且不保证字节已到达终端写入器，因此根据主机的有界回复优先级策略，终端生成的回复可以在接受的客户端字节之前传送。在该响应之前断开的连接会使结果未知并且永远不会授权重播。

TypeScript 生产者使用 `encodeInputRequest`；消息类型选择原始或语义二进制编解码器。本地消费者通过一个语义输入解码器路由相同的注册类型，因此双方都不需要维护业务层类型到格式表。

`KeyInput`、`TextInput`、`MouseInput`、`FocusInput` 和 `PasteInput` 是有界打包有效负载，以相同的 24 字节权限标头为前缀：附件标识后跟其正小端 uint64 功能修订版。它们携带浏览器规范化的语义意图，而不是 DOM 对象或预选的转义序列。 `KeyInput` 字节 `24` 携带按键操作，而字节 `25` 在位 `0` 中携带组合，在位 `1` 中携带每个事件 Option-as-Alt 意图。客户端在发布之前解决任何左/右 macOS 偏好； Terminal Host 将意图应用于权威 Ghostty 编码器模式，而不是接受客户端选择的转义序列。 `PasteInput` 使用 32 字节标头：字节 `24` 在位 `0` 中携带经过审核的括号粘贴期望，字节 `25-27` 保留零，字节 `28-31` 携带小端文本字节长度。未知的标志位或非零保留字节将被拒绝。按下或释放鼠标始终会识别其按钮。没有按下按钮的鼠标运动带有空按钮；按下按钮的运动标识 `pressedButtons` 中存在的一个活动按钮，其位集描述了完整的当前按下按钮状态。滚轮报告仍然是按钮按下情况，不需要描述按住的按钮。主机调度在编码之前保留入口顺序和快照权威 Ghostty 编码器模式，因此输出合并或飞行中的帧不会使键、鼠标或焦点编码过时。对于粘贴，主机将权威的括号粘贴模式与审查的期望进行比较，同时保持用于编码的相同终端锁定。不匹配在队列准入之前返回不可重试的 `input-mode-changed`；客户端必须获取当前的预计状态并请求新的用户决定，而不是重播不明确的粘贴。协商的 `inputBytes` 限制适用于编码的终端字节输出，而不是打包的语义负载； `acceptedBytes` 报告当当前终端模式故意不发出任何内容时，输出长度可能为零。主机必须在队列准入之前预检零输出并粘贴边界，然后仅将编码字节计入有序入口预算。

关闭活动是一项提示性的、对新鲜度敏感的采样，而不是生命周期或遏制权威。消费者将缺失、重复、畸形或无法识别的关闭活动载荷映射到 `unknown`。已接受的非焦点输入会在输入 API 返回前同步将客户端最近提交的观察失效为 `unknown`。仅焦点输入和同步遭拒的输入不会使其失效。历史行、失败的实时快照及已暂存但未提交的帧都不能恢复新鲜度；只有随后提交且具备因果新鲜度证据的实时呈现可以恢复。

Host 在投影脏数据门控前按有界节奏采样活动。已接受的会影响活动的输入会使缓存采样失效，并在终端内容修订未变时仍强制生成实时快照。如果已在途的帧到达已在本地失效的消费者并声称 `idle`，消费者会针对其精确序列发送原因是 `activity-stale` 的 `NeedSnapshot`，而不是 `FrameApplied`。Host 放弃该在途帧并强制生成完整快照；由于该请求在消费者到 Host 的流中位于输入之后，替换帧构成因果证据，证明即便终端修订未变，Host 缓存也是在失效后捕获的。它既不证明 Host 接受了输入，也不证明终端进程消费了输入。Host 接受的非焦点输入会立即使缓存观察失效。后续有界当前状态采样可以发布 `active`、`idle` 或 `unknown`，因此替换帧及同一生命周期内后续帧可以合法恢复新鲜的 `idle`。主题暂存阶段会在声明就绪前应用此围栏。新鲜的 `idle` 可以允许产品不经确认直接关闭；`active`、`unknown` 及任何本地过时的呈现都需要确认。

进度状态字节 `0` 移除指示器，`1` 有效，`2` 错误，`3` 不确定，`4` 暂停。 `remove` 和 `indeterminate` 需要空标记。 `set`、`error` 和 `pause` 接受空标记或百分比。重复的进度扩展、未知状态、高于 `100` 的百分比以及非法状态/值组合会拒绝整个帧。省略的进度扩展解析为 `remove`。进度是当前的呈现元数据，而不是生命周期、流程、通知或完成权限。

| `32`   |    4 | 聚合解码像素字节              |
| `36`   |    4 | 保留零                        |

每个快照图像都是一个 32 字节记录，紧接着其原始像素字节：图像 ID `u32`、gray/gray-alpha/RGB/RGBA 格式 `u8`、三个保留零字节、generation `u64`、宽度和高度 `u32`、字节长度 `u32` 以及保留零 `u32`。像素长度必须恰好等于维度乘以通道；图像 ID 唯一且非零；所有当前放置必须引用快照图像。每个 56 字节放置记录图像与放置 ID、带符号网格列和行、像素偏移、源裁剪、目标像素大小、带符号 `z` 和标志。只定义 internal-ID 标志位。每个有符号 32 位 z 值都合法；合成精确使用三个有序层：`z < -1073741824` 位于单元格背景下方，`-1073741824 <= z < 0` 位于单元格背景与文本之间，`z >= 0` 位于文本上方。快照裁剪矩形受其图像边界约束。

客户端在 256 个可见解码图像和 1,024 个可见放置中最多保留 4 MiB。仅放置更新不携带图像字节，并且必须命名精确的已保留资源修订；消费者在提交任何文本行前还会根据已保留图像图验证每个引用与裁剪。携带仅放置扩展数据的终端快照无效。资源集或显示动画 generation 变化、重传、删除、重置、屏幕变化或未确认基线都会把 Host 的整个 OBTF 记录提升为快照。direct、文件、临时文件及受支持的 POSIX 共享内存输入、raw/PNG/zlib/chunk 传输、动画、virtual 与 relative 放置、裁剪、有符号 z 合成和历史相交都在本机边界解析。OBKG 只携带自有解码像素和已解析放置；绝不携带路径、URL、句柄、共享内存名称或映射、编码容器、压缩流或未解析 Ghostty pin。

快照没有基础，并且包含按规范顺序排列的每个可见行。增量命名确切的已确认基数，并按递增的行顺序替换完整的、唯一的脏行；它从不携带部分细胞。当没有网格行变脏时，增量可以包含零行，同时仍携带其元数据与修订转换。尺寸、活动屏幕或世代更改需要快照。 TypeScript 解码器首先验证并扫描所有表和行，然后分配精确类型的列并读取单元格，而无需为每个单元格构建 JavaScript 对象。在改变提交的网格之前，预计的存储会暂存完整快照或每个增量行。帧序列是单调发出的，但废弃的帧可能会在提交的客户端序列中留下间隙。增量必须是确切的下一个序列并命名确切的提交碱基。完整快照可以使用大于最后提交序列的任何序列，并跨过这样的间隙原子地重新建立客户端基础。固定标题检查器仅验证有界标题，从不接受单元格、字符串、样式、行或扩展数据。能力范围的本地客户端可以在完全解码之前使用该检查器，仅确认它已经提交的序列。这是合理的，因为主机交付所有者在移交该作用域序列时使完整的编码记录不可变。每个更高的 OBTF format-`0.0.3` 序列以及到达可信本地传送路径之外的每个帧在暴露或提交任何有效负载数据之前仍然需要完整的解码器。 OBPB 格式 `0.0.2` 投影缓冲区提供下面单独命名的严格解码和局部结构视图边界。具有不同标头提交元数据的重复序列是协议状态冲突，需要恢复；消费者不会散列或重新扫描重复的有效负载，以防止生产者违反不可变序列合约。对于一帧中存在的每一对相邻行，前一行的换行标志等于下一行的换行继续标志。间隔头仅在换行行的最后一列中有效；如果存在下一行，则它从相应的宽单元格开始。这些关系在框架公开或提交之前进行验证。

原生表面证据集包含导出的 `ghostty-surface-v0.0.3.bin`、`ghostty-alternate-surface-v0.0.3.bin` 和 `ghostty-render-row-window-v0.0.3.bin`。Terminal Host 从一个固定版本的原生 Ghostty VT 和真实 OBTF 编码器依次生成 OBTF 夹具对。另一个固定版本的终端会重放主语料，加入 DECSCA 受保护与未受保护单元，并且只通过 `row_encoding.encode` 和 `projection_buffer.encodeRenderSnapshot` 生成 render-detail OBRW；这些字节不由 TypeScript 编码器构造。生产者一致性检查会重新生成并逐字节比较全部三个夹具。TypeScript OBRW 消费者依据一份按契约编写的完整 6x8 矩阵检查严格视图与可信视图，通过 `replaceProjectionBufferSnapshot` 提交可信帧，并验证颜色节顺序、样式、语义、保护、超链接、行换行和宽度拓扑的线协议有效变异。该证据能检测原生列误赋值或遗漏，但不会改变格式、验证 PTY/历史行为，也不向本包授予 VT、渲染器、生命周期或可信本地路径权威。

## 当前投影缓冲区

OBPB 格式 `0.0.2` 是打包的主机到渲染数据平面。 `decodeTerminalProjectionBuffer` 是默认边界，在公开类型化视图之前严格扫描行、单元格、颜色、字符串范围、UTF-8 和宽单元格不变量。网关、网络对等点、插件或持久工件必须使用该严格边界。 `viewTerminalProjectionBuffer` 保留用于不可变、同一用户、功能范围的本地主机路径。它检查固定标头、身份、计数、规范节目录、对齐和零填充、总长度以及两个小元数据字符串，然后在相同字节上创建类型化数组视图。它故意不遍历每个单元格来重新验证已从规范 Ghostty 状态生成的值；跨语言一致性和生产者测试建立了这些列不变量。

## 当前打包的终端行窗口

`ReadRows` 的范围包括附件、修订、生成、肯定请求序列、请求的行数、协商字节最大值、详细信息（`render` 或 `text`）、用途（`viewport`、`search` 或`buffer`），以及一个来源：

- `absolute` 命名保留的绝对行。
- `oldest` 命名距最旧保留行的无符号偏移量。
- `tail` 指定请求的视口下方剩余的行数。
- `committed` 将有界符号增量应用于附件的最后应用的锚点。

Host 解析一次来源并返回连续 `RowsSnapshot`。每个附件的每个 purpose 通道至多有一个行请求在途；`viewport`、`search` 与 `buffer` 通道彼此独立推进。请求序列在附件生命周期内严格递增；安装前失败的请求不消费序列。响应只形成待定锚点；匹配的 `RowsApplied` 才把它提升为已提交锚点，因此较早行请求的迟到确认无法提升较晚锚点。调整大小会使待定且固定到生成的行捕获失效，但已提交跟随锚点仍可跟随有效 Ghostty reflow pin。屏幕生成变化、分离或 Ghostty 页面淘汰会使受影响锚点失效。等待精确确认期间，`HistoryChanged` 会合并。每个 `HistoryChanged` 事件及其 `HistoryObserved` 确认都携带正数的附件本地事件 `sequence`；该值在附件生命周期内严格递增且从不复用。`HistoryObserved` 会原样返回被确认事件的精确 `sequence`。若确认的 `sequence` 早于当前在途事件，则无论过时还是重复都作为幂等空操作，绝不会清除更新在途事件；修订/生成标识仍按完全匹配的在途事件校验。

## 主机拥有的选择和导出

选择手势和命令始终携带附件的当前修订和生成。手势`start`携带浏览器分类的点击次数、整数表面位置以及第三次点击是否选择语义输出； `update` 携带当前表面位置、矩形意图和有界单元几何形状； `end` 只携带其终点； `cancel` 不携带点或操作特定字段。主机使用这些事实和固定的 Ghostty 选择行为来拥有字、行、输出块、矩形和单元内端点语义。 `cancel` 幂等地释放固定手势，同时保留最新的选择，而只有 `end` 代表普通的指针释放。端点是绝对行/列对；活动状态仅包括端点、矩形模式和可选的 4 KiB 预览。 `none` 和 `evicted` 是不同的，因此客户端无法在回滚丢失或屏幕更改后以静默方式复制替换内容。

`SelectionCommand.set-range` 携带显式包含的 `start` 和 `end` 单元端点以及矩形模式。它是辅助技术和其他程序化选择的非指针路径；它不会综合点击计数、拖动阈值或指针手势状态。

`SelectionExport` 携带文字 `plain` 格式和严格增加附件生命周期的附件本地导出序列； HTML 和原始 VT 不是允许的请求或响应值。在安装之前失败的导出不会消耗其序列。主机首先返回 `SelectionExportStarted`，然后在飞行中最多发出一个原始 `SelectionExportChunk`。每个块包含附件标识、导出序列、单调 `u32` 块序列、最终位以及最多 1 MiB 字节。 `SelectionExportChunkApplied` 仅推进匹配的导出，因此来自较早导出的延迟确认无法推进较晚的流。完成或明确取消会释放所有导出存储。格式化输出总量上限为 16 MiB。选择-导出剪贴板写入和其他平台效果保留在该协议包和主机之外；单独定义的 OSC 52 请求仅携带意图，但仍然不授予任何平台效果。

## 硬界限

握手可以选择较小的传输有效负载范围。它永远不会提高这些包的硬限制。

| 输入或保留单位               |           硬最大值 |
| ---------------------------- | -----------------: |
| 控制 JSON                    |             64 KiB |
| 一项 OSC 52 剪贴板文本       |             16 KiB |
| 一个库存页面中的终端         |                128 |
| 一个原始、文本或粘贴输入正文 |              1 MiB |
| 一键文字                     |              4 KiB |
| `WriteInput` 原始有效负载    |       1 MiB + 24 B |
| 最大语义输入有效负载         |       1 MiB + 32 B |
| 每个终端待处理的有序输入     |              4 MiB |
| 每个终端的回滚配置           |    1,000,000,000 B |
| PTY 读取批次                 |            256 KiB |
| 包装框架                     |              8 MiB |
| 所有帧扩展/一条 OBKG 记录    |              5 MiB |
| 解码Kitty资源                |              4 MiB |
| 小猫图片/展示位置            |         256 / 1024 |
| 传输记录                     |      16 MiB + 64 B |
| 行窗口记录                   |             16 MiB |
| 客户端边界处的搜索查询       |             16 KiB |
| 选择预览                     |              4 KiB |
| 选择导出/一大块              |     16 MiB / 1 MiB |
| 单个 UTF-8 字符串            |             16 KiB |
| 字符串/样式/行记录           | 4096 / 1024 / 4096 |
| 单元/框架扩展                |        262144 / 64 |
| 总扩展字节数                 |              5 MiB |
| 网格列/行                    |        4096 / 4096 |
| 单元格像素宽度/高度          |        4096 / 4096 |
| 终端像素总宽度/高度          |      65535 / 65535 |

`One UTF-8 string` 限制每个序列化字符串，并且对于文本行窗口，每个逻辑单元的字节跨度：从映射开始到下一个映射开始的字节以及到行文本结束的最终跨度必须适合 16,384 个字节。聚合行文本不受此每个单元格边界的限制。

在相关分配之前检查计数和长度。整数溢出、长度不一致、截断、无效的 UTF-8、错误的表引用、重复或超出网格的行以及未知的必需标志都属于类型失败。

终端、附件和连接总数没有协议或产品硬最大值。分配、进程、PTY、标识符空间或操作系统耗尽拒绝当前操作；它不授权截断库存或删除保留状态。

## 消费者拥有的行为

有效的协议值本身并不是合法的域转换。状态所有者决定该值是否可接受、执行效果、提交状态并确定重试行为：

| 消费者        | 权威行为和证据                                                                                                                                                                                       |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Terminal Host | 终端成员资格和生命周期、进程/PTY 所有权、运行时故障遏制、附件功能状态、有序输入、投影/历史/选择交付、批量提交和主机关闭。请参阅[主机运行时模型](../../../apps/terminal-host/docs/runtime-model.md)。 |
| 桌面          | 产品绑定、持久意图、重新连接、终端关闭升级、结果发布、更新激活和渲染器/网关协调。请参阅 Desktop 拥有的指南、模型和测试。                                                                             |
| 渲染器        | 呈现并应用已经验证的投影/历史值；它不会获得 Host 生命周期权限。                                                                                                                                      |

消费者模型可以使用协议消息名称和模式作为细化点，但它们与拥有建模状态的消费者一起生活。该包的证据有意仅限于线路形状、精确版本处理、安全边界、确定性编解码器、畸形输入拒绝、生成的夹具完整性和跨语言一致性。它不声明流程、交付、恢复、调度或产品策略的正确性。
