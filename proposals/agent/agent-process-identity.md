## Claims

### Four separate facts

| Claim       | Question                                                                                           | Owner                            | Evidence                                                                                 |
| ----------- | -------------------------------------------------------------------------------------------------- | -------------------------------- | ---------------------------------------------------------------------------------------- |
| Identity    | Which supported provider is the interactive Agent of this Terminal generation, and which run is it | This proposal                    | An anchor process and registry rules, or a launch receipt                                |
| Liveness    | Is that run's anchor process still alive                                                           | Derived from identity            | The anchor's process identifier and creation time in a successful sample or anchor probe |
| Readiness   | Can the Agent's interactive interface accept input                                                 | Agent start and hook observation | Hook lifecycle observations                                                              |
| Task status | Working, attention, and outcome                                                                    | Canonical Agent model            | Hook observations, then screen fallback                                                  |

Identity never implies readiness or task status. A missing hook never revokes a proven identity, and a hook alone never establishes one: it can only verify the provider of a run that a receipt already anchors.

### Identity results

A Terminal generation is one Host Terminal identity within one Host epoch and creation generation. Each Terminal generation has exactly one current result.

| Result                      | Meaning                                 | Required evidence                                                                                                                                                                                                       |
| --------------------------- | --------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `agent`, grade `confirmed`  | An Orchbee-started run                  | A Server-minted run whose receipt comes from the same Terminal generation, an anchor process that appeared inside the receipt window, and a provider verified by registry rules or by a hook that carries the run token |
| `agent`, grade `recognized` | A typed run                             | Successful samples showing one anchor whose provider, provenance, and interactive mode the registry resolves, held for the settle window                                                                                |
| `none`                      | No interactive Agent run                | A successful sample with no candidate and no unresolved row that could hold one                                                                                                                                         |
| `unknown`                   | Evidence is incomplete or contradictory | Exactly one reason from the closed list                                                                                                                                                                                 |
| `unsupported`               | Outside the declared matrix             | Exactly one reason, such as the platform or remote execution                                                                                                                                                            |

Unknown reasons form a closed, user-visible list: `settling`, `sample-failed`, `sample-limit`, `command-line-unreadable`, `ambiguous-candidates`, `unclassified-arguments`, `unverified-provenance`, and `detached-console`. Unsupported reasons start with `platform` and `remote-execution`. The Server mints each run, binds it to one Terminal generation, and never reuses it; a restart is a new run. A run binds at most one Agent Session, and a bound session never moves to another run.

### Meaning of 100 percent

Inside the declared matrix, for every Terminal generation at every moment after the settle window:

1. No misidentification: `agent` appears only when that provider's interactive run is the anchor.
2. No miss: `none` never appears while a supported interactive run exists.
3. Correct association: an `agent` result names the right Terminal generation, anchor, and run, and its bound Agent Session belongs to that run.
4. No hidden failure: `unknown` always carries a visible reason. In a supported cell it counts against the target and never as a pass.

Outside the matrix there is no completeness promise, but rule 1 holds everywhere: no rule may produce `agent` from evidence that would be wrong inside the matrix. Confirmed means causally correlated through cooperative shell and Host evidence; it is not authentication against a hostile process running as the same user.

## Recommended design

### Provider registry

- Each provider entry lists aliases with a collision class: unique, shared with other programs, or generic. Shared and generic aliases need provenance from an install root or package path that the entry lists.
- Install shapes are explicit per platform: native image, package entry, bundled runtime, launcher wrapper, and shim. Wrappers such as `cmd /c`, PowerShell `-Command`, `.bat`, and allowed Python modules resolve to the shape they launch, never to names mentioned in arbitrary arguments.
- A mode classifier per provider returns interactive, noninteractive, or unclassified from the documented grammar of the verified version range. Unreadable arguments never default to interactive.
- Executables of the GUI subsystem are never candidates.
- The registry is versioned data owned by the protocol crate. The Server, Client diagnostics, and the later POSIX sampler share it.

### Identity state

- The Server keeps one identity state per Terminal generation, fed by successful samples, anchor probes, receipts, and token-carrying hooks.
- A recognized result needs the same anchor in two successful samples at least 500 ms apart; until then the result is `unknown` with `settling`.
- The anchor is the outermost recognized process of the run. When it exits while a same-provider descendant continues, the run hands off to that descendant; otherwise the run ends.
- Failed samples keep the last result for at most two seconds and then yield `unknown` with `sample-failed`, unless the anchor probe proves the anchor gone, which ends the run.
- Panel Agent reports, screen fallback, and Agent start consume this state instead of separate interpretations.

### Controlled launch flow

1. Agent start reserves as today, and the Server also mints the run and its token.
2. In managed PowerShell the Client submits the launch with the run prefix. The wrapper strips it and exports the token for that command, and the Host records the start marker.
3. The anchor is the outermost recognized descendant of the shell that appears while the run window is open and belongs to no earlier run; until the registry recognizes one, the outermost such descendant serves. The registry or a token-carrying hook verifies the provider.
4. The launch result is started, provider mismatch, early finish with the shell status, ambiguous, or deadline. A finish marker or anchor departure ends the run.
5. In cmd and unmanaged shells Agent start keeps the current typed launch and reaches only the recognized grade.

### Typed runs

Typed runs reach the recognized grade through the registry and the settle window. A later slice lets managed PowerShell mark every accepted command with its own token and markers, which gives typed runs exact boundaries and exact hook binding without changing what the user types. cmd stays at the recognized grade.

### Hook association

The hook transport forwards the run token from its own environment, inherited from the Agent process, as an optional bounded envelope field. A token-carrying hook binds its Agent Session to that run when the provider matches. Without a token, a session binds to the newest live run with the same provider in the same Terminal generation, and to none when that is ambiguous. Managed integrations need an update to forward the token; older installations keep the fallback.

### Privacy and diagnostics

Command lines and environment values stay in memory. The Host reads only the named token variable, never the whole environment. Diagnostics show the result, grade, reason, anchor identity, and the matched shape with arguments reduced to their classified form, never raw command lines.

| Runtime decoys        | `node -e`, a runtime REPL, `python -c`, scripts whose arguments mention provider names, and a forged argument zero                                         | `none`                                                                                                                   |
| Wrappers              | `.cmd`, `.bat`, `.ps1`, `cmd /c`, PowerShell `-Command`, package runners, version-manager shims, and Python launchers                                      | The wrapped shape's result                                                                                               |
| Child changes         | Short-lived tool churn under an Agent, launcher hand-off, a nested Agent of another provider, and sibling Agents                                           | The same run through churn and hand-off; the outer Agent for nesting; `unknown` with `ambiguous-candidates` for siblings |
| Permissions           | Children whose security descriptor denies memory reads or all access                                                                                       | The correct result, or the matching `unknown` reason                                                                     |
| Exit and restart      | Normal exit, termination, crash, immediate restart of the same and of another provider, and exit during failing samples                                    | A run end, then a new run                                                                                                |
| Identifier reuse      | Deterministic traces with reused identifiers and inverted parent creation order                                                                            | No run transfer                                                                                                          |
| Limits and consoles   | More than 64 members, budget overrun, `start` into a new console, and a detached child                                                                     | `unknown` with the matching reason, or `none` for the original Terminal                                                  |
| Launch receipt        | Not found, early exit, alias collision, interrupt during start, and deadline                                                                               | The matching launch result                                                                                               |
| Hook association      | Token present, token absent, a late hook after restart, and two sequential same-provider runs                                                              | Exact binding, or no binding when ambiguous                                                                              |
| Remote clients        | Stand-in executables named like remote clients                                                                                                             | `unsupported` with `remote-execution`                                                                                    |

### Acceptance

- A cell is certified only when every case in it passes on each listed provider version with no false `agent`, no false `none`, no wrong association, and no `unknown` after the settle window.
- Pure rule and selector cases are table-driven regression evidence for this Consequential contract. Host cases use controlled Windows subprocesses. Real provider runs form an opt-in corpus that records verified version ranges in the registry.
- Real verification never logs in, sends prompts, or uses paid quota, and remote environments use stand-ins.

## Recorded defaults

These defaults keep the work moving; each can be vetoed on its own.

1. The 100 percent target covers only the declared certified matrix; other providers and shapes stay best effort.
2. `unknown` in a supported cell is a failure and is always shown with its reason.
3. Unclassified arguments yield `unknown`, not interactive.
4. Shared and generic aliases need provenance, so bare `agent` no longer means Cursor by itself.
5. The settle window is two successful samples at least 500 ms apart.
6. Controlled launch uses the managed PowerShell receipt, and cmd keeps the recognized grade.
7. Session binding uses a hook-forwarded run token, and integrations without it use the newest-run fallback.
8. Windows is certified first; macOS and Linux report `unsupported` until the POSIX sampler lands.
9. Failed samples keep the last result for at most two seconds.
10. This document compares no other products; external research informed only the options.

## Reserved decisions

- A private launcher process or an Agent-as-root Terminal (L-C, L-D) changes the accepted topology or product behavior and needs the decision owner.
- How the TUI and GUI present identity results belongs to their presentation owners.
