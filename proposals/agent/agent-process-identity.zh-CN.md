## 变更授权

| 字段     | 建议授权                                                                                                                                                                                                                                                   |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 分级     | 身份是建立在终端代际、运行、有序样本和时间之上的状态，因此属于 Modeled；它改变跨进程契约（Host 样本行、启动回执、Hook 信封），也改变进程上报和 Agent 启动完成的含义，因此同时属于 Consequential                                                            |
| 问题     | 原生 Agent 识别是只在 Windows 上运行、基于可执行文件名和脚本名的启发式方法。它可能认错 provider，把非交互调用算作 Agent，在某个进程不可读或候选有歧义时静默丢失身份，而且 Orchbee 发起的启动、该启动产生的进程、Hook 上报的 Agent 会话三者之间没有因果关联 |
| 阶段结果 | 在声明的支持矩阵内，每个终端代际恰好有一个带明确原因的身份结果。Orchbee 发起的运行由启动回执确认。每个受支持的矩阵单元都通过其验证样本集：无误识别、无漏识别、无错误关联，稳定窗口过后也没有未知结果                                                       |
| 非目标   | 新增 provider；无交互批处理或 API 接入；重新设计任务状态机；除保持区分外不涉及就绪与轮次语义；运行在其他机器上、或在终端背后的 WSL 中运行的 Agent；鉴别 provider 二进制的真伪；修改屏幕检测规则；TUI 与 GUI 的呈现设计                                     |
| 兼容性   | 手动输入的命令、shell 别名、包管理器 shim 和现有 Agent 启动参数继续可用。无法证明 provider 的证据给出带原因的 `unknown`，而不是猜测。现有进程上报的形状保持不变，直到其消费者采用新的结果词汇                                                              |
| 交付     | 先交付规则注册表和结果模型，然后依次是 Host 采样、Server 身份状态、启动回执、Hook 关联和 Client 消费者。每个切片附带自己的证据                                                                                                                             |
| 恢复     | 每个切片都可以单独撤回。没有回执时，运行退回识别等级；没有扩展的 Host 行时，Server 保留当前样本；注册表变更是带版本的数据                                                                                                                                  |

## 声明

### 四项独立事实

| 声明     | 问题                                                               | Owner                  | 证据                                             |
| -------- | ------------------------------------------------------------------ | ---------------------- | ------------------------------------------------ |
| 身份     | 这个终端代际的交互式 Agent 是哪个受支持的 provider，属于哪一次运行 | 本提案                 | 锚点进程加注册表规则，或启动回执                 |
| 存活     | 该运行的锚点进程是否仍然存活                                       | 由身份派生             | 成功样本或锚点探测中出现的锚点进程标识与创建时间 |
| 就绪     | Agent 的交互界面能否接收输入                                       | Agent 启动与 Hook 观测 | Hook 生命周期观测                                |
| 任务状态 | 工作中、需要关注和结果                                             | 规范 Agent 模型        | Hook 观测，其次是屏幕回退                        |

身份从不蕴含就绪或任务状态。缺少 Hook 永远不会撤销已证明的身份，单独的 Hook 也永远不能建立身份：它只能为回执已经锚定的运行核实 provider。

### 识别结果

终端代际指一个 Host epoch 和一个创建代际内的一个 Host 终端身份。每个终端代际在任一时刻恰好有一个当前结果。

| 结果                       | 含义                  | 所需证据                                                                                                                          |
| -------------------------- | --------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `agent`，等级 `confirmed`  | 由 Orchbee 发起的运行 | 一个由 Server 生成的运行，其回执来自同一终端代际；一个在回执窗口内出现的锚点进程；provider 由注册表规则或携带运行令牌的 Hook 核实 |
| `agent`，等级 `recognized` | 手动输入的运行        | 若干成功样本显示同一个锚点，注册表能解析其 provider、来源证明和交互模式，并在稳定窗口内保持不变                                   |
| `none`                     | 没有交互式 Agent 运行 | 一个成功样本中没有候选，也没有可能包含候选的未解析行                                                                              |
| `unknown`                  | 证据不完整或相互矛盾  | 封闭原因列表中的恰好一个原因                                                                                                      |
| `unsupported`              | 超出声明的矩阵        | 恰好一个原因，例如平台或远程执行                                                                                                  |

未知原因构成一个封闭且对用户可见的列表：`settling`、`sample-failed`、`sample-limit`、`command-line-unreadable`、`ambiguous-candidates`、`unclassified-arguments`、`unverified-provenance` 和 `detached-console`。不支持原因首先包括 `platform` 和 `remote-execution`。每次运行由 Server 生成，绑定到一个终端代际，且永不复用；重启就是一次新运行。一次运行最多绑定一个 Agent 会话，已绑定的会话永远不会转移到另一次运行。

### 100% 的含义

在声明的矩阵内，对每个终端代际，在稳定窗口之后的任何时刻：

1. 无误识别：只有当锚点就是该 provider 的交互式运行时，才出现 `agent`。
2. 无漏识别：存在受支持的交互式运行时，绝不出现 `none`。
3. 关联正确：`agent` 结果指向正确的终端代际、锚点和运行，其绑定的 Agent 会话属于这次运行。
4. 不隐藏失败：`unknown` 总是带有可见原因。在受支持的矩阵单元中，它计入未达标，绝不算作通过。

矩阵之外不承诺完整性，但第 1 条处处成立：任何规则都不得根据在矩阵内会出错的证据给出 `agent`。确认等级表示通过协作式的 shell 与 Host 证据建立了因果关联；它不是针对同一用户下恶意进程的鉴别。

| 维度     | 首批承诺支持范围                                                                             | 后续                                  | 矩阵之外                                              |
| -------- | -------------------------------------------------------------------------------------------- | ------------------------------------- | ----------------------------------------------------- |

## 已核实现状

以下陈述是基准提交上的事实，依据为阅读各行列出的代码和 owner 文档。仍需真实复现的行会注明。

### 证据链

| 阶段       | Owner                     | 行为                                                                                                                                                                                                                                                                                                                                                                                |
| ---------- | ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 采集       | Terminal Host，仅 Windows | 枚举终端的 Job Object，固定每个进程句柄，读取创建时间、映像、父进程、命令行和目录，然后重新枚举。读取命令行需要进程内存读取权限。任何一个进程无法打开或正在退出、成员变化、成员超过 64 个，或超出 250 ms 预算，都会让整个样本失败（`process_query_windows.zig`）                                                                                                                    |
| 识别       | Agent 观测协议            | `identify_agent_process` 接受小写 basename 为 provider 别名的原生映像，其中单独的 `agent` 映射为 Cursor；或者接受受支持的运行时（`node`、`bun`、Python、POSIX shell、PowerShell `-File`），其脚本 basename 是别名或以列出的包路径结尾。只有一组固定的 Letta 打印与格式参数被视为非交互。`select_agent_process` 返回后代包含所有其他候选的最外层已识别进程，其他任何排列都报告为歧义 |
| 观测       | Server，仅为 Windows 编译 | 按有界轮次采样绑定，记录所选锚点的进程标识与创建时间，只在成功样本中找不到它时才发出退出，把歧义当作不存在，在样本失败或没有选中时保留上一次选择，按识别出的 provider 选择屏幕回退规则，并把结果送入 Panel Agent 上报而不是规范 Agent 会话（`process_observation.rs`）                                                                                                              |
| Agent 启动 | 原生 Client，仅 Windows   | 把 provider 的启动名输入空闲的 cmd 或 PowerShell。当绑定到同一 Presentation generation 的 Hook 上报 Agent 会话处于空闲状态或已有结束的轮次，且 3 s 稳定期后进程样本给出所请求的 provider 时，启动完成（`workflow.rs`）                                                                                                                                                              |
| Hook 关联  | Hook 传输与 Server join   | 通过写入控制台的私有关联和 Presentation generation，把每个 Hook 事件与终端关联起来。会话属于哪次运行只由 provider 和时间推断                                                                                                                                                                                                                                                        |
| Desktop    | Electron Client           | 只把 shell preexec 启动标记用作在场提示；没有进程身份                                                                                                                                                                                                                                                                                                                               |

owner 文档已经写明了这一局限。启动预留的候选是 “local observation evidence, not causal authentication of a provider process”，以及 “process recognition does not authenticate a provider or create canonical Agent Sessions”。

矩阵按 Host 采样到的形态列出入口形态。“已识别”表示当前规则返回了正确的 provider；它不说明是否处于交互模式。

| 入口形态                                               | 形态示例                                          | 当前结果                                                                         | 代码证据                                        |
| ------------------------------------------------------ | ------------------------------------------------- | -------------------------------------------------------------------------------- | ----------------------------------------------- |
| 以别名命名的原生映像                                   | `claude.exe`、`codex.exe`、`grok.exe`             | 已识别                                                                           | `native_agent_provider`                         |
| 名称未列出的原生映像                                   | 带版本号或被改名的映像                            | 漏识别                                                                           | `native_agent_basename`                         |
| 其他 provider 提供的名为 `agent` 的原生映像            | 额外安装 `agent` 别名的安装程序                   | 误识别为 Cursor                                                                  | `native_agent_provider`                         |
| 与别名同名的桌面或 IDE 应用                            | `Cursor.exe`、`Kiro.exe`                          | 只要它留在不允许脱离的 Job 中就被误识别；之后启动的真实 Agent 会变成歧义；需复现 | `process_job_windows.c`、`select_agent_process` |
| 以别名命名的运行时脚本                                 | `node <package>/bin/codex.js`                     | 已识别                                                                           | `identify_agent_process`                        |
| 位于已列出包路径的运行时脚本                           | 包后缀表中的条目                                  | 已识别                                                                           | `executable.rs`                                 |
| 位于未列出包路径或捆绑运行时中的运行时脚本             | provider 目录中的 `node.exe index.js`             | 漏识别                                                                           | `executable.rs`                                 |
| 带有固定列表之外选项的运行时                           | 堆大小或警告类别选项                              | 该进程漏识别                                                                     | `entrypoint`                                    |
| 包管理器 shim                                          | 经由 `cmd /c` 的 `.cmd`；在 shell 内执行的 `.ps1` | shim 本身不被识别；其运行时子进程匹配时被识别                                    | `entrypoint`                                    |
| PowerShell 脚本启动                                    | `pwsh -File <script>`                             | 已识别                                                                           | `entrypoint`                                    |
| PowerShell 命令、批处理文件或没有匹配子进程的 `cmd /c` | `pwsh -Command <text>`、`.bat`                    | 漏识别                                                                           | `entrypoint`、`native_agent_basename`           |
| Python 控制台启动器与模块启动                          | `<name>.exe` 启动器；`python -m <module>`         | 启动器按名称识别；模块启动漏识别                                                 | `entrypoint`                                    |
| 版本管理器 shim 映像                                   | 与 provider 同名的 shim                           | 按名称识别，没有来源证明                                                         | `native_agent_provider`                         |
| 命令行不可读                                           | 拒绝内存读取的进程                                | 原生映像不经模式检查即被接受；运行时承载的 Agent 漏识别                          | `process_query_windows.c`、`interactive`        |
| 非交互调用                                             | 版本、帮助、打印、exec、登录、更新和服务器形式    | 除 Letta 参数外都算作交互                                                        | `interactive`                                   |
| 位于终端控制台之外的 Agent                             | 用 `start` 打开到新控制台；脱离的子进程           | 算作本终端的 Agent；需复现                                                       | `process_query_windows.c`                       |
| 远程执行                                               | SSH、WSL 和容器客户端                             | 报告为没有 Agent                                                                 | `identify_agent_process`                        |

macOS 和 Linux 上没有原生进程采样：Host 查询、Server 采样器和 Agent 启动都只支持 Windows，因此上表所有形态都观测不到，只剩 Hook 观测。provider 版本在任何地方都没有记录；两个版本之间的包布局变化会让已识别的行静默变成漏识别。

## 缺口

S1 产生错误的身份或关联。S2 在本应支持的单元中产生漏识别或静默的未知。S3 超出当前能力范围或属于诊断问题。各行按严重程度排序。

| 编号 | 严重程度 | 触发条件                                                                                                         | 当前行为                                                                                                         | 期望行为                                                                                                    |
| ---- | -------- | ---------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| G1   | S1       | 运行了一个名为 `agent` 但不是 Cursor 的二进制，包括其他 provider 的别名                                          | 被识别为 Cursor；为 Cursor 执行 Agent 启动时可能启动这个二进制                                                   | 通用别名需要来源证明；否则给出带 `unverified-provenance` 的 `unknown`，Agent 启动报告 provider 不匹配       |
| G2   | S1       | 从终端启动了一个可执行文件与别名同名的桌面或 IDE 应用                                                            | 它留在 Job 中期间被识别为该 provider；之后启动的真实 Agent 变成歧义，旧结果被保留；需复现                        | 没有挂接到本终端控制台的进程永远不作为候选                                                                  |
| G3   | S1       | 已识别的 provider 以非交互形式运行：版本、帮助、打印、exec、登录、更新或服务器                                   | 除 Letta 外，所有 provider 都算作交互式 Agent；各家参数含义不同（`-p` 对一个 provider 是打印，对另一个是配置档） | 按 provider 的模式分类器：非交互形式给出 `none`；无法分类的形式给出带 `unclassified-arguments` 的 `unknown` |
| G4   | S1       | 无关程序与短别名同名，例如 `amp` 或 `kilo` 编辑器，以及 `hermes` 引擎                                            | 被识别为该 provider                                                                                              | 每个别名都有冲突类别；共享名称需要来源证明                                                                  |
| G5   | S1       | 上一次运行的 Hook 在重启后才到达，或同一终端中两次同 provider 的运行相互重叠                                     | 会话属于哪次运行只由 provider 和时间推断，因此可能挂到错误的运行上                                               | Hook 携带运行令牌；已绑定的会话永不重新绑定                                                                 |
| G6   | S1       | 从本终端启动的 Agent 运行在另一个控制台中                                                                        | 算作本终端的 Agent；需复现                                                                                       | 控制台挂接检查；否则给出带 `detached-console` 的 `unknown`                                                  |
| G7   | S2       | 手动启动：用户输入 Agent 命令                                                                                    | 只靠规则，没有运行边界；由第一个样本决定                                                                         | 稳定窗口过后达到识别等级；之后由托管 PowerShell 补充逐命令的运行边界                                        |
| G8   | S2       | 某个进程因权限或属于其他账户而无法打开、在采样期间退出，或成员发生变化                                           | 整个样本失败；保留上一次选择；看不到退出；不向外暴露任何信息                                                     | 不透明行让样本仍可使用；锚点探测仍报告存活；持续失败时变为带 `sample-failed` 的 `unknown`                   |
| G9   | S2       | Job 中超过 64 个进程，例如在构建和测试工具下                                                                     | 整个样本因超限而失败                                                                                             | 紧凑行提高上限；超过上限时给出带 `sample-limit` 的 `unknown`                                                |
| G10  | S2       | 没有内存读取权限时无法读取命令行                                                                                 | 运行时承载的 Agent 漏识别                                                                                        | 先使用受限权限的命令行查询；否则给出带 `command-line-unreadable` 的 `unknown`                               |
| G11  | S2       | 存在多个互不相关的候选，例如兄弟进程或后台作业                                                                   | 歧义被当作不存在，旧选择被保留                                                                                   | 带 `ambiguous-candidates` 的 `unknown`                                                                      |
| G12  | S2       | 安装形态不在表中：捆绑运行时、未列出的包作用域、`.bat`、PowerShell `-Command`、Python 模块启动、额外的运行时选项 | 漏识别                                                                                                           | 按 provider 安装形态建立注册表条目，每条附带一个样本                                                        |
| G13  | S2       | Agent 启动的目标 provider 的真实进程形态无法识别                                                                 | 完成判断永远看不到进程 provider，一直等到截止时间；需复现                                                        | 回执锚定运行；由携带令牌的 Hook 或注册表核实 provider                                                       |
| G14  | S2       | 退出、重启或启动器交接，即启动器退出而其 provider 子进程继续运行                                                 | 只在成功样本中才看到退出；交接看起来像先退出再启动；没有任何东西区分不同运行                                     | 每个锚点对应一次新运行；交接给同 provider 的后代时保持同一运行；锚点离开或回执结束时退出                    |
| G15  | S2       | provider 新版本改变了名称或包布局                                                                                | 对应行静默变成漏识别                                                                                             | 带核实版本范围的版本化注册表条目，以及每个版本的样本集                                                      |
| G16  | S3       | macOS 和 Linux                                                                                                   | 没有进程路径                                                                                                     | POSIX 采样器；落地之前给出带 `platform` 的 `unsupported`                                                    |
| G17  | S3       | 终端背后的远程执行                                                                                               | 报告为没有 Agent                                                                                                 | 远程客户端是前台程序时给出带 `remote-execution` 的 `unsupported`                                            |
| G18  | S3       | 诊断                                                                                                             | explain 输出和 `panel process-info` 显示事实，但没有结果或原因                                                   | CLI 诊断中给出结果、等级和原因                                                                              |
| G19  | 已覆盖   | 进程标识复用                                                                                                     | 已处理：锚点使用进程标识加创建时间，被复用的父进程会使进程链失效                                                 | 保持，并且绝不通过被复用的标识转移运行                                                                      |

## 推荐设计

### Provider 注册表

- 每个 provider 条目为别名标注冲突类别：唯一、与其他程序共享，或通用。共享和通用别名需要来自条目所列安装根目录或包路径的来源证明。
- 安装形态按平台显式列出：原生映像、包入口、捆绑运行时、启动器包装和 shim。`cmd /c`、PowerShell `-Command`、`.bat` 以及允许的 Python 模块等包装器，解析为它们实际启动的形态，绝不解析为任意参数中提到的名称。
- 每个 provider 的模式分类器依据已核实版本范围内的文档语法，返回交互、非交互或无法分类。不可读的参数绝不默认为交互。
- GUI 子系统的可执行文件永远不作为候选。
- 注册表是由协议 crate 拥有的版本化数据。Server、Client 诊断以及后续的 POSIX 采样器共用它。

### 身份状态

- Server 为每个终端代际维护一个身份状态，输入来自成功样本、锚点探测、回执和携带令牌的 Hook。
- 识别等级的结果要求同一个锚点出现在相隔至少 500 ms 的两个成功样本中；在此之前结果为带 `settling` 的 `unknown`。
- 锚点是该运行最外层的已识别进程。它退出而同 provider 的后代继续运行时，运行交接给该后代；否则运行结束。
- 样本失败时最多保留上一个结果两秒，之后给出带 `sample-failed` 的 `unknown`；若锚点探测证明锚点已经消失，则运行结束。
- Panel Agent 上报、屏幕回退和 Agent 启动都消费这一状态，不再各自解释。

### 受控启动流程

1. Agent 启动照常预留，同时由 Server 生成运行及其令牌。
2. 在托管 PowerShell 中，Client 带运行前缀提交启动命令。包装器剥离前缀并为该命令导出令牌，Host 记录开始标记。
3. 锚点是运行窗口打开期间出现、且不属于任何更早运行的 shell 最外层已识别后代；在注册表识别出这样的进程之前，由最外层的此类后代暂时充当锚点。由注册表或携带令牌的 Hook 核实 provider。
4. 启动结果为已启动、provider 不匹配、带 shell 状态的提前结束、歧义或截止。结束标记或锚点离开会结束运行。
5. 在 cmd 和非托管 shell 中，Agent 启动保持当前的输入式启动，只能达到识别等级。

### 手动输入的运行

手动输入的运行通过注册表和稳定窗口达到识别等级。后续切片让托管 PowerShell 为每条被接受的命令加上各自的令牌和标记，从而在不改变用户输入内容的情况下，为手动运行提供精确边界和精确的 Hook 绑定。cmd 保持识别等级。

### Hook 关联

Hook 传输把从 Agent 进程继承到自身环境中的运行令牌，作为可选的有界信封字段转发。携带令牌的 Hook 在 provider 匹配时把其 Agent 会话绑定到该运行。没有令牌时，会话绑定到同一终端代际中同一 provider 最新的存活运行；存在歧义时不绑定。托管集成需要更新才能转发令牌；较旧的安装保留回退规则。

### 隐私与诊断

命令行和环境变量值只保存在内存中。Host 只读取那个具名令牌变量，绝不读取整个环境。诊断显示结果、等级、原因、锚点身份，以及匹配到的形态，其中参数被归约为分类后的形式，绝不显示原始命令行。

### 验收

- 只有当某个矩阵单元的每个用例在每个列出的 provider 版本上都通过，且没有错误的 `agent`、错误的 `none`、错误的关联，稳定窗口后也没有 `unknown` 时，该单元才进入承诺支持范围。
- 纯规则和选择器用例是这一 Consequential 契约的表驱动回归证据。Host 用例使用受控的 Windows 子进程。真实 provider 运行构成按需执行的样本集，并把经核实的版本范围记录到注册表中。
- 真实验证从不登录、不发送提示词、不消耗付费额度，远程环境使用替身。

## 已记录的默认决定

这些默认决定用于让工作持续推进；每一项都可以单独否决。

1. 100% 目标只覆盖声明的承诺支持矩阵；其他 provider 和形态保持尽力而为。
2. 受支持单元中的 `unknown` 算作失败，并且总是连同原因一起显示。
3. 无法分类的参数给出 `unknown`，而不是交互。
4. 共享和通用别名需要来源证明，因此单独的 `agent` 不再自动表示 Cursor。
5. 稳定窗口为相隔至少 500 ms 的两个成功样本。
6. 受控启动使用托管 PowerShell 回执，cmd 保持识别等级。
7. 会话绑定使用由 Hook 转发的运行令牌，不支持令牌的集成使用最新运行回退规则。
8. 先在 Windows 上达成承诺支持；在 POSIX 采样器落地之前，macOS 和 Linux 报告 `unsupported`。
9. 样本失败时最多保留上一个结果两秒。
10. 本文不与其他产品作比较；外部调研只为方案选项提供了参考。

## 保留决策

- 私有启动器进程或以 Agent 作为根进程的终端（L-C、L-D）会改变已接受的拓扑或产品行为，需要 decision owner 决定。
- TUI 与 GUI 如何呈现身份结果，由各自的呈现 owner 决定。
