# 前端本地化

## 权威性和支持的 Locale

本文档负责前端产品界面的 locale 选择、产品消息编写、翻译目录、格式化、回退和本地化验证。对翻译内容的视觉适配遵循 [`visual-foundations.md`](visual-foundations.md)，包放置遵循 [`package-boundaries.md`](package-boundaries.md)。

Orchbee 发布以下产品 locale：

| Locale  | 语言             | 角色             |
| ------- | ---------------- | ---------------- |
| `en-US` | 英语（美国）     | 源 locale 和回退 |
| `zh-CN` | 简体中文（中国） | 必需的发布翻译   |

严格使用表中所列的规范 BCP 47 locale 标识符。新增或修改面向产品的消息时，在同一个变更中更新两个 locale。运行时回退是韧性机制，不是合并不完整目录的许可。

英文仍然是源码标识符、注释和工程文档的权威语言。本地化消息值是产品资产，不是权威文档，其中应包含对应 locale 的语言。

## Locale 所有权和解析

应用工作区拥有用户 locale 偏好、平台检测、持久化和有效 locale 选择。`@orchbee/i18n` 拥有受支持 locale 契约、locale 规范化、文本方向、格式化运行时、产品消息描述符和所有发布的翻译目录。应用在组合边界把经过验证的 locale 传给该包的 Provider；功能包使用此 Provider，绝不检测宿主 locale。

按以下顺序解析有效 locale：

1. 应用提供了显式用户偏好时，使用该偏好。
2. 有序的操作系统或浏览器语言偏好。
3. `en-US`。

把英语语言变体规范化为 `en-US`。把简体中文变体规范化为 `zh-CN`；不要默默地把繁体中文 locale 映射为简体中文。不受支持或无效的 locale 标识符回退到 `en-US`。

Locale 变更无需重新加载页面即可更新已渲染界面。应用让文档 `lang` 属性与有效 locale 同步，并从 locale 推导 `dir`，而不是假定未来每种语言都从左向右书写。Locale 变更时，不重写现有外部生成的记录和其他历史外部内容。

`@orchbee/i18n` 不读取浏览器或操作系统全局对象，不存储偏好，不修改文档，也不代表应用选择 locale。应用通过该包的纯 locale 契约解析 locale 后，同步文档元数据。

## 包边界和目录所有权

所有 Orchbee 产品工作区都使用 `@orchbee/i18n`；其他工作区不得导入 `react-intl`，也不得拥有产品翻译目录。应用在其组合边界提供有效 locale，功能包使用共享格式化能力，不检测宿主 locale，也不创建另一套消息系统。

每个应用只在具有产品语义的界面上方安装一个本地化 Provider。不要安装功能局部 Provider，不要通过无关组件层传递已翻译字符串，也不要让可复用功能包自行选择 locale。非 React 产品 adapter 使用同一个经过验证的 locale 和同一组目录进行格式化。

所属包的 `README.md` 是导出符号名称和使用方示例的权威来源。本规范拥有跨工作区的目录放置、编写边界、回退和验证规则。

把每个本地化值实际存放在 `packages/i18n/src/locales/<canonical-locale>/<product-domain>.ts` 中。Locale 目录名使用规范 BCP 47 标识符及其规范大小写，并镜像相同的产品领域文件名。绝不能在同一个文件中编写英文和翻译后的产品文案：`locales/en-US/` 只包含英文值，`locales/zh-CN/` 只包含简体中文值。新增、删除或移动消息时，在同一个变更中更新每个发布 locale 对应的领域文件。

在 `packages/i18n/src/descriptors/` 下按相同的稳定产品领域对导出的描述符分组，并把每组导出为 `<domain>Messages`。描述符的英文 `defaultMessage` 引用 `en-US` 领域目录中的对应值，不重复编写文案。稳定 ID 和英文翻译者说明属于源码元数据，而不是本地化值。为每个发布 locale 组合一份完整运行时目录；新增领域不会创建另一个 Provider 或 locale 契约。

## 产品消息边界

本地化 Orchbee 为产品界面编写的每条消息，包括：

- 可见的标题、描述、标签、按钮、菜单、tooltip、placeholder 和空状态。
- 加载、验证、确认、错误、状态和通知消息。
- 仅用于无障碍的名称和描述，包括 `aria-label`、`title`、`alt` 和视觉隐藏文本。
- 在另一个内容表面内渲染、由产品编写的新手引导或指导。

不要翻译用户编写的值、条目名称、文件路径、命令、源码、协议标识符、日志，也不要翻译由外部进程或工具生成的输出。当存在产品术语表时，产品名称和批准的技术术语按术语表保持不变。

内部异常和边界错误携带稳定代码和结构化值，而不是本地化句子。产品界面把预期错误代码映射到本地化消息。意外错误显示一条本地化通用消息；原始异常文本可以通过有明确所有者的诊断通道记录，但不得作为产品文案显示。

通用 UI primitive 包不选择产品 locale，也不拥有具有产品语义的消息。需要面向使用方的可见文本或仅无障碍文本的 primitive 应公开该文本，让使用方提供。在带有上游固定语言默认值的注册表 primitive 进入产品界面前，先调整它，使具有产品语义的使用方可以提供本地化文本。

## 消息标识符和语法

使用描述所属领域和用途的稳定语义标识符：

```text
navigation.actions.open
navigation.emptyState.title
```

不要使用英文句子作为标识符，不要在标识符中编码 locale，也不要仅仅因为当前英文文本相同就复用泛化消息。当位置、语气或变量含义并非不言自明时，消息描述符应包含翻译者上下文。

把一段完整、可翻译的意思写成一条消息。不要拼接翻译片段，不要手工选择单数和复数字符串，也不要假设另一种语言会保留英语词序。当语法或格式随 locale 变化时，使用 `{itemTitle}` 等具名变量和 ICU MessageFormat 的 `plural`、`select`、数字、日期及时间参数。

翻译中不包含任意 HTML。富文本使用由应用控制的具名 placeholder，其 React 元素由调用方提供。绝不能通过 `dangerouslySetInnerHTML` 渲染翻译后的标记。

## 运行时实现

消息格式化使用 ICU MessageFormat。英文源消息位于 `locales/en-US/` 目录，简体中文消息位于 `locales/zh-CN/` 目录，每个 locale 都提供一份由相同稳定标识符作为 key 的完整目录。带类型的描述符引用英文目录值作为默认值，使回退和源 locale 格式化共享唯一一份编写的英文值。功能代码格式化导出的描述符，而不是直接渲染面向产品的字符串字面量。

运行时回退遵循一条路径：locale 协商回退到 `en-US`，缺失的翻译消息回退到其英文描述符默认值，无效或缺失的描述符属于开发错误。回退行为只用于韧性；目录完整性仍然是合并要求。

对数字、列表、日期、时间、相对时间和显示名称使用 locale 感知的格式化工具。存储和传输时间戳、数值等 locale 中立值；只在展示边界使用有效 locale 格式化，并在含义依赖时区时显式指定时区。

## 布局和交互

产品布局在不缩小字体的情况下支持每个发布的 locale。控件和行使用固有尺寸或 `min-height`，让翻译后的标签和描述可以换行。不要使用由一个英文标签推导的固定宽度，不要只在 placeholder 中放置必需文案，也不要把文本编码进图片。

当用户数据的完整值仍可访问时，可以截断用户数据。不要仅仅为了保持固定组合而截断必需的操作标签、错误或说明。在两个发布的 locale 中审查键盘访问、焦点顺序、换行和无障碍名称。

## 验证

本地化变更满足以下所有检查：

1. 源描述符和每个发布的翻译目录包含相同的消息 ID。
2. 每个 locale 的 ICU 语法都可解析，对应消息使用兼容变量。
3. Locale 解析覆盖精确匹配、受支持的语言变体、无效输入、不受支持的语言和繁体中文回退。
4. 具有代表性的产品界面在 `en-US` 和 `zh-CN` 下均可渲染。
5. 产品审查会在变更的界面代码中搜索可见和仅无障碍的原始字符串。
6. Storybook 和视觉审查针对受影响组件检验翻译扩展、换行、缩放和窄布局。
7. 仓库 `pnpm verify` 门禁通过。

在无关测试中，优先断言行为和消息身份，而不是重复偶然的英文文案。当 locale 选择、插值或文案本身就是受测行为时，断言准确的翻译输出。
