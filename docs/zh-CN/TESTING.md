# 测试

## 源码和测试路径

`orchbee/filename-naming-convention` 强制执行：

| 产物                    | 命名契约                                                                                                                                                  |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 源码目录                | 使用 kebab-case。                                                                                                                                         |
| `locales/` 的直接子目录 | 使用规范 BCP 47 标识符和大小写，例如 `en-US` 或 `zh-CN`。                                                                                                 |
| 唯一运行时身份          | 只计算具名运行时导出；仅类型导出和私有实现符号不改变公共身份。                                                                                            |
| 自有函数模块            | 唯一具名运行时导出是本地定义的函数时，使用精确的 camelCase 符号，例如 `formatDisplayLabel.ts`。                                                           |
| 自有类模块              | 唯一具名运行时导出是本地定义的类时，使用精确的 PascalCase 符号，例如 `EventEmitter.ts`。                                                                  |
| 通用模块                | 成组操作、契约、数据目录、常量、重新导出门面及其他没有唯一可调用或可构造身份的模块，使用按职责命名的 kebab-case。                                         |
| 生成的源码              | 保留由生成器拥有的 kebab-case 名称。                                                                                                                      |
| 自有函数组件            | 使用唯一运行时导出的精确 PascalCase 名称，例如 `FilterPanel.tsx`。                                                                                        |
| 自有专用 Hook           | 使用唯一 Hook 导出的精确 camelCase 名称，例如 `useFilterPanel.ts`。                                                                                       |
| 非组件 TSX 入口         | 使用 kebab-case。                                                                                                                                         |
| 单元测试                | 使用所属模块的 `__tests__` 目录以及 `.unit.test.ts` 或 `.unit.test.tsx` 后缀。伴随测试保留源码 stem；覆盖多个实现文件的测试套件使用 kebab-case 行为名称。 |

## 必需的单元测试

所有自有语言的测试义务都由行为、不变量和风险决定。实现文件与测试文件之间没有一一对应要求。
只拆分或移动实现而不改变行为，不会产生新的测试义务。

新增测试前，先为变化的主张选择证据。已有行为测试、编译器或契约检查，以及适当的集成或
视觉证据可能已经覆盖它。只有存在有意义的缺口时才新增或加强自动化用例；验证义务不等于
新增单测文件。算法、状态转换、持久化、协议兼容和恢复仍须为相关决策与失败模式提供自动化证据。

| 范围               | 契约                                                                                                                     |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------ |
| 领域行为           | 在能够判断它们的最低层覆盖决策、状态转换、边界输入、预期失败和所属不变量。                                               |
| 内聚模块           | 一个行为测试套件可以覆盖多个实现文件。通过位置、导入和面向行为的测试名称保持归属可发现；映射不明显时使用已有的所属契约。 |
| 薄投影或装配       | 复用能够发现连接损坏的已有行为或集成测试。不要仅为断言导出存在、函数类型、复制的常量或实现自身的公式而添加伴随测试。     |
| `.tsx` 源码        | 为有意义的回归、交互、无障碍契约或集成边界添加测试；准备好的 props 和静态标记本身不要求测试。                            |
| 检入的 shadcn 快照 | 测试 Orchbee 适配、公共包契约和所依赖的行为，不要复制上游套件或要求每个生成文件对应一项测试。                            |

对每个新增或实质变更的测试，说明它能发现的真实缺陷。文件存在、断言数量和覆盖率百分比都
不能证明这种价值。结合变更主张评审此义务；文件名 lint 只约束命名与放置。
期望结果应来自需求、不变量或独立参考。不要把生产算法复制进断言，也不要仅为匹配新输出而
更新期望值。共享套件时保持现有可见性边界；测试便利不能成为导入其他所有者私有实现的理由。

合并重复用例，把只绑定私有实现的断言替换为可观察行为检查。所约束的行为已经退役时，删除
过时用例。保留当前独有的行为、失败和边界证据，并指出保留的检查；测试慢或失败本身不代表
它已过时。不要仅为满足可发现性而保留占位伴随测试，或创建第二份逐文件覆盖清单。

## 测试层次与成本

| 层次         | 证据与执行成本                                                                                                             |
| ------------ | -------------------------------------------------------------------------------------------------------------------------- |
| 确定性核心   | 通过显式输入、时钟和能力验证组合、边界及转换序列；主张不需要时，不启动浏览器、进程或服务。                                 |
| 适配器或组件 | 检查转换、交互、清理和所属外部能力；使用最小且忠实的环境。纯 TypeScript 逻辑使用 Node 环境，依赖 DOM 的行为使用 DOM 环境。 |
| 进程或系统   | 证明真实启动、IPC、PTY、操作系统和关闭行为。保留这些主张所需的跨进程用例；避免在每条启动路径中重复完整的核心决策矩阵。     |

按这些层次评估新增和变更的套件。测试的文件名或 runner target 不会把真实进程或文件系统
工作变成廉价单测。共享 fixture 可以复用不可变准备结果，但每个测试拥有自己的可变状态和
清理职责；fixture 复用不得让结果依赖执行顺序。

- 优先使用可观察完成信号和可控时间，而不是无条件 sleep。主张涉及操作系统截止时间时使用
  真实经过时间，并保留有依据的上界。
- 说明串行化或并发上限为何必要，以及它保护的资源。更多 worker 不一定缩短经过时间；
  不要仅为更快通过而移除隔离、锁或截止时间。
- 将实际经过时间与编译、模块加载、环境初始化和测试主体时间分开测量。并行 worker 的累计
  时间不能相加作为实际经过时间。声明性能改进前，对比等价输入、机器负载和冷、热缓存。
- 为核心测试和昂贵边界测试维护实用的聚焦命令。完整门禁范围、受影响测试选择以及必需检查
  的变更仍由[验证](VERIFICATION.md)约束；测试慢不代表可以跳过必需证据。

## 测试执行

- `vitest/expect-expect`：每个测试都必须包含断言。
- `vitest/no-disabled-tests`：不要提交被跳过的测试。
- `vitest/no-focused-tests`：不要提交聚焦测试。
- `vitest/no-identical-title`：同一测试套件中的测试标题必须唯一。

## 类型错误测试

测试可以使用 `@ts-expect-error`，但必须附带至少十个字符的说明；`@ts-ignore` 和 `@ts-nocheck` 仍然禁用。

测试中允许为平台 Mock 和有意无效的边界输入使用类型断言；`any`、`oxlint-disable` 和 `eslint-disable` 仍然禁用。

测试局部辅助函数可以依赖推断的返回类型。

```ts
// ❌
// @ts-ignore
acceptsOnlyStrings(1);

// ✅
// @ts-expect-error -- 验证数字会被拒绝
acceptsOnlyStrings(1);
```

## 回归覆盖

对于可自动化的行为缺陷，新增或加强一项修复前失败、修复后通过的回归用例。如果能证明
已有失败测试、编译器检查或契约检查的失败及修复效果，它们可以提供该证据；不要在另一层重复。

对于稳定自动化检查无法忠实判断的视觉或环境相关缺陷，使用受控的视觉、集成或复现检查。
在现有审查记录中说明观察到的失败、检查结果、环境和自动化限制。可分离的领域决策仍由
自动化测试保护。困难、成本或作者信心本身，不能免除状态、数据完整性、协议、安全或恢复
主张的自动化要求。

## 本地化契约

产品消息变更要保持源描述符和每个发布的目录完整，验证 ICU 语法和变量，并在 `en-US` 和 `zh-CN` 下渲染具有代表性的行为。Locale 协商测试应覆盖受支持的变体、无效输入、不受支持的语言和繁体中文回退。权威的消息和视觉审查要求位于 [`docs/frontend/localization.md`](frontend/localization.md#验证)。

## 原生应用测试

- 把 Rust unit-test body 放在相邻 test-module 文件或 crate 的 `tests/` 树中，只从 production
  source 暴露窄化 conditional module 声明，并通过根 test 门禁运行每个 Cargo member。Rust
  专属布局和 failure-boundary 规则以 [`docs/RUST.md`](RUST.md#测试) 为权威。
- 把所有 Zig 测试和测试专用 helper 放在所属源码树的 `__tests__` 目录下，并通过应用的非交互式 `test` 脚本公开每个测试根节点。Zig 专属布局、命名和白盒访问的权威来源是 [`docs/ZIG.md`](ZIG.md#测试)。
- 通过 `test:cross` 编译每个维护的操作系统系列；绝不能仅凭交叉编译就声明运行时、ABI、PTY、IPC、打包或安装器行为。
- 在声明某项平台行为受支持前，在其原生操作系统上运行行为和集成测试。
- 固定必需测试使用的每个原生 dependency resolution 和 compiler input；机器本地的同级
  checkout 和可变 revision 不是测试 fixture。

## 包契约

库包在 `build` 后运行 `test:exports`，以验证打包后的公共表面、两种 JavaScript 模块格式和严格的外部 TypeScript 使用方。跨包行为应放在面向使用方的契约测试中，而不是放在导入其他包私有源码的测试中。
