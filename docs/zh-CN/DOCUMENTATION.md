# 文档

## 权威性

| 产物                             | 受众              | 职责                                         |
| -------------------------------- | ----------------- | -------------------------------------------- |
| `README.md`、`README.zh-CN.md`   | 用户              | 同步的项目价值、能力、安装和首次使用说明     |
| 包 `README.md`                   | 包使用方          | 公共包能力、API、安装和用法                  |
| `packages/*/docs/**/*.md`        | 包维护者          | 当前包所拥有的行为、内部架构、集成和维护参考 |
| `CLAUDE.md`                      | AI Agent          | 简短项目地图、硬性规则和权威规范链接         |
| `docs/**/*.md`，排除 locale 子树 | 维护者和 AI Agent | 权威的仓库级工程规范和跨工作区架构契约       |
| `docs/zh-CN/**/*.md`             | 中文维护者        | 英文规范的完整同步翻译，绝非独立权威来源     |
| `proposals/**/*.md`              | 决策参与者        | 正在审查的未来设计，绝非当前权威来源         |
| `research/**/*.md`               | 维护者和 AI Agent | 有时间边界的证据和开放调查，绝非权威来源     |
| Lint 诊断                        | 执行中的 AI Agent | 违规项、纠正操作和权威英文规范链接           |

权威性跟随所有权。仓库规范可以约束每个包，但不拥有任何包的行为。包 README 或包本地参考可以描述
该包，但不会为无关工作区创建规则。

## 规范准入

只有当一份文档中的规则或架构决策治理仓库运作、多个工作区或工作区之间的边界时，它才属于
`docs/`。规范陈述可复用决策及其验证方式；它不盘点某一个包的实现。

- 把公共包 API 和使用方用法放在所属包的 `README.md` 中。
- 把包所拥有的行为、源码架构、外部集成事实和维护流程放在 `packages/<package>/docs/` 中。
- 把产品交互模型、界面组合、具名组件行为和其他业务决策放在拥有它们的产品或包中。
- 把未实现的架构、产品行为、包拓扑和迁移计划放在 `proposals/` 下；绝不能把它们呈现为
  当前规范。
- 把有时间边界的证据和未解决发现放在 `research/` 下。
- 把当前工作区身份、职责、运行时、稳定性和非目标保存在各工作区的 `project.json` 中；
  不要在规范中重复维护一份手工工作区目录。

只有当具体路径、包、命令、配置键或规则 ID 是应用或验证跨仓库规则所必需时，规范才可以
指名它。指名一个实现并不会让其业务行为、源码树或路线图获得规范准入资格。

## Agent 上下文契约

- 每个文件只服务于一类 Agent 任务，每个 H2 小节独立回答一个可检索的问题。
- 让检索到的小节无需周边对话也能被理解；显式命名主题、约束和前置条件。
- 把必需操作和约束放在理由之前；只有理由会改变后续决策时才包含它。
- 在执行或验证所属文档需要时，使用准确且可搜索的标识符。
- 保持概览文档浅层，并链接到拥有细节的权威来源，让 Agent 能够渐进加载上下文。
- 删除不会改变 Agent 决策或执行的历史、重复和评论性内容。

## 文档类别

| 类别       | 位置和名称                                | 内容                                           |
| ---------- | ----------------------------------------- | ---------------------------------------------- |
| 仓库规范   | `docs/UPPER-KEBAB-CASE.md`                | 当前仓库级规则和跨工作区架构                   |
| 领域规范   | `docs/<engineering-domain>/kebab-case.md` | 一个工程学科当前的跨工作区规则                 |
| 本地化规范 | `docs/zh-CN/<same-standard-path>`         | 英文规范的完整简体中文翻译                     |
| 包指南     | `packages/*/README.md`                    | 公共包能力、API、安装和用法                    |
| 包参考     | `packages/*/docs/kebab-case.md`           | 当前包所拥有的行为、架构、集成或维护信息       |
| 提案       | `proposals/<owner>/kebab-case.md`         | 有明确状态和所有者的未来决策，绝非当前权威来源 |
| 研究       | `research/<domain>/kebab-case.md`         | 有时间边界的调查、证据和未解决发现             |

只有仓库规范和领域规范属于 `docs/`。目录名称不会把包参考或产品决策变成规范。

## 文档本地化

- `docs/` 下排除 locale 子树的英文规范是工程权威来源。运行时配置、Schema、lint 诊断、`CLAUDE.md` 和其他仓库契约都链接到这些英文规范。
- `docs/zh-CN/` 只用于完整的简体中文镜像。位于 `docs/<path>` 的英文规范必须精确映射到 `docs/zh-CN/<path>`，保留 `docs/` 之后的路径和文件名。
- 保持规范镜像完整。`docs/` 下的每个权威 Markdown 文件都必须在 `docs/zh-CN/` 下有且只有一个对应文件；不允许 locale 只覆盖部分规范。
- 任一规范树中的每次新增、删除、移动、标题或章节变更、示例、命令、链接和内容变更，都必须在同一个变更中更新其对应文件。两种版本在含义、覆盖范围或结构上仍有差异时，变更尚未完成。
- 翻译所有文字，不得添加、省略或弱化规则。保留准确的标识符、路径、命令、配置键、规则 ID 和代码语义。两个版本发生冲突时以英文为准。
- `pnpm test:lint-rules` 验证规范文件一一对应、结构标记、内联代码标识符、本地化链接、规范目录准入和具体工作区引用。人工审查仍负责验证翻译语义忠实和文档分类正确。
- 包本地参考、提案和研究保持为权威英文工程资料，不在 `docs/zh-CN/` 下创建文件。当受众需要时，面向用户的包指南可以添加自己的 locale 后缀 README。

## 提案生命周期

- 把未来决策保存在 `proposals/<owner>/` 下；绝不能把提案作为当前工程权威来源引用。
- 每份提案以 `Status`、`Owner` 和 `Exit condition` 元数据开头。
- 说明提议的变更、当前约束、替代方案、后果以及接受前所需的验证。
- 提案被接受并实现后，只把仓库级规则提升到 `docs/`；把包行为提升到所属包 README、包参考、代码或测试。
- 当决策已由当前权威来源完整表达时删除提案。Git 历史会保留讨论。

## 研究生命周期

- 把调查保存在 `research/<domain>/` 下；未经重新验证，绝不能把研究用作权威来源。
- 每个研究文件以 `Status`、`Last verified` 和 `Exit condition` 元数据开头。
- 把稳定结论提升到拥有它的权威来源：仓库规范、包指南、包参考、代码、配置、测试或已跟踪决策。
- 达到退出条件时删除研究文件；如果以后需要，Git 历史会保留调查记录。
- 研究的依赖、上游来源或实现发生变化后，在使用活跃研究前重新验证它。

## 目录契约

- `docs/` 根目录只保留 `CLAUDE.md` 索引的跨项目规范；根规范文件名使用大写 kebab case。
- 只有当一个稳定工程学科的规范适用于工作区边界时，才在 `docs/` 下使用领域目录。新增规范领域目录需要明确审查和 lint 契约准入。
- 绝不能把 `docs/<product>/` 或 `docs/<package>/` 用作某一个所有者行为的存储位置。使用所属的 `packages/*/README.md`、`packages/*/docs/`、`proposals/` 或 `research/` 位置。
- 为完整本地化规范镜像保留 `docs/zh-CN/` 等 BCP 47 locale 目录；不要把 locale 标识符用作产品或工程领域名称。
- 优先按所有者组织包参考、提案和研究，并在目录变成混杂的扁平列表之前添加更深的子领域。
- 不要使用 `misc/`、`notes/`、`general/` 或 `shared/` 等兜底目录。
- 当聚焦目录中的文件名能够清晰表达内容时，不需要索引文件。

```text
docs/
  ARCHITECTURE.md
  frontend/
    react.md
packages/
  <package>/
    README.md
    docs/
      maintenance.md
proposals/
  <owner>/
    capability-change.md
research/
  <domain>/
    compatibility-analysis.md
```

## 文件契约

- 按独立职责、权威来源或受众拆分文件，不要按任意行数拆分。
- 使用一个命名主题的 H1；如果第一节可以立即开始，就省略介绍、总结和目录。
- 先放当前契约，再放理由、例外和验证。
- 面向公众的产品语言放在项目或包 README 中，包实现指导放在包本地参考中，`docs/` 只放仓库规范。
- 不要创建 `notes.md`、`misc.md` 或 `todo.md` 等泛化文件。

## 内容契约

- 每项事实或规则只设一个权威章节；链接到它，不要在规范和包参考中重复。
- 把规范写成可复用约束。不要包含包源码树清单、具名产品组件目录、当前界面尺寸、产品路线图或已完成任务叙述。
- 映射使用表格，独立规则使用列表，必要理由使用散文，只有语法会改变含义时才使用代码。
- 命令以仓库根目录为工作目录；如果工作目录不同，要明确说明。
- 对照主要来源验证具有时效性的外部事实，并把它们保存在所属包参考或活跃研究中，而不是仓库规范中。
- 删除或重新分类无法验证的指导，不要把它呈现为当前权威来源。

## 规则和示例

- 由 lint 或编译器强制执行的规则使用准确的规则或选项名称，随后用一句话描述合规状态。
- 如果只有文字可能引起误解，没有机器强制执行的规则应包含一个最小错误示例和正确示例。
- 除非应用规则必须使用真实标识符，否则示例使用中性占位符或通用符号。示例绝不会变成产品清单或未来承诺。
- 示例只包含揭示差异所需的行，并且必须对当前项目技术栈保持有效。

```text
❌ 把一个包的当前组件树复制到仓库规范中。
✅ 记录可复用组件边界，把具体源码树留给所属包。
```

## 链接和锚点

- 使用仓库相对 Markdown 链接，并在存在权威章节时指向该章节。
- 代码、工具和诊断指向拥有跨仓库规则的英文仓库规范；包行为和维护链接指向所属包指南或参考。
- 中文镜像内的链接可以留在 `docs/zh-CN/` 中，以支持本地化规范导航。其他工程权威来源绝不能把本地化镜像视为独立来源。
- 保持标题唯一且稳定，因为 Markdown 锚点是文档 API 的一部分。
- 标题或文件移动时，在同一个变更中更新每条链接、lint 诊断、脚本输入和包指南。
- 只有在外部来源仍然具有权威性时才链接它；在正确的本地权威来源中记录项目决策。

## Lint 与文档契约

| 组成部分       | 要求                                                |
| -------------- | --------------------------------------------------- |
| 规范路径       | `docs/` 下只准入经过审查的根规范和工程领域目录      |
| 具体工作区引用 | 当前规范只引用已有工作区；未来拓扑放入 `proposals/` |
| 本地化镜像     | 保持文件覆盖、结构、内联标识符和链接同步            |
| 显式规则 ID    | 在其权威规范章节中使用准确的已配置 ID               |
| 自定义诊断     | 说明操作、违反的约束和仓库相对 `path#anchor`        |
| 变更           | 同时更新规则实现、配置、规范、本地化镜像和规则测试  |

```text
❌ 无效测试文件。
✅ 把单元测试 "parser.test.ts" 重命名为 "parser.unit.test.ts"。参见 docs/TESTING.md#source-and-test-paths。
```

## 变更检查清单

- 编写前先分类内容：仓库规范、包指南、包参考、提案或研究。
- 确认当前规范指名的每个具体工作区都已存在；只在提案中描述未来拓扑。
- 重命名或移动内容前，搜索旧术语、路径、标题、规则 ID 和脚本输入。
- 验证每个变更的规范都在同一个变更中拥有同步的本地化对应文件。
- 验证命令和示例；不要记录未成功运行的命令。
- 修改工程契约文档后，运行格式化、lint、类型检查和相关测试。
