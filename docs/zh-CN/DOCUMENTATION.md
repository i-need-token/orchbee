# 文档

## 权威性

| 产物                             | 受众              | 职责                                     |
| -------------------------------- | ----------------- | ---------------------------------------- |
| `README.md`、`README.zh-CN.md`   | 用户              | 同步的项目价值、能力、安装和首次使用说明 |
| 包 `README.md`                   | 包使用方          | 公共 API 和包专属用法                    |
| `CLAUDE.md`                      | AI Agent          | 简短项目地图、硬性规则和权威规范链接     |
| `docs/**/*.md`，排除 locale 子树 | 维护者和 AI Agent | 权威英文架构、工程规则和操作契约         |
| `docs/zh-CN/**/*.md`             | 中文维护者        | 英文文档的完整同步翻译，绝非独立权威来源 |
| `research/*.md`                  | 维护者和 AI Agent | 有时间边界的证据和开放调查，绝非权威来源 |
| Lint 诊断                        | 执行中的 AI Agent | 违规项、纠正操作和权威英文文档链接       |

## Agent 上下文契约

- 每个文件只服务于一类 Agent 任务，每个 H2 小节独立回答一个可检索的问题。
- 让检索到的小节无需周边对话也能被理解；显式命名主题、约束和前置条件。
- 把必需操作和约束放在理由之前；只有理由会改变后续决策时才包含它。
- 使用路径、命令、包名、配置键和规则 ID 等准确且可搜索的标识符。
- 保持概览文档浅层，并链接到聚焦的详细内容，让 Agent 能够渐进加载上下文。
- 删除不会改变 Agent 决策或执行的历史、重复和评论性内容。

## 文档类别

| 类别       | 位置和名称                              | 内容                               |
| ---------- | --------------------------------------- | ---------------------------------- |
| 项目契约   | `docs/UPPER-KEBAB-CASE.md`              | 当前跨项目规则和架构               |
| 聚焦参考   | `docs/<domain>/kebab-case.md`           | 当前子系统行为、API 或外部集成事实 |
| 提案       | `docs/proposals/<domain>/kebab-case.md` | 尚不具有权威性的未来设计           |
| 本地化镜像 | `docs/zh-CN/<same-source-path>`         | 英文文档的完整简体中文翻译         |
| 研究       | `research/<domain>/kebab-case.md`       | 有时间边界的调查、证据和未解决发现 |
| 包指南     | `packages/*/README.md`                  | 公共包 API、安装和用法             |

活跃文档默认描述当前事实；提案以 `> Status: Draft` 开头，并在解决后合并到权威文档中或删除。

## 文档本地化

- `docs/` 下排除 locale 子树的文件是权威英文文档。运行时行为、配置、Schema、lint 诊断、包指南、`CLAUDE.md` 和其他工程契约必须使用这些英文文件。只有本地化导航和镜像完整性验证可以访问 `docs/zh-CN/`，二者都不得把它视为独立权威来源。
- `docs/zh-CN/` 只用于完整的简体中文镜像。位于 `docs/<path>` 的英文源必须精确映射到 `docs/zh-CN/<path>`，保留 `docs/` 之后的路径和文件名。
- 保持镜像完整。`docs/` 下的每个权威 Markdown 文件都必须在 `docs/zh-CN/` 下有且只有一个对应文件；不允许 locale 只覆盖部分文档。
- 任一文档树中的每次新增、删除、移动、标题或章节变更、示例、命令、链接和内容变更，都必须在同一个变更中更新其对应文件。两种版本在含义、覆盖范围或结构上仍有差异时，变更尚未完成。
- 翻译所有文字，不得添加、省略或弱化规则。保留准确的标识符、路径、命令、配置键、规则 ID 和代码语义。两个版本发生冲突时以英文为准。
- `pnpm test:lint-rules` 验证文件一一对应、结构标记、内联代码标识符和本地化链接。审查者负责验证翻译含义保持完整和忠实。
- 根级本地化项目文档继续使用 `README.zh-CN.md` 等 locale 后缀文件；`docs/` 内的文档使用 `docs/zh-CN/` 等保留的 locale 子树。

## 研究生命周期

- 把调查保存在 `research/<domain>/` 下；未经重新验证，绝不能把研究用作权威来源。
- 每个研究文件以 `Status`、`Last verified` 和 `Exit condition` 元数据开头。
- 把稳定结论提升到受影响的权威文档、代码、配置或已跟踪工作项中。
- 达到退出条件时删除研究文件；如果以后需要，Git 历史会保留调查记录。
- 研究的依赖、上游来源或实现发生变化后，在使用活跃研究前重新验证它。

## 目录契约

- `docs/` 根目录只保留 `CLAUDE.md` 索引的跨项目契约。
- 为完整本地化镜像保留 `docs/zh-CN/` 等 BCP 47 locale 目录；不要把 locale 标识符用作产品或工程领域名称。
- 其他所有文档从首个版本开始就放在稳定的领域目录下，例如 `docs/terminal/`、`docs/agents/` 或 `docs/security/`。
- 优先按产品或工程领域分组，再按文档类型分组；只有为了区分未来设计和当前事实时才使用 `docs/proposals/<domain>/`。
- 在领域目录变成混杂的扁平列表之前添加更深的子领域；不要等到目录已经拥挤才处理。
- 不要使用 `misc/`、`notes/`、`general/` 或 `shared/` 等兜底目录。
- 当领域目录中的文件名能够清晰表达内容时，不需要索引文件。

```text
docs/
  ARCHITECTURE.md
  CODESTYLE.md
  terminal/
    ghostty-wasm-api.md
  proposals/
    terminal/
      renderer-recovery.md
research/
  terminal/
    surface-gap-analysis.md
```

## 文件契约

- 按独立职责或受众拆分文件，不要按任意行数拆分。
- 使用一个命名主题的 H1；如果第一节可以立即开始，就省略介绍、总结和目录。
- 先放当前契约，再放理由、例外和验证。
- 面向公众的产品语言放在 README 中，实现指导放在 `docs/` 中。
- 不要创建 `notes.md`、`misc.md` 或 `todo.md` 等泛化文件。

## 内容契约

- 每项事实或规则只设一个权威章节；链接到它，不要复制。
- 映射使用表格，独立规则使用列表，必要理由使用散文，只有语法会改变含义时才使用代码。
- 在 `docs/` 的 locale 子树之外以英文编写权威文档，并在 `docs/zh-CN/` 中维护其完全同步的翻译。
- 命令以仓库根目录为工作目录；如果工作目录不同，要明确说明。
- 对照主要来源验证具有时效性的外部事实；当事实可能过期时，记录来源和验证日期。
- 删除或重新分类无法验证的指导，不要把它呈现为当前事实。

## 规则和示例

- 由 lint 或编译器强制执行的规则使用准确的规则或选项名称，随后用一句话描述合规状态。
- 如果只有文字可能引起误解，没有机器强制执行的规则应包含一个最小错误示例和正确示例。
- 示例只包含揭示差异所需的行，并且必须对当前项目技术栈保持有效。

```text
❌ 运行检查。
✅ 从仓库根目录运行 `pnpm typecheck`。
```

## 链接和锚点

- 使用仓库相对 Markdown 链接，并在存在权威章节时指向该章节。
- 每个代码、工具、诊断和工程契约链接都指向英文 `docs/` 目标。中文镜像内部的链接可以留在 `docs/zh-CN/` 中，以支持本地化导航。
- 保持标题唯一且稳定，因为 Markdown 锚点是文档 API 的一部分。
- 标题或文件移动时，在同一个变更中更新每条链接和 lint 诊断。
- 只有在外部来源仍然具有权威性时才链接它；在本地记录项目决策。

## Lint 与文档契约

| 组成部分    | 要求                                         |
| ----------- | -------------------------------------------- |
| 显式规则 ID | 在其权威文档章节中使用准确的已配置 ID        |
| 自定义诊断  | 说明操作、违反的约束和仓库相对 `path#anchor` |
| 文档        | 描述合规状态，不重复诊断实现                 |
| 变更        | 同时更新规则实现、配置、文档和规则测试       |

```text
❌ 无效测试文件。
✅ 把单元测试 "terminal.test.ts" 重命名为 "terminal.unit.test.ts"。参见 docs/TESTING.md#source-and-test-paths。
```

## 变更检查清单

- 重命名或删除内容前，搜索旧术语、路径、标题和规则 ID。
- 验证每个变更的文档文件都在同一个变更中拥有同步的对应文件。
- 验证命令和示例；不要记录未成功运行的命令。
- 修改工程契约文档后，运行格式化、lint、类型检查和相关测试。
