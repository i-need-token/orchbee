# 功能开发

## 建模门禁

在功能模型以可审查的形式回答以下问题之前，不得开始生产集成。所需产物可以是提案、所属包参考、公共包契约、类型加测试，或它们的组合；不要创建没有长期所有者的一次性任务文档。

| 问题             | 必需答案                                     |
| ---------------- | -------------------------------------------- |
| 要解决什么问题？ | 参与者、上下文、期望结果、约束和明确的非目标 |
| 输出是什么？     | 可观察结果、语义事件、失败、取消和无操作行为 |
| 数据结构是什么？ | 实体、标识符、关系、所有权、生命周期和不变量 |
| 状态如何流转？   | 状态、事件、守卫条件、转换、派生状态和副作用 |
| 能否先测试核心？ | 不依赖生产 UI 的场景矩阵和确定性测试         |

当行为协调多个状态、拥有排序或分组、跨越持久化或进程边界、包含异步工作，或解释多步骤用户手势时，必须通过建模门禁。如果一个局部展示变更没有引入新的领域状态或转换，它可以把模型保存在现有组件契约和测试中。

- 在决策被接受之前，把未来行为放在 `proposals/` 下。
- 把当前公共行为放在所属包 README 中，把当前内部维护契约放在所属包参考中。
- `docs/` 只存放可复用的跨工作区规则；仓库规范不得盘点某个功能的状态或界面行为。

## 建模记录

在生产实现之前，在将长期拥有该决策的权威来源中创建一份紧凑的建模记录。使用具体的领域名称和类型完成它；只有标题而没有决策，不能通过门禁。

| 字段     | 必需内容                                       | 完成证据                   |
| -------- | ---------------------------------------------- | -------------------------- |
| 问题     | 参与者、触发条件、期望结果、约束和非目标       | 一条可观察的问题陈述       |
| 输入     | 可信与不可信输入，以及缺失语义                 | 具名输入类型和验证边界     |
| 输出     | 成功变体、失败、事件、副作用、取消和无操作     | 具名输出类型               |
| 不变量   | 每次操作前后都必须保持为真的事实               | 断言或不变量测试           |
| 决策     | 会改变结果的独立维度                           | 决策表或场景矩阵           |
| 模型形态 | 提取器、规范化器、策略、构建器、状态机或工作流 | 一个有理由的选定形态       |
| 依赖     | 时间、存储、网络、进程、DOM 和其他能力         | 最小能力接口               |
| 所有权   | 权威状态所有者和允许的写入方                   | 每个可变事实只有一个所有者 |
| 验证     | 核心 case、集成边界和真实交互路径              | 映射到决策的测试清单       |

只有当另一位维护者无需查看预期 UI 实现，就能推导出公共领域操作及其测试 case 时，记录才算完成。

## 问题契约

先用用户可观察的术语定义问题，再命名组件、Hook、存储键或实现技术。

- 识别谁会在什么上下文中遇到问题。
- 说明该参与者会得到什么不同的结果。
- 记录会实质性限制有效方案的约束。
- 声明非目标，避免相邻行为被隐式纳入功能。
- 定义如何观察成功、失败、取消和有意的无操作行为。

- ❌ 构建一个看起来像参考产品的可拖动列表组件。
- ✅ 让用户在保持选择、成员关系和取消不变量的前提下重新排序其拥有的条目。

## 输出契约

在选择内部表示之前，列出每个外部可观察输出。

| 输出类别 | 必需决策                                     |
| -------- | -------------------------------------------- |
| 返回值   | 形状、含义、顺序和缺失语义                   |
| 语义事件 | 名称、负载、发出时机、幂等性和所有者         |
| 状态变更 | 权威所有者、提交点以及回滚或取消行为         |
| 渲染状态 | 有意义的视觉、焦点、无障碍和减少动态效果结果 |
| 副作用   | 目标系统、时机、重试行为、失败处理和可观测性 |
| 无操作   | 拒绝工作的守卫条件，以及拒绝是否可见         |

优先输出条目标识符和目标位置等语义结果，而不是 DOM 坐标或组件局部标志。在所属契约明确转移职责之前，由调用方拥有的模型始终保持权威。

## 领域模型形态

选择与问题匹配的最小模型形态。当领域只是确定性转换时，不要引入状态机；也不要把多阶段工作流隐藏在构建器中。

| 形态             | 适用情况                               | 公共操作                       | 副作用         |
| ---------------- | -------------------------------------- | ------------------------------ | -------------- |
| 提取器或解析器   | 需要从编码输入中推导含义               | `extract` 或 `parse`           | 无             |
| 规范化器         | 外部或旧版数据必须变成一种规范领域形式 | `normalize`                    | 无             |
| 策略或决策器     | 需要根据显式事实做出一个决策           | `resolve` 或 `decide`          | 无             |
| 构建器或投影器   | 多个规范输入生成一个完整读模型         | `build` 或 `project`           | 默认无         |
| 状态机或 reducer | 事件通过受守卫的转换改变长生命周期状态 | `transition` 或 `reduce`       | 以命令形式返回 |
| 工作流或编排器   | 有序阶段协调副作用、短路和恢复         | `execute`、`load` 或 `prepare` | 显式允许       |

使用领域单元所拥有的结果命名它，而不是使用恰好调用它的页面、框架生命周期或当前组件来命名。

## 数据模型

建立能够表达每个有效 case 并拒绝无效组合的最小领域模型。

- 为持久实体提供稳定标识符，并定义关系基数。
- 为每个可变事实指定唯一权威所有者。
- 分离权威状态、临时投影、派生值和展示状态。
- 声明排序、唯一性、成员关系、生命周期和引用完整性不变量。
- 显式定义边界解析和缺失语义；不要把两个可选值的偶然相等用作状态转换。
- 当相互独立的布尔值可能表示不可能的组合时，优先使用可辨识联合。

```ts
// ❌ 可以表示“带有分组的空闲状态”和“没有分组的拖动状态”。
interface DragState {
	readonly isDragging: boolean;
	readonly groupId?: string;
}

// ✅ 每个状态只携带它所必需的数据。
type DragState =
	{ readonly kind: 'idle' } | { readonly groupId: string; readonly kind: 'dragging-group' };
```

如果模型无法解释哪个所有者可以改变某个值，或者哪些组合有效，实现就不得使用组件局部状态或 CSS 选择器进行补偿。

## 领域单元契约

每个领域单元都公开一个窄而有类型的公共表面，其构造函数或入口函数负责建立主操作所需的全部前置条件。

```ts
interface Item {
	readonly id: string;
}

interface CanonicalInput {
	readonly items: readonly Item[];
}

interface Selection {
	readonly itemId: string | undefined;
}

interface BuildDependencies {
	readonly resolvePath: (itemId: string) => string;
}

type BuildResult =
	| { readonly kind: 'empty' }
	| { readonly items: readonly Item[]; readonly kind: 'ready'; readonly selectedId: string };

declare class ItemProjectionBuilder {
	constructor(input: CanonicalInput, dependencies: BuildDependencies);
	build(selection: Selection): BuildResult;
}
```

- 在领域单元边界让必需数据变为非可选；对缺失的前置条件只拒绝一次，不要在整个操作中反复分支。
- 接收专用能力接口。只有当 `Pick<Context, ...>` 精确暴露该单元允许使用的方法时，才可在集成边界使用它。
- 保持主要公共操作小而明确。次要公共查询需要自己的输出契约。
- 使用私有辅助方法命名独立领域决策，而不只是缩短长方法。
- 返回完整领域结果，并让其变体无法表示无效字段组合。
- 在远程、持久化、旧版和框架所有的类型进入构建器、策略或状态机之前进行规范化。
- 不要在确定性提取器、规范化器、策略或构建器中导入网络或存储服务。

## 状态转换模型

只有当功能拥有长生命周期状态或多事件交互时，才使用状态转换模型。把行为表示为应用于显式状态的事件。为每次转换记录其守卫条件、下一状态、语义输出、副作用和取消路径。

| 当前状态     | 事件     | 守卫条件         | 下一状态         | 输出         |
| ------------ | -------- | ---------------- | ---------------- | ------------ |
| 空闲         | 开始     | 目标符合条件     | 已准备           | 无           |
| 已准备       | 越过阈值 | 手势仍然有效     | 活跃             | 激活事件     |
| 活跃         | 移动     | 候选项满足不变量 | 带投影的活跃状态 | 仅预览       |
| 活跃         | 提交     | 投影仍然有效     | 空闲             | 语义移动     |
| 已准备或活跃 | 取消     | 始终             | 空闲             | 恢复权威状态 |

- 除非契约明确定义乐观所有权，否则在可逆预览活跃期间保持权威模型不变。
- 从当前模型和交互阶段派生视觉状态；不要把 DOM 是否存在或 CSS 作为业务事实来源。
- 当环境可能产生重复、乱序、中断或陈旧事件时，明确规定其行为。
- 测试转换序列，而不只是孤立的最终状态。

## 领域核心

在连接生产界面之前实现领域决策。提取、规范化和策略决策优先使用纯函数；当构造过程需要建立前置条件、保存领域缓存，或围绕同一规范输入组织多个操作时，可以使用类。确定性领域单元必须对相同的已验证输入返回相同结果。

```ts
interface TransitionResult<State, Command> {
	readonly commands: readonly Command[];
	readonly state: State;
}

declare function transition<State, Event, Command>(
	state: State,
	event: Event,
): TransitionResult<State, Command>;
```

- 把时间、随机性、存储、网络、进程 API 和 DOM 测量放在显式能力边界之后。
- 不要把排序、成员关系、资格、冲突和取消规则放进组件与事件处理程序。
- 返回语义结果；由适配器把它们转换为框架回调和外部副作用。
- 如果一条规则只能通过当前标记或选择器顺序解释，应视为模型不完整的证据。

## 工作流契约

工作流拥有顺序和副作用；其各阶段把决策委托给领域单元。在实现编排器之前，先记录阶段顺序。

| 阶段   | 消费               | 产出                       | 副作用策略     |
| ------ | ------------------ | -------------------------- | -------------- |
| 规范化 | 不可信或旧版输入   | 规范领域输入               | 仅边界验证     |
| 决策   | 规范输入和语义意图 | 决策或投影                 | 确定性         |
| 准备   | 决策加外部能力     | 准备好的数据或有类型的失败 | 允许副作用     |
| 呈现   | 准备好的领域结果   | 公共输出模型               | 不新增领域决策 |

- 编排器是阶段顺序、短路、重试和恢复的唯一所有者。
- 每个阶段声明其读写的最小能力；不要因为方便就传入完整应用 store 或请求上下文。
- 优先使用阶段专属输入和输出类型。如果必须使用可变工作流上下文，应记录每个写入方、为读取方提供窄能力视图，并在缺少必需数据时于阶段边界失败。
- 除非输出类型显式建模降级行为，否则绝不能捕获意外失败并伪造一个空的成功值。
- 直接测试确定性阶段，并单独测试编排器的顺序、副作用调用、短路和错误映射。

## 测试设计门禁

在生产 UI 集成之前编写决策清单、场景矩阵和领域核心测试。核心测试套件必须能够独立于渲染、浏览器自动化、网络服务和持久化存储通过。

| 覆盖维度 | 必需 case                                                    |
| -------- | ------------------------------------------------------------ |
| 等价类   | 每个含义有实质差异的有效状态至少一个代表                     |
| 边界     | 适用时覆盖第一个、最后一个、空、单元素、阈值、最大值和最小值 |
| 无效输入 | 被拒绝的身份、关系、转换和陈旧引用                           |
| 方向     | 当方向不应改变语义时，覆盖正向与反向操作                     |
| 序列     | 重复、中断、取消、回滚和重新进入                             |
| 不变量   | 在每个被接受的转换中始终成立的属性                           |
| 所有权   | 调用方控制的更新、延迟提交和被拒绝的乐观假设                 |
| 歧义     | 零次、一次和多次匹配，以及冲突裁决规则                       |
| 层级     | 每个支持深度，以及缺失、空、部分和完整分支                   |
| 回归     | 每个缺陷修复都有一个修复前失败、修复后通过的 case            |

- 在编写 case 之前，从独立决策维度推导矩阵。覆盖有意义的组合和冲突点；不要依赖快乐路径的行覆盖率，也不要盲目生成无关的笛卡尔积。
- 使用领域语言命名 case，让测试套件能够被读成决策树：输入条件、选中的规则和预期结果。
- 执行主要公共操作并断言其完整的有类型输出。不要用测试私有辅助方法代替领域契约。
- 为 fixture 构建器提供有效的最小默认值，然后只覆盖当前 case 所测试的决策维度。
- 在领域单元承诺拒绝缺失前置条件和无效边界数据的位置测试它们。
- 紧凑矩阵优先使用表驱动测试，排序、唯一性和成员关系不变量优先使用属性式断言。
- 只有为回答尚未解决的可行性问题时，才允许一次性交互试验先于核心；它不得悄然成为生产实现。

测试位置、命名和回归要求遵循 [`docs/TESTING.md`](TESTING.md)。

## 交互建模

交互功能要建模完整的手势时间线，而不只是释放后的状态。当这些阶段产生不同行为时，至少要区分空闲、已准备、活跃、预览、提交和取消阶段。

| 维度       | 必需决策                                   |
| ---------- | ------------------------------------------ |
| 激活       | 指针或键盘阈值，以及选择发生变化的时刻     |
| 命中测试   | 合格目标、重叠规则和边界迟滞               |
| 几何       | 测量所有者、坐标空间、滚动和尺寸变化行为   |
| 层叠       | 每个交互阶段中哪个表面绘制在另一个表面之上 |
| 预览       | 可逆投影、插入反馈和成员关系指示           |
| 焦点和菜单 | 焦点所有权、关闭、点击穿透和键盘连续性     |
| 动效       | 位移、中断、减少动态效果和完成行为         |
| 取消       | 指针取消、Esc、捕获丢失、卸载和陈旧数据    |

- 当操作预期对称时，测试两个方向。
- 保持预览与提交分离，避免经过候选项时改变权威数据。
- 定义 active、hover、focus、selected 和 dragging 视觉状态重叠时的优先级。
- 让反馈描述用户在当前时刻提交后会得到的结果。
- 不要用动画或样式掩盖含糊的转换或无效状态。

## 参考产品和新行为

- 把现有产品视为证据，而不是功能规范。记录观察到的场景，推导规则，并明确决定产品采用还是拒绝它。
- 比较交互时间线和状态变化，而不只是截图。
- 没有成熟参考时，先创建一次性原型，并在生产集成前审查问题、输出、模型、转换表和场景矩阵。
- 把未解决行为记录为阻塞实现的决策；不要让原型中的偶然行为成为契约。
- 当行为对齐是目标时，对参考产品、原型和集成功能重新运行相同的受控场景。

- ❌ 先复制可见细节，再通过回归发现底层规则。
- ✅ 建立自己拥有的行为契约，在原型中验证困难转换，然后实现稳定核心。

## 集成边界

通过薄壳集成稳定核心，由薄壳把平台输入转换为语义事件并渲染结果模型。

- 组件渲染准备好的状态并发出语义意图；它们不重复实现领域决策。
- Hook 协调框架生命周期和适配器；它们不会变成一个分散在 Effect 之间的隐式状态机。
- CSS 表示模型提供的展示状态；选择器不从缺失值或同级顺序推断领域状态。
- 外部副作用在转换后消费显式命令，并通过显式事件报告结果。
- 组件测试验证接线和无障碍，浏览器测试验证真实手势时间线，视觉审查验证展示；它们都不能取代领域核心覆盖。

React 所有权遵循 [`docs/frontend/react.md`](frontend/react.md)，视觉决策遵循 [`docs/frontend/visual-foundations.md`](frontend/visual-foundations.md)，跨工作区依赖遵循 [`docs/ARCHITECTURE.md`](ARCHITECTURE.md)。

## 变更纪律

- 编辑生产代码前，把每个缺陷分类为模型规则缺失、场景缺失或实现违规。
- 应用生产修复前，先添加缺失的不变量以及失败的核心测试或交互测试。
- 如果一个修复改变了目标场景之外的行为，把它视为停止信号：恢复一致的模型和测试矩阵，而不是再添加一个条件标志。
- 当权威所有者、转换守卫条件、取消行为或预期输出不明确时，停止集成。
- 模型变更后删除过时投影和标志；除非显式边界要求，否则同一事实的并行表示不是迁移策略。
- 当缺陷反复跨越状态组合、方向或交互阶段时，重新审视抽象；反复的局部补丁说明当前边界是错误的。

- ❌ 因为当前截图不正确，就再添加一个组件布尔值。
- ✅ 找到缺失的状态或不变量，扩展核心和场景矩阵，然后更新投影。

## 实现顺序

每个已建模功能都按以下顺序进行：

1. 写出问题、非目标、输入和可观察输出。
2. 定义规范输入、输出、错误、标识符和不变量类型。
3. 选择领域模型形态，并命名其主要公共操作。
4. 盘点独立决策并构建场景矩阵。
5. 实现确定性领域单元，并让其测试通过。
6. 当需要副作用时，实现并测试工作流或外部适配器。
7. 把稳定的公共操作集成到应用或组件薄壳中。
8. 为只有在真实交互环境中才存在的行为添加浏览器和视觉验证。

如果后续步骤暴露了前面尚未解决的决策，应返回对应产物并先更新其测试，然后再继续。不要只在集成层编码答案。

## 就绪定义

只有满足以下条件，才能开始生产集成：

- 问题、参与者、结果、约束和非目标已经明确；
- 可观察输出、失败、取消和无操作行为已经定义；
- 选定的模型形态和主要公共操作与问题匹配；
- 数据模型明确了所有权、生命周期、缺失语义和不变量；
- 必需依赖已经表示为最小能力，工作流阶段也已经排定顺序；
- 当功能有状态时，转换模型覆盖守卫条件、预览、提交、副作用和取消；
- 场景矩阵覆盖等价类、边界、歧义、层级、序列和对称性；
- 确定性核心及其测试无需生产 UI 即可通过；并且
- 尚未解决的参考产品或原型行为已经转化为显式决策。

## 完成定义

只有满足以下条件，功能才算完成：

- 当前所属权威来源描述已实现的契约，且不包含任务历史；
- 领域核心测试保护每条自有规则、决策维度和不变量；
- 工作流测试保护阶段顺序、副作用边界、短路和失败映射；
- 集成测试保护框架边界和无障碍；
- 浏览器级测试保护有意义的多步骤手势和取消路径；
- 每个已发现回归都在最低有效层拥有一个修复前失败、修复后通过的测试；
- 临时原型行为、重复状态和过时标志已经删除；并且
- 根级 [`pnpm verify`](VERIFICATION.md#合并门禁) 门禁通过。
