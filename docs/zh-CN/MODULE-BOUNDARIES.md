# 模块边界

## 源模块树

`orchbee/module-boundaries` 将 `apps/*/src` 或 `packages/*/src` 树中的每个目录视为一个源模块，测试目录、自有 React 组件分组，以及由已识别公共或私有组件树拥有的支撑目录除外。`src` 目录是根模块。`__tests__` 目录属于最近的源模块祖先，不会创建模块。

每个源模块都必须有一个 `index.ts` 边界入口。同一模块中的文件可以直接相互导入。后代也可以直接导入祖先的实现，因为祖先内部位于其词法可见范围内。每个横向依赖都必须导入目标模块的 `index.ts`；即使 TypeScript 可以解析，横向边界之下的文件路径仍然是私有的。

## 结构化组件分组

包含 `<component-name>.tsx` 的自有 `components/<component-name>/` 目录是由 [`docs/frontend/react.md`](frontend/react.md#组件目录边界) 约束的私有组件所有权边界的结构形式，而不是源模块。它的整棵子树——包括 `components`、`contexts`、`hooks`、`constants`、`types` 和 `utils` 目录——都属于拥有最外层匹配组件分组的源模块祖先。

结构化组件分组不定义 `index.ts` 入口，也绝不能跨源模块边界导入。其所有者和实现文件作为同一源模块的成员直接相互导入；对其他源模块的依赖仍遵循正常的可见性表。当另一个模块需要某个私有组件时，把该组件及其完整所有权树提升到合适的源模块边界。仅仅命名为 `components` 的目录不会获得这项处理，除非它包含组件分组形态，因此生成的 `packages/ui/src/components/ui` 公共模块树仍然是正常的源模块树。

围绕一个公共边界组件组织的源模块，只把自身 `index.ts`、根组件 `.tsx` 和可选的同名 `.module.css` 作为直接组件文件。其组件支撑目录使用与私有组件分组相同的名称和所有权，并继续作为该源模块的结构组成，而不是独立子模块。非组件目录和组件所有权树之外的目录仍然是正常源模块，并且需要自己的 `index.ts` 边界。

## 模块可见性

源模块可见性遵循词法树作用域：

| 源模块 | 目标模块                     | 允许 | 必需目标   |
| ------ | ---------------------------- | ---- | ---------- |
| `B/B1` | `B/B1` 自身                  | 是   | 实现文件   |
| `B/B1` | `B` 或其他祖先               | 是   | 实现文件   |
| `B/B1` | `A`，某个祖先的同级模块      | 是   | `index.ts` |
| `B/B1` | `B/B2`，当前层级的同级模块   | 是   | `index.ts` |
| `B/B1` | `A/A1`，另一棵子树           | 否   | 隐藏       |
| `B`    | `B/B1`，子级或后代           | 否   | 隐藏       |
| `A/A1` | `B/B1`，同祖但不同分支的子树 | 否   | 隐藏       |

该规则同样适用于运行时导入、仅类型导入、动态导入和重新导出。

## 边界入口点

`index.ts` 是导出清单，不是实现文件。它只能包含带来源的显式命名重新导出，包括 `export type`；禁止导入、声明、可执行语句、本地导出、默认导出和 `export *`。

一个 index 可以重新导出自身模块的实现文件和直接子级的 `index.ts`。更深层的 API 必须逐层提升通过每一个边界。

```text
src/
├── a/
│   ├── index.ts
│   └── a1/
│       └── index.ts
└── b/
    ├── index.ts
    └── b1/
        ├── index.ts
        └── consumer.ts
```

```ts
// src/a/index.ts：通过 A 显式提升选定的 A1 API。
export { createA1 } from './a1';
export type { A1Options } from './a1';

// src/b/b1/consumer.ts
import { createA1 } from '../../a'; // 允许：通过 A 的边界。
import { createA1 as hiddenA1 } from '../../a/a1'; // 禁止：A1 对 B1 隐藏。
```

即使 `src/a/a1/index.ts` 存在，第二个导入仍然被禁止。只有通过 `src/a/index.ts` 的显式导出，其 API 才会对 `B/B1` 可见。TypeScript 会验证请求的符号确实已导出。

## 测试

生产源码绝不能从 `__tests__` 导入。测试继承其所属模块的可见性，包括对祖先测试辅助函数的访问。`src/__tests__` 中的包级测试可以通过后代模块的 `index.ts` 检验它们，但绝不能通过私有后代文件。

## 组合和循环依赖

父模块不作为其子模块的组合根。把编排放在一个专用叶模块中，由它使用可见的同级边界，然后在需要时向上重新导出其 API。

模块实现不得导入自身的 `index.ts`，因为这会产生 barrel 循环；应直接导入本地实现文件。

`import/no-cycle` 以 `ignoreTypes: false` 运行，因此仅类型循环依赖和运行时循环依赖一样会使 lint 失败。通过把共享契约移动到双方都可见的最近模块、在接口后反转依赖，或者引入专用同级模块来打破循环；不要抑制或降级该规则。
