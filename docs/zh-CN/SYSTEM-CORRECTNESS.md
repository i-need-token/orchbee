# 系统正确性

## 正确性门禁

在一个已建模子系统拥有可审查的正确性论证，且以下风险触发的每种方法都有可执行证据之前，不得宣称它已经完成。示例测试通过、截图一致、逐文件翻译参考实现或完成源码清单，本身都不能建立正确性。

| 风险触发条件                                     | 必需证据                                                   |
| ------------------------------------------------ | ---------------------------------------------------------- |
| 任何拥有领域状态或转换的行为                     | 显式状态、事件、输出、不变量、确定性核心测试和证据可追踪性 |
| 状态、排序、层级或事件序列存在大量组合           | 带收缩和重放的有状态属性测试                               |
| 并发、异步完成、重试、取消或独立排序的事件       | 带已检查安全属性及适用进展属性的 TLA+ 模型                 |
| 其正确性必须超越抽样或有界状态而成立的纯关键转换 | Lean 定义，以及机器检查的不变量保持、确定性或精化定理      |
| 源码兼容移植或行为复刻                           | 固定的参考版本、显式对齐范围，以及差分或精化验证           |
| 依赖手势、时序、动画、几何、焦点或平台集成的行为 | 在受控真实集成环境中的确定性系统轨迹                       |

使用全部适用的行。一行中的复杂性不能豁免另一行。源码兼容的交互状态机通常同时需要 TLA+、属性测试、确定性系统测试和参考实现精化；当其关键的纯排序、分组、选择、规范化或状态转换需要全称结论时，使用 Lean。

未来采用或迁移工作在实现之前放在 `proposals/` 下。把当前正确性论证放在所属包契约或内部参考旁边。本仓库规范只定义可复用方法，不得盘点某个功能的状态、上游文件或测试 case。

## 正确性论证

为每个通过正确性门禁的子系统创建一份长期正确性论证。它是“实现满足其自有契约”这一论证的索引，而不是实现工作的叙事。

| 字段     | 必需内容                                                   |
| -------- | ---------------------------------------------------------- |
| 范围     | 参与者、操作、可观察行为、支持的环境、版本和显式排除项     |
| 权威来源 | 自有行为契约、参考证据，以及二者冲突时采用的规则           |
| 模型     | 权威状态、语义事件、转换关系、命令和可观察投影             |
| 声明     | 安全不变量、进展属性、代数定律，以及允许的失败或无操作     |
| 信任边界 | 平台行为、解析器、外部代码、测量，以及本地未证明的假设     |
| 精化关系 | 形式化状态和动作如何对应实现状态、事件与观察结果           |
| 证据     | TLA+ 属性、Lean 定理、属性名称、确定性轨迹和差分场景       |
| 限制     | 模型检查边界、生成 case 限制、不支持的参考行为和未验证假设 |

正确性论证必须让审查者无需阅读 UI 代码就能回答三个问题：声明了什么、每条声明由哪个机器可检查产物支撑，以及哪些内容仍在声明之外。

使用精确措辞：

- TLA+ 模型检查证明在已探索模型和边界中不存在反例；它不证明 TypeScript 实现，也不证明无界执行。
- Lean 证明关于 Lean 中编码的定义与假设的定理；如果没有精化桥梁，它不证明另一份独立编写的 TypeScript 实现。
- 属性测试探索生成的示例；它不建立全称定理。
- 确定性系统测试为受控轨迹和环境建立可重现行为；它不枚举所有环境。
- 差分验证证明在声明的可观察投影上保持一致；它不证明参考实现在所采用对齐契约之外是正确的。

## 方法选择

根据各方法能够回答的问题进行选择。不得仅仅因为另一层更容易添加，就用它代替应有的方法。

| 方法           | 回答的问题                                       | 最适合的场景                         | 主要限制                         |
| -------------- | ------------------------------------------------ | ------------------------------------ | -------------------------------- |
| 示例测试       | 这个已知 case 是否产生预期结果？                 | 具名回归和边界示例                   | 只能找到有人选择的 case          |
| 属性测试       | 不变量能否在大量生成状态和序列中保持？           | 组合型数据和有状态命令               | 只对配置的搜索空间抽样           |
| TLA+           | 抽象状态机在允许的交错下能否违反安全或进展属性？ | 工作流、交互阶段、并发、取消和排序   | 检查模型，通常处于有限边界内     |
| Lean           | 一个定理是否对形式化定义允许的所有值成立？       | 纯转换和不变量保持                   | 证明形式化定义，而不是无关的实现 |
| 确定性系统测试 | 集成系统能否重现相同的可观察时间线？             | 手势、布局、调度、焦点、动画和适配器 | 覆盖声明的轨迹和受控环境         |
| 差分验证       | 实现是否精化了所采用的参考行为？                 | 移植、复刻、兼容层和迁移             | 取决于参考范围和观察质量         |

这些方法构成一条精化链，而不是彼此独立的徽章：

`reference evidence -> owned contract -> abstract model and theorems -> deterministic core -> platform adapters -> observable system`

每个箭头都需要显式映射或可执行比较。缺少某个箭头时，其左侧的证明不能建立右侧的行为。

## 行为发现与决策边界

把每个观察到的不一致视为“可能缺少决策规则”的证据，而不是立即把它当成孤立的实现或样式缺陷。在修改生产行为之前：

1. 记录场景的参考来源、环境、规范初始状态、语义动作和第一个发生分歧的观察结果。
2. 识别相互独立的决策维度，包括离散模式、所有权、选择、焦点、交互阶段、平台开关，以及宽度或指针位置等连续输入。
3. 当多个输出竞争同一资源时，显式声明优先级。类似 `status indicator > primary action > decorative icon`（状态指示器优先于主操作，主操作优先于装饰图标）的策略是一项有序决策；不得让它从彼此无关的组件条件和 CSS 流中偶然产生。
4. 从每个守卫条件、源码常量和观察到的转换阈值推导有限分区。对于边界 `b`，在输入域允许时覆盖 `b - 1`、`b`、`b + 1`，以及相邻分区中的代表性内部值。
5. 定义每个分区和转换处的规范观察结果，包括语义状态、可见控件、几何、焦点，以及允许的重叠或裁剪。
6. 为每条声明选择最低有效证据层，先让新增证据因预期原因失败，再实现最早的权威规则。

连续输入不需要任意抽样截图。它的决策过程通常会产生有限个等价类。属性测试应遍历完整支持输入域并断言各类不变量；具名示例应固定每个边界；确定性系统轨迹应在真实渲染器中穿越这些分区，并验证适配器、动画或布局引擎没有改变投影。

同一控件的可见性、位置、命中测试和无障碍语义属于同一项策略结果。应由一个语义决策计算它们，或由可证明等价的投影生成它们。不得让可见性 helper、flex 布局、绝对定位规则和指针目标分别决定控件是否存在或它会挤占什么。

局部检查器通过只属于局部证据。它通过后必须运行完整的适用门禁。更广泛的回归在被分类为其他原因之前，都属于对新推导规则的反例：它通常说明遗漏了更高优先级状态、生成器缺少一个边界分区，或某个投影只在一个适配器中成立。应先修订契约和最早的策略所有者，再调整下游预期。

## 可执行状态机边界

在与框架或平台集成之前，把有状态行为表示成确定性的领域转换。该边界必须公开形式化模型、生成命令、重放轨迹和系统观察所需的语义信息。

```ts
interface TransitionResult<State, Command> {
	readonly commands: readonly Command[];
	readonly state: State;
}

declare function transition<State, Event, Command>(
	state: State,
	event: Event,
): TransitionResult<State, Command>;

declare function observe<State, Observable>(state: State): Observable;
```

- 为每个持久实体提供稳定身份，并为每个可变事实指定唯一权威所有者。
- 使用不同状态变体表示不可能并存的阶段组合，不要使用相互独立的布尔值。
- 把指针数据、测量值、时间、外部响应和其他平台输入规范化为显式事件。
- 以命令形式返回副作用。通过后续事件应用其结果，不要在转换内部执行隐藏副作用。
- 把权威状态与可逆预览、动画投影和渲染状态分开。
- 定义无效、重复、陈旧、乱序和中断事件的结果。
- 让状态、事件、命令和观察结果可序列化，或者提供无损的规范轨迹表示。
- 在每个已接受转换后检查自有不变量，而不只在最终提交后检查。

集成薄壳可以测量 DOM、捕获指针、调度帧和渲染像素。它不得独立决定成员关系、排序、选择、资格、取消或提交语义。

- ❌ 组件、拖拽库和 CSS 分别保留自己对分组成员关系与预览位置的局部理解。
- ✅ 一个转换模型拥有成员关系和预览语义；适配器提供测量并渲染其可观察投影。

[`FEATURE-DEVELOPMENT.md`](FEATURE-DEVELOPMENT.md) 中的状态转换和集成规则仍是权威来源。本规范为高保证行为增加所需证据。

## TLA+ 规约

使用 TLA+ 在能够暴露相关安全和进展故障的最小抽象层级上建模语义状态与动作。除非 React 组件、CSS 声明、像素或实现调用栈会改变所声明行为，否则不要对它们建模。

每份长期维护的规约必须包含：

- 覆盖声明所需每个权威事实的变量；
- 仅允许受支持初始状态的 `Init` 谓词；
- 对应语义事件和副作用完成的具名动作；
- `Next` 关系和包含停顿步骤的完整时序规约；
- 类型与结构不变量，以及领域安全不变量；
- 适用的进展或活性属性；
- 仅在自有环境契约保证时才采用的公平性假设；
- 带显式常量、边界、对称性选择和状态约束的已检查 TLC 配置；以及
- 每个形式化动作和属性到正确性论证的映射。

至少考虑身份唯一性、引用完整性、成员关系互斥、排序或分区保持、连续性、活动项有效性、预览可逆性、提交原子性、取消恢复和所有权不重叠等不变量。在长期规约中使用领域名称。

绝不能使用状态约束移除可达的错误状态。状态约束可以限制探索范围，但必须列为限制；安全不变量必须检测无效的可达状态。如果一个模型只有在排除正在调查的故障后才能完成，它就不是证据。

模型检查必须覆盖快乐路径之外的情况：

- 两个方向和每个有意义的边界位置；
- 适用时覆盖空、单元素、已建模最大值、折叠、展开、已选择和未选择形态；
- 重复、陈旧、乱序、中断和取消动作；
- 当副作用与所有权发生竞态时，覆盖取消之前、期间和之后的副作用完成；以及
- 足以离开并重新进入每个交互阶段的历史长度。

当 TLC 找到反例时，在缺陷记录中保留其最短语义动作序列，并把它转换成确定性实现轨迹。如果该轨迹合法但自有契约没有定义它，应先修复契约和模型，再修改生产代码。如果它违反已声明不变量，应把它保留为最低可执行层的回归。

固定 TLA+ 工具链，并让合并配置可重现。更大的探索配置可以在合并门禁之外运行，但合并门禁必须检查一个具有代表性的有界模型，执行每个动作并检查每个长期维护的安全属性。记录两种配置及其限制。

## Lean 证明

对于必须对形式化定义允许的所有值都成立的纯定义和声明，使用 Lean。对于一旦失败就会破坏身份、成员关系、排序、分组、选择、规范化或状态机保持性的转换，应优先使用它。

每个长期维护的证明单元必须提供：

- 形式化输入、输出和有效性谓词；
- 所论证转换或抽象状态转换的定义；
- 与正确性论证中的声明对应的具名定理；
- 每个定理所需的最小显式假设；以及
- 当需要把 Lean 语义连接到生产实现时所需的可执行示例或序列化 oracle。

典型定理类别包括：

- 输出身份是输入身份的一个排列或声明的子集；
- 唯一性、分区、成员关系和连续性得到保持；
- 有效的活动或选中身份在每个已接受操作下保持有效；
- 规范化具有幂等性；
- 逆操作或取消操作恢复之前的抽象状态；
- 转换具有确定性；以及
- 具体纯操作精化了抽象关系。

不得使用 `sorry`、`admit` 或项目创建的公理让必需定理通过。任何无法避免的公理、经典假设、外部函数边界或解析器信任都必须在正确性论证中具名，并作为可信计算基的一部分接受审查。只有当 Lean 内核能够在没有遗留证明义务的情况下检查所得定理时，才允许使用生成的证明代码和证明自动化。

Lean 不会自动证明 TypeScript。必须有意连接二者。优先采用共享的规范输入输出 schema：在长期语料上执行 Lean 定义或提取出的 oracle，再对同一语料执行生产确定性核心，并比较规范观察结果。属性测试可以生成语料，但失败必须能够在脱离生成器后收缩和重放。

Lean 是本规范下新增演绎证明的默认证明助手。如果某个包已经拥有成熟的 Coq 或其他证明助手代码库，只有在它提供相同的内核检查声明、信任边界披露、精化桥梁和合并门禁保证时，才能继续使用。

## 属性测试

使用属性测试搜索实现的状态空间，特别是示例无法覆盖排序、分组、层级、选择、阶段、方向和历史组合的情况。

对于有状态子系统，定义：

- 有效初始状态生成器；
- 前置条件从当前生成模型状态推导的命令生成器；
- 针对拒绝、陈旧、重复和边界事件的显式对抗生成器；
- 简单 oracle、形式化 oracle、蜕变关系或不变量集合；
- 能保留复现故障所需前置条件的语义收缩器；
- 针对独立决策维度的覆盖分类；以及
- seed、生成状态、命令序列和观察结果的稳定序列化格式。

适用时必须包含以下属性族：

| 属性族       | 示例声明                                                 |
| ------------ | -------------------------------------------------------- |
| 保持性       | 每个已接受转换都保持身份、成员关系、排序和活动状态不变量 |
| 确定性       | 相同规范状态和事件产生相同规范状态、命令与观察结果       |
| 蜕变关系     | 两次规范化等价于一次规范化                               |
| 逆操作       | 提交后执行已定义逆操作，或预览后取消，会恢复抽象状态     |
| 对称性       | 反转方向或镜像几何只改变已声明的方向投影                 |
| 精化关系     | 生产输出与抽象模型、Lean oracle 或固定参考投影一致       |
| 无操作稳定性 | 被拒绝或陈旧的输入不改变权威状态，并且只发出允许的诊断   |

随机性绝不能让合并门禁变得不确定。使用显式 seed、固定大小限制、确定性调度器和已记录的生成参数。合并套件拥有稳定 seed 语料。更广泛的轮换或穷举式模糊测试可以作为探索运行，但每个失败都必须被缩减为最小序列化 case 并加入稳定回归语料，之后才算解决。

属性套件不能仅因为运行了大量 case 就算通过。它必须报告生成器是否到达每个必需状态类别、动作、边界、方向和交互阶段。无论迭代次数多大，一个几乎从不生成困难状态的生成器都只能提供很弱的证据。

## 确定性系统测试

使用确定性系统测试执行真实集成代码，同时控制所有可能改变可观察时间线的输入。目标是精确重放，而不只是降低偶发失败。

控制或记录每个适用的不确定性来源：

- 墙上时间和单调时间、计时器、动画帧，以及任务或微任务调度；
- 随机性、生成标识符、进程顺序和异步完成顺序；
- 视口、设备缩放、页面缩放、字体、区域设置、主题、减少动态效果和平台开关；
- 指针或键盘事件序列、坐标、捕获、取消和合并；
- 布局测量、滚动偏移、命中测试候选项、尺寸变化观察和几何快照；
- 网络、存储、worker、进程和操作系统响应；以及
- 初始持久化状态和外部参考版本。

确定性交互轨迹必须记录语义检查点，而不只是输入事件或最终像素。检查点应包括激活、跨越边界、预览变化、提交、取消和动效完成时的权威模型、交互阶段、待处理命令、可观察投影、焦点所有者、相关几何和渲染状态标识符。

- 推进逻辑时钟或等待具名语义条件；不要使用任意墙上时间 sleep。
- 使用固定逻辑帧驱动动画，并断言其语义开始、中间位移规则、中断行为和稳定结果。
- 在依赖截图之前比较规范几何和状态。像素比较只是绘制与样式的次级证据。
- 让每条轨迹都能按稳定名称独立运行，并拥有可序列化输入。
- 把掩盖未改变竞态的重试视为失败，而不是稳定机制。

有头探索观察仍然有助于发现行为和验证受控测试框架。在同一场景能够用已捕获输入和断言重放之前，人工观察不属于合并证据。

## 参考实现精化

当目标是兼容或复刻时，定义带版本的对齐契约。“与参考一致”或“完全复刻”不是可接受的无界声明。

对齐契约必须明确：

- 上游产品版本、源码 revision、构建开关、操作系统、主题和其他相关环境事实；
- 支持的操作、状态、输入方式、视觉模式和显式排除项；
- 要比较的可观察投影，包括语义状态、时序检查点、几何、无障碍和必需的绘制细节；
- 允许的规范化，例如不稳定进程标识符，以及它为什么不能隐藏行为差异；以及
- 源码审计、观察到的产品行为、上游测试和本地自有契约发生冲突时采用的权威规则。

把参考源码树视为由参数决定的一组行为，而不是单一且无条件的 oracle。记录选择所采用行为的 revision、功能开关、构建通道、平台分支、实验和运行时配置。上游测试只能为它所配置的分支提供证据；它不能证明另一个已安装二进制也选择了该分支。当源码、上游测试和观察到的二进制发生冲突时，应先对变体进行分类，不得混合证据，也不得静默选择最容易实现的行为。

审计行为依赖闭包，而不是一份同名文件清单。该闭包包括被调用的策略、所有权和生命周期规则、常量、功能开关、调度器行为、几何与命中测试代码、动画模型、平台主题集成、无障碍行为、上游测试，以及表面组件之外共享的状态。没有这份闭包的逐文件翻译只是源码相似，而不是行为精化。

对于每个对齐场景：

1. 从干净、已记录的状态建立参考前置条件。
2. 对参考实现和本地实现应用相同的语义动作序列。
3. 在相同语义检查点捕获观察结果，而不是在大致相等的墙上时间捕获。
4. 只规范化已声明的非领域噪声。
5. 比较完整的已采用投影，并在不匹配时保留两份轨迹。
6. 把不匹配分类为契约缺口、模型缺口、实现缺陷、测试框架缺陷、环境差异或显式不支持行为。

源码审计和探索式 computer use 可以发现场景并解释不匹配。稳定的差分证据必须来自可重复测试框架，或来自记录了来源和捕获流程的带版本 golden 轨迹。有意重新捕获参考轨迹；绝不能为了接受新的实现结果而静默更新它们。

上游升级属于语义变更。重新审计受影响的依赖闭包，重新运行场景清单，审查每个发生变化的 golden 轨迹，并在宣称兼容新版本之前更新对齐范围。

## 证据可追踪性

在正确性论证中维护一份追踪矩阵。每一行代表一条自有声明，而不是一个文件或一个实现函数。

| 声明               | 契约所有者   | TLA+ 属性          | Lean 定理          | 属性测试   | 系统轨迹   | 参考场景   | 限制       |
| ------------------ | ------------ | ------------------ | ------------------ | ---------- | ---------- | ---------- | ---------- |
| 使用领域名称的声明 | 所属参考章节 | 名称或有理由的 N/A | 名称或有理由的 N/A | 稳定测试名 | 稳定轨迹名 | 稳定场景名 | 边界与假设 |

- 每条可观察规则和不变量都必须在最低有效层拥有至少一个可执行见证。
- 每个长期维护的形式化属性或定理都必须映射回一条自有契约声明。
- 只有基于方法选择规则给出理由时，才能把方法标记为 N/A；空白单元格表示尚未解决的工作。
- 使用稳定名称，让检查器失败时能够识别受影响声明，而无需从任务或提交中重建历史。
- 把模型边界和信任假设记录在它们所限制的声明旁边。
- 当行为被有意移除时删除追踪行；不要保留陈旧证据来虚增表面覆盖率。

覆盖率百分比只是辅助诊断，而不是可追踪性。行、分支、截图或生成 case 数量都不能表明每条自有规则拥有证据。

## 反例纪律

把每个发现的故障视为正确性论证中某个链接缺失或为假的证据。

1. 保留准确的环境、seed、状态、事件序列、参考版本和观察结果。
2. 把故障缩减为仍会违反声明的最短语义轨迹。
3. 找到第一个分歧检查点，以及第一个被违反的不变量、定理假设或精化映射。
4. 把根因分类为契约规则缺失、形式化假设无效、生成器不完整、实现违规、适配器违规或测试框架缺陷。
5. 修复精化链中最早出错的权威来源。
6. 把缩减后的 case 加入稳定回归语料，并重新运行更广泛探索。

如果最小相关检查器通过但完整门禁失败，应同时保留两项结果。这组结果说明局部声明过窄、推导出的规则过宽，或精化映射遗漏了竞争状态。不得仅仅因为更广泛的测试早于本次变更就更新它；应识别冲突由哪个权威来源拥有，并显式定义优先级或边界。

不得只为状态机缺陷添加截图断言、削弱属性以接受当前输出、排除可达的 TLA+ 状态、添加 Lean 公理，或重试存在竞态的系统测试。这些操作是在移除证据，而不是解决矛盾。

如果缺陷反复跨越状态组合、方向、交互阶段或所有权边界，应停止局部修补并修订模型或精化边界。一系列狭窄的视觉修复说明缺少语义状态、不变量或投影规则。

## AI 辅助实现

AI Agent 可以审计源码、提出模型、生成测试与证明并实现代码。机械检查器和可审查证据决定是否符合规范。

在编辑通过正确性门禁的子系统生产代码之前，Agent 必须：

- 获取当前所属契约和正确性论证；
- 为所有采用的参考行为识别行为依赖闭包；
- 列出权威状态、事件、输出、不变量和未解决假设；
- 应用方法选择表并命名必需产物；
- 当工作源于一个故障时，把现有缺陷复现为最小语义轨迹；以及
- 说明每项预期变更影响哪条声明和哪个精化链接。

实现期间，在依赖新的实现行为之前更新抽象模型或证明定义。每次语义变更后先运行最小相关检查器，再运行完整适用门禁。当检查器返回反例时，先保存并分类它，再让 Agent 尝试下一次修改。

Agent 不得因为审计了每个可见文件、翻译了每个类、通过当前示例或匹配选定截图，就宣称完成。完成报告必须说明已检查声明、边界、参考 revision、已执行证据和排除项。未知行为仍然是显式范围债务；不得静默计为兼容。

独立审查在以下抽象边界最有价值：自有契约到 TLA+ 或 Lean、形式化模型到确定性核心，以及核心观察到真实系统或参考轨迹。只审查生成代码而不审查这些映射，无法建立系统正确性。

## 变更契约

实现之前对语义变更分类，并在同一次变更中更新每个受影响的所有者。

| 变更类别                                 | 必需更新                                                                     |
| ---------------------------------------- | ---------------------------------------------------------------------------- |
| 新增或变更状态、事件、守卫条件或取消规则 | 自有契约、状态模型、适用的 TLA+ 动作与属性、生成命令模型和确定性轨迹         |
| 新增或变更纯转换或不变量                 | 自有契约、适用时的 Lean 定义与定理、属性 oracle 和回归语料                   |
| 新增平台、几何、焦点、时序或动画行为     | 环境契约、确定性轨迹输入与检查点、适配器测试，以及属于对齐范围时的参考投影   |
| 参考 revision 或兼容范围                 | 固定的来源信息、依赖闭包审计、差分场景、已审查的 golden 变更和声明的限制     |
| 缺陷修复                                 | 修复前失败的缩减反例、根因分类、对最早错误所有者的修正，以及修复后通过的证据 |

不得变更生产行为而推迟其规约、证明、生成器或轨迹。除非显式兼容边界同时拥有两个模型且差分测试会比较二者，否则不得为了迁移方便保留两个相互竞争的语义模型。

当契约变更使一个证明或模型属性失效时，审查声明是否真的发生了变化。仅为了让当前代码通过而削弱声明，需要与其他行为变更相同的产品和架构审批。

## 验证门禁

每个由仓库提供、具有确定性、边界明确且版本固定的长期正确性产物，都必须在 [`VERIFICATION.md`](VERIFICATION.md) 定义的根级合并门禁中运行。所属包必须记录并公开真实命令；本规范不发明仓库没有执行的命令。

适用的合并门禁必须在以下情况失败：

- TLA+ 在已检查配置中发现安全不变量或进展属性反例；
- Lean 定理未检查、证明被承认，或存在未声明的信任假设；
- 属性失败、必需生成器类别不可达，或生成的失败无法重放；
- 确定性系统轨迹不匹配，或使用会影响结果的不受控时序；
- 声明的对齐范围内存在差分不匹配；或
- 已变更自有声明缺少可追踪性。

保持门禁可重现并快速失败。不得通过重试让偶发失败的命令通过。固定检查器版本和模型配置，显式限制资源使用，并把可操作反例作为产物保留。

当仓库无法以确定性方式提供参考产品、远程服务或特定环境时，对它们的捕获、比较和探索套件仍属于维护验证。兼容性发布前必须运行它们，但普通合并门禁不得依赖环境中的外部状态。只有在其参考、环境和输入都被固定并由仓库提供后，才把它们提升到合并门禁。

[`TESTING.md`](TESTING.md) 中的测试约定和回归要求适用于本规范引入的每个可执行测试。

## 完成定义

通过正确性门禁的子系统只有在满足以下条件时才算完成：

- 当前自有契约和正确性论证定义了范围、可观察投影、权威来源、不变量、假设和排除项；
- 有状态行为拥有唯一确定性语义转换边界和可序列化观察模型；
- 每个适用的方法选择触发条件都有证据，或追踪矩阵中存在经过审查的 N/A 理由；
- 每个采用的离散模式和连续阈值都有显式决策分区、适用优先级规则和可执行边界证据；
- TLA+ 在已记录边界下检查每个长期维护属性，并把发现的反例转换成重放轨迹；
- Lean 在没有遗留证明义务的情况下检查每个长期维护定理，而且其语义通过已测试的精化桥梁连接到生产代码；
- 属性测试覆盖必需状态类别，并保留可重放的最小失败；
- 确定性系统测试控制相关环境，并在完整交互时间线上断言语义检查点；
- 对齐声明标识固定参考，并通过声明的完整差分投影；
- 每个已知缺陷都已被缩减、分类并保留在最低有效回归层；
- 追踪矩阵没有无法解释的空缺或陈旧声明；
- 根级合并门禁无需重试即可通过；并且
- 完成报告说明已检查边界和剩余排除项，不使用“完全验证”或“完美复刻”等无界声明。
