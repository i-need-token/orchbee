# 应用

## 放置位置

把可独立运行或部署的入口点放在 `apps/*` 中。应用工作区既包括最终用户产品，也包括开发应用；受众差异不会改变放置位置。

把通过导入供其他模块使用的可复用能力放在 `packages/*` 中。把没有独立运行应用生命周期的仓库自动化放在 `scripts/*` 中。

```text
apps/desktop   # Electron 产品应用，引入后使用
apps/web       # 浏览器产品应用
apps/daemon    # 无头长时间运行的产品入口，引入后使用
apps/storybook # 开发应用
```

不要为了区分内部应用和产品应用而创建新的顶层目录。通过工作区名称、清单的 `private` 字段、`project.json` 的职责与非目标，以及发布流水线存在时的发布配置来表达这种区别。

产品应用应以它所拥有的用户界面或运行时角色命名。完整 Electron 产品使用 `desktop`，不要使用 `main`；这个名称只表示一个 Electron 进程，在 preload、renderer 和后台服务共存后会产生歧义。只有在确实存在一个长时间运行的无头入口时才创建 `daemon`；架构图不足以作为准入理由。

## 必需的应用结构

每个直接应用工作区都包含：

| 路径            | 职责                          |
| --------------- | ----------------------------- |
| `package.json`  | 身份、命令和依赖              |
| `project.json`  | 运行时、稳定性、职责和非目标  |
| `tsconfig.json` | TypeScript 应用的类型检查契约 |

应用公开其生命周期所需的脚本。浏览器应用通常公开 `dev`、`build`、`typecheck`、`test` 和 `test:watch`。专门的开发应用可以添加显式工作流命令，但必须让 `build` 保持非交互式，以便 `pnpm verify` 能够运行它。

## 工作区开发

浏览器应用为其开发命令注册官方 `@rsbuild/plugin-source-build` 插件。该插件解析工作区包声明的 `@orchbee/source` 条件，在应用图中编译这些公共源码入口点，并让应用的 Rsbuild 服务器负责 React 和 CSS 热替换。因此，包源码的修改会像应用源码修改一样经过同一个原生 HMR 图，无需预先构建包、并行运行库 watcher 或使用仓库进程监督器。

应用必须注册 source-built 包所需的每个编译器插件。例如，对 `@orchbee/ui` 使用源码构建的应用也要注册该包使用的 Tailwind CSS 插件；源码构建不会加载另一个工作区的 Rslib 配置。

只为开发注册源码构建。生产应用构建解析常规的 `types`、`import`、`require` 和 `default` 包条件，并使用 Rslib 输出。源码条件改变的是已声明公共入口点的编译方式，而不是应用可以导入哪些包路径。

运行 `pnpm web` 或 `pnpm storybook` 等公共根命令。让应用的 `dev` 脚本保持为直接的 Rsbuild 或 Storybook 命令，使 CLI 参数和进程生命周期继续由底层工具负责。

## 依赖方向

应用只能通过声明的包导出来使用包。包和应用绝不能从另一个应用的源码树导入。任何运行时工作区都不能依赖开发应用。

只有在权威仓库契约定义了产物格式和所有权时，应用才能发现另一个工作区的 Story 文件等非运行时产物。Storybook 遵循专用契约 [`docs/frontend/storybook.md`](frontend/storybook.md)。

## 产品应用和开发应用

产品应用属于 Orchbee 面向用户的运行时或发行版。开发应用支持浏览、测试或记录 UI 代码等可重复的仓库工作流。

开发应用：

- 将 `private` 设为 `true`；
- 在 `project.json` 中说明仅用于开发的角色和产品非目标；
- 当其构建验证已跟踪源码时，参与本地验证门禁；
- 不进入产品打包和发布输出；
- 不得成为可复用运行时代码的存放位置。

只有在构建、发布或策略自动化需要时，才添加机器可读的产品/开发分类。不要添加仅仅重复工作区名称和职责的元数据。

## 验证

`pnpm verify` 会构建、类型检查和测试每个公开相应标准脚本的应用工作区。应用构建输出在本地或 CI 中生成，并保持未跟踪状态。
