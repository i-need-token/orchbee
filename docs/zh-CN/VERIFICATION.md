# 验证

## 合并门禁

`pnpm verify` 是本地和 CI 的本机验证门禁。提交已完成的变更前，从仓库根目录运行适用的根级门禁。它只准备检查所需输入，不执行全量应用构建或交叉编译，顺序如下：

1. `pnpm format:check`
2. `pnpm test:tla:inventory`
3. `pnpm build:packages`
4. `pnpm lint`
5. `pnpm typecheck`
6. `pnpm test`
7. `pnpm test:exports`

迭代期间可以使用聚焦命令，但完成工作必须通过适用的根级门禁。
有明确范围的完整变更使用下文的日常影响范围门禁；明确要求全部本机测试时（包括 CI），
或无法解析范围时运行全部本机测试。通过适用门禁即满足仓库或包对根门禁的要求；
不要仅因另一份规范将命令写成 `pnpm verify` 就把两种形式都跑一遍。
其他规范应引用本节，不再定义第二套根门禁策略。

普通修改和合并不要求额外执行应用构建。`pnpm build` 是 `pnpm build:packages` 的别名，
只生成检查所消费的共享库产物。修改某个工作区的打包、资源、原生链接或安装包契约时，运行该工作区的构建。
需要为本机构建全部包、应用和 Cargo target 时，显式运行 `pnpm build:full`。
`pnpm test:cross` 显式编译所维护的其他平台目标。`pnpm verify:full` 将共享库准备步骤替换为
`build:full`，并在本机测试之后添加 `test:cross`；它用于有意执行完整构建/平台验证，
不是日常合并门禁。影响范围未知时选择全部本机测试，绝不自动加入可选的全量构建或交叉编译。
合并后受检输入未变化时，不需要重复门禁或构建。

## 按影响范围验证

`pnpm verify:changed -- <base>` 是日常根级门禁，与 `pnpm verify --changed-since <base>` 等价；
添加 `--plan` 可以查看实际采用的选择结果而不执行检查。基线必须解析为 HEAD 的祖先提交。
选择器包含已提交、暂存、未暂存、删除、重命名及未被忽略的未跟踪路径，读取 NUL 分隔的 Git 输出，
同时考虑重命名两端。基线无效、依赖清单变化、路径未知或依赖图不受支持时，选择全量测试范围。
它合并基线至 HEAD、HEAD 至暂存区以及暂存区至工作区的差异，防止撤回工作区文件隐藏已暂存的改动。
因此，无关的未跟踪文件也可能导致全量回退；选择器不会删除或忽略它。

本实现只收窄昂贵测试的范围。格式、TLA 清单、共享库准备、lint、类型检查、导出检查和根级工具测试仍全部执行。
被选中的真实进程测试会先准备所需的本机可执行文件；应用包和无关原生二进制不是前置条件。
不缓存普通测试结果，也不新增构建结果缓存；原生编译器保留正常的增量行为。
受影响的 pnpm 测试使用原工作区命令；受影响的 Cargo 成员保留全部 target、全部 feature、锁文件和文档测试。
Node 测试完成后才启动 Rust 测试。`pnpm verify` 和 `pnpm test` 执行全部本机测试，不执行交叉编译。

私有根验证所有者维护 `scripts/verification-scope.mjs`。这一无状态策略接收当前 pnpm/Cargo 工作区依赖
及改动路径，生成单一不可变计划。计划包含受影响所有者和全部传递消费者，覆盖普通、开发、可选、peer、
构建及目标平台相关的本地依赖。经审查的额外依赖还覆盖原生进程组合、共享协议夹具、Desktop 适配器资源
和 Storybook 发现机制。这些关系变化时，必须在同一变更中更新选择器及正向回归用例。
所有者缺失或有歧义时保守回退。命令将选中和未受影响的测试与实际执行结果分开报告；未受影响的测试
属于未执行，不能称为通过或缓存命中。

共享路径必须明确归属。已有的 `docs/tui/` 规范及中文对应文档选择原生终端客户端和它的消费者。
根级验证命令、已声明的辅助模块和测试，选择根级工具证据；上面的完整前置检查
仍全部执行。新增根级辅助模块或规范在审查前仍视为未知。对于 `scripts/documentation-pairing.json`，
使用配对模式解析基线、HEAD、暂存区和工作区清单，将这些快照之间每条新增、删除或修改的回执
映射到其英文文档的所有者。
JSON 或模式错误、任一版本不可用、回执所有者未知，均选择全量测试范围。
只有回执排序或空白变化时不增加产品所有者。完整 lint 门禁仍检查所有文档的配对完整性。

证据包括 Git 边界夹具、依赖闭包的正反控制、命令选择见证和现有真实 Cargo 运行器测试。
这些证据建立受支持的所有权映射，不证明任意动态文件读取。新增未声明的跨所有者输入必须补充映射
或全量回退。最终证据仍须满足下文关于检查输入保持不变的执行规则。全部本机测试继续用于发现映射遗漏，
CI 仍执行该基线。本策略不免除按变更触发的 TLA 检查，也不承诺固定耗时。

`schemas/terminal/` 下的改动选择 Rust 协议 crate、TypeScript 协议包和 Terminal Host，
再沿正常依赖选择其消费者。三者既有测试命令各自运行一项针对
`schemas/terminal/v1/constants.json` 的独立检查；夹具生成器不生成该注册表。
规范载荷及原生表面检查继续读取同一权威。

## 执行与证据

- 不要在同一工作树中把 `pnpm verify` 与另一次根门禁、`pnpm test` 或 build 重叠运行。
  独立调度的检查只有在可写产物和 fixture 隔离时才能并行。根级 Node workspace tests 完成后，
  才开始 Rust workspace tests：缓存分离不能保护 native 进程的启动截止时间免受高 CPU 负载 Node 测试的影响。
  这不禁止 workspace task 已拥有的并行执行。
- 针对完整集成候选运行适用的根门禁。受检输入未变化时，提交、报告、交接或内部切片边界
  不要求再跑一次。这不省略另行要求的按变更触发的正确性证据，也不为普通门禁步骤引入缓存。
- 在最终门禁前完成受治理编辑。如果相关输入在运行期间或之后改变，应识别失效的证据，
  并在宣布完成前针对最终输入重跑必需门禁。命令成功只证明它检查过的输入，不证明后续编辑。
- 在受版本控制源码之外保留首次失败的命令、源码状态、平台/工具链、可用的 seed 和完整日志。
  后续通过不能诊断首次失败，也不能证明已经修复；应把未解决失败与后续结果一起报告。
  诊断性重跑必须指明要回答的问题，并保留先前结果；不得重试到通过，也不得在缺乏证据时
  把失败归类为环境问题或测试不稳定。
- 区分失败、中断、跳过、未执行与通过。部分门禁通过不代表完成，聚合摘要也不是完整测试清单。

## 检查输出

新增或修改的面向人的验证输出必须定义有界摘要、可操作的失败诊断以及完整详情的访问方式。
兼容时复用现有输出层；保留机器可读输出契约和显式详细模式。减少输出绝不授权删减检查、
吞掉警告或用日志解析的成功替代进程失败。

根级 `test`、`verify` 命令、Node 测试包装入口和 Rust workspace runner 默认输出阶段摘要。
`scripts/run-checks.mjs` 拥有根命令执行序列；`scripts/check-output.mjs` 拥有共享的输出呈现。
这一呈现边界不选择执行范围：阶段仍然顺序执行、失败即停；显式分组的独立检查并行运行，保持相同的 workspace 范围、
compiler flags 和手动测试排除项。组内所有成员排空后按声明顺序报告，并以声明顺序中首个
失败成员的结果停止。只有子进程结果决定成功与否，绝不使用日志解析结果判定成功。

- 每项检查报告开始、结果和从启动到自身进程及 stdio 关闭的耗时，不包含等待同组其他成员
  或格式化摘要的时间。已识别的测试计数以及有界的警告或跳过提示作为补充；
  它们仅供参考，不是完整测试清单。
- 完整的 stdout/stderr 合并后直接写入 OS 临时目录中的私有文件，执行前打印目录路径。
  日志位于工作树之外，并在失败或中断后保留。调用任务负责保留与回收，在最后一个诊断、
  审查或恢复使用方结束后删除；运行器不会自动回收。不会自动上传；
  分享前应检查是否包含敏感诊断信息。
- 失败时报告日志路径、有界的已识别错误摘要和开头/末尾摘录，并明确标记省略内容。保留子进程非零退出码；
  子进程信号产生惯例对应的非零信号退出码。检查启动失败或日志保存/读取失败也会让命令失败。
- 嵌套包装入口继承外层捕获，不重复创建日志或摘要。
  `pnpm test --verbose`、`pnpm verify --verbose` 和
  `node scripts/run-rust-workspace.mjs test --verbose` 直接流式输出底层信息，不捕获日志。
  被包装的 Node 测试命令也接受相同的 `--verbose` 选项。
- 并行流式输出为每行添加检查名称前缀。超长行拆为有界、带标签的片段，不丢失文本或拆开
  Unicode 字符；末尾未终止的片段补上换行。每条流等待目标写入完成后才继续转发，
  因而慢速目标不会导致输出队列无限增长。
- 包装层异步执行子进程并继承现有进程组。未捕获的单项检查继承 stdin；捕获输出或并行管道
  检查忽略 stdin。不引入重试、超时、后台执行或取消监督器。
  中断仍由现有终端/job 取消机制负责；只打印开始、没有结果不代表通过。

执行模型是固定有序列表：启动一个阶段的成员，保留输出，分别记录各成员关闭时间，排空整组，
然后在全部零退出时前进，或在失败时停止。摘要和详细模式执行相同列表。`scripts/check-output.test.mjs` 通过成功、失败、
信号终止、可执行文件缺失、嵌套和大输出子进程，以及无损日志和有界诊断，验证这个公开操作。
它不证明任意后代进程的取消，也不证明未实际运行这些用例的平台行为。独立 TLC 输出及其
机器可读结果保持不变。

## 必需任务

| 任务                      | 契约                                                                                                                           |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `format:check`            | Oxfmt 管理的文件与 `.oxfmtrc.json` 一致，并且 rustfmt 与每个应用自有原生 formatter 都接受其所属文件。                          |
| `lint`                    | 代码、Rust workspace 与 Clippy、文档配对、样式、存储、架构、依赖、项目契约、体验目录、导出和清单规则全部通过。                 |
| `test:tla:inventory`      | TLA+ 执行清单、产物登记、owner 命令、触发映射以及 runner 负向控制彼此一致。                                                    |
| `build`, `build:packages` | 共享库工作区生成 lint、类型检查、测试和导出检查消费的产物。                                                                    |
| `build:full`              | 使用固定工具链和依赖，显式为本机构建每个可构建的 pnpm 与 Cargo 工作区。                                                        |
| `typecheck`               | 每个具有 TypeScript 契约的工作区都满足该契约。                                                                                 |
| `test`                    | 契约检查器测试、文档配对负向测试、自定义 lint 规则和依赖范围测试、pnpm 与 Cargo 本机测试套件和必需的受控本地系统见证全部通过。 |
| `test:cross`              | 显式编译已声明的其他平台原生测试图。                                                                                           |
| `verify:rust-native`      | 按当前主机平台配置运行 Rust workspace Clippy、原生测试前置准备和全部 Cargo 本机测试套件。                                      |
| `test:exports`            | 每个库的打包导出、运行时格式和声明均可被使用。                                                                                 |

- `build:packages` 先于 `lint` 和 `typecheck`，因为依赖分析和生产使用方解析库产物，不解析另一个包的源码。全新检出必须先生成这些导出，再让 Knip 判断依赖使用情况。
- `build:full` 先完成全部共享包，再启动应用构建；两个阶段各自保持拓扑顺序。Story 发现可能使用其所属方的包依赖，而宿主并不直接在运行时依赖这些包，因此应用不能与这些包的构建争抢执行顺序。
- `scripts/run-checks.mjs` 按受测消费者和本机平台选择原生测试前置产物。只准备真实进程测试消费的 Host 可执行文件和配套二进制，再运行 Cargo 测试。Cargo 测试和 Clippy 自行编译输入，不要在它们之前重复构建整个工作区。单独调用 Rust runner 时，如涉及真实进程测试，也须准备相同前置产物。
- 应用模块开发不消费库的 `dist`；Rsbuild 把已声明源码入口解析到开发图中。通过 Node 执行、且消费库 runtime export 的开发准备流程，必须在进程启动前显式构建该依赖。
- `pnpm verify` 可以重建包输出而不中断正在运行的应用服务器；验证和生产继续使用按拓扑顺序构建的产物。
- Rust workspace 工作使用精确的根工具链与已提交 Cargo lockfile；Zig 源码依赖使用不可变 URL 与
  content hash。必需 build 必须在生成 artifact 前拒绝不同 compiler 或 dependency resolution。
- `scripts/run-rust-workspace.mjs` 把根 pnpm 门禁连接到 Cargo。第一个已接受 Rust member 存在前，
  它验证固定工具链和 empty workspace metadata；之后同一批 task 使用 `--locked` 对每个 member
  运行 rustfmt、Clippy、build 与 test。
- 原生交叉编译检查只证明源码和依赖可为已声明目标编译；平台行为仍然需要原生 runner。
- `verify:rust-native` 复用 `lint` 与 `test` 中相同的 Rust runner 任务和原生测试准备，自身不新增步骤，
  因此 Windows 本机门禁和 Windows CI Job 不会与 Linux 根门禁漂移。修改受平台条件编译约束的 Rust
  代码时，在 Windows 上运行它。

## 变更触发的 TLA+ 验证

`pnpm test:tla` 是完整 TLA 验证门禁：先执行无需 Java 的清单与 runner 测试，再检查全部已注册配置及真实 TLC 缓存/变异证据。模型检查始终从全新状态开始，不复用成功结果。整次调用墙钟耗时超过 60 秒即失败。修改预算或模型集合时，在依赖及固定工具已安装的条件下测量三次完整全新状态运行；另行说明机器/负载和工具准备时间。

`scripts/tla/models.json` 注册 13 个协议模型、15 个配置，记录语义所有者、声明、实现触发路径、所需动作覆盖及每配置 20 秒期限。这就是全部维护中的模型集合，不是隐藏必跑全集前的快速子集。新增模型必须满足完整预算及[建模与正确性](MODELING-AND-CORRECTNESS.md)的准入条件。超时属于失败，不能用于跳过工作。

普通 `pnpm verify` 门禁执行 `test:tla:inventory`，不隐式运行 Java。产品协议状态、转移、假设或细化关系变化时，需要相应已注册模型及实现测试。工作区命令委托共享 runner；仅有本地实现证据的工作区不提供空 TLA 命令。`node scripts/tla/run-models.mjs --all` 仅执行模型基线，不是完整 TLA 门禁。

`pnpm test:tla:changed -- <base>` 选择受影响协议，并可按[工具缓存契约](../../scripts/tla/README.zh-CN.md#本地成功缓存)复用数学输入完全未变的结果。复用不证明修改后的产品代码。完整 `pnpm test:tla` 永不复用这些结果。Runner/helper、验证标准、受支持 TLC job 或触发策略变化会选择精简后的完整模型基线，并要求真实工具证据。已知清单测试入口仍归必跑清单门禁，不另设流程元模型。

选择范围合并当前与基线依赖、重命名两端及已提交/暂存/未暂存/未跟踪变化。删除注册不选择无关保留模型。共享元数据变化、无效或非祖先基线、隐藏 Git 输入及歧义 workflow 会选择全部模型。当前与基线排除规则分别求值，防止同一 diff 的排除隐藏所有者变化。可选文档范围必须分类全部支持的 H2 标题；有歧义时回退整文件。产品对工具路径的依赖仍有效。CI TLA job 执行所选模型及真实缓存/变异证据；准备/下载及 CI job 开销与本地验证计时分开。

每个配置使用固定 TLC 1.7.4 及 SHA-256、指纹多项式 0、显式有限边界、所需动作覆盖、声明的 worker 和独立状态/Java 临时目录。`-lncheck final` 在可达图完成后检查全部配置中的时序性质。成功要求 child/stdio 正常关闭、完整成功报告、状态队列归零及所有所需动作证据。输出保留机器可读的计数、耗时、worker/heap 预算、输入摘要和日志路径。部分探索不构成进展证明。

独立配置共享受处理器与可用内存 60% 限制的 FIFO 资源队列。默认 heap 上限 4096 MiB，另留 512 MiB 进程预算。`--max-heap-mib N` 接受 256 至 8192 的十进制整数；`--jobs N` 在相同内存预算内显式限制进程数。声明的 worker 计入 CPU 接纳；超出主机容量的任务单独运行。这些是接纳上限，不保证 GC 线程、实际 RSS 或外部负载。调用者在最后一个使用者结束后回收日志和恢复状态。

本地 UI 选择、菜单、显示配置、固定 CLI 流程和确定性业务 reducer 使用既有受控/生成实现测试。所有者文档须指明证据，并说明其不提供 TLC 穷举保证。保留核心在声明的抽象范围内覆盖共享身份、grant、提交/发布、不明结果、持久化和队列进展。

## CI 契约

- `.github/workflows/verify.yml` 安装冻结的 lockfile，并在 Pull Request、向 `main` 推送和手动运行时执行 `pnpm verify`。
- CI 传入 `--verbose`，让完整诊断在临时 runner 被回收后仍保留于现有 job 日志中；
  只有本地临时日志路径不能构成持久的 CI 证据。
- `rust-windows` Job 在 `windows-latest` 上运行 `pnpm verify:rust-native`，让每个 Rust 成员都在
  Linux `verify` Job 从不编译的 Windows 平台配置下执行 Clippy 和 Cargo 测试套件。格式、文档、
  TypeScript 与 TLA 检查与平台无关，仍留在 `verify` 中。
- 平台排除是显式的。macOS 没有 Rust Job，因为原生 Client 仅是未签名、按用户安装的 Apple Silicon
  开发 cohort；其原生 Terminal Host 和 Desktop endpoint 适配器在 `terminal-host-native` 中运行。
  任何 Job 都不运行 `test:cross` 或会抢占焦点的 `test:system:manual:native-window`；交叉编译保持显式，
  原生窗口测试保持仅手动运行。
- 必需的 `verify` Job 不运行 TLC。必需的 `tla` Job 从已跟踪清单中选择并运行变更触发检查；
  无关变更会在不配置 Java 或 TLC 的情况下完成该 Job。
- 工作流通过固定的官方工具链机制安装每个已跟踪原生 workspace 要求的精确 compiler version。
  直接下载的 archive 在加入 `PATH` 前必须校验 digest。
- 在仓库 ruleset 中要求工作流的 `verify` 和 `tla` Job。
- CI 在验证后运行 `git diff --exit-code`；已跟踪的生成变更在提交前会导致失败。
- 工作流使用只读仓库权限。
- 凭据、写权限、发布操作、外部检出和其他副作用需要单独人工审查，不得隐式进入必需 Job。

## 外部来源审计

- 生产构建使用的内容寻址原生源码依赖是已声明构建输入，不是外部来源审计。其不可变 URL 和摘要属于所属原生清单。
- 需要外部检出、凭据、服务、设备或未声明环境输入的包专属审计，继续作为所属包记录的显式维护命令，不属于 `pnpm verify`。
- 只有当独立 CI Job 固定并配置每个外部输入、拥有稳定所有者且不为必需合并门禁添加副作用时，才提升这类审计。

## 扩展阈值

分别测量逐阶段耗时和输出字节数、行数。比较时保持命令范围、工具链及冷缓存或热缓存条件等价；
输出更安静本身不代表运行更快。下面的阈值只允许启动设计审查，不授权跳过必需检查。

| 决策           | 契约                                                                   |
| -------------- | ---------------------------------------------------------------------- |
| 默认           | 有明确范围的改动使用按影响范围的本机验证；全量构建和交叉编译保持显式。 |
| 受影响任务阈值 | 至少三个可独立变更的工作区，或冷启动 CI 关键路径持续超过 30 秒。       |
| 变更前         | 先测量瓶颈。                                                           |
| 全局策略检查   | 即使包任务改为仅运行受影响项，也保留显式输入。                         |
