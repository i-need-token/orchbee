# 验证

## 合并门禁

`pnpm verify` 是唯一的本地和 CI 合并门禁。提交一个已完成的变更前，从仓库根目录运行它。它按顺序执行：

1. `pnpm format:check`
2. `pnpm lint`
3. `pnpm build`
4. `pnpm typecheck`
5. `pnpm test`
6. `pnpm test:exports`

迭代期间可以使用聚焦命令，但完成工作必须通过根级门禁。

## 必需任务

| 任务           | 契约                                                             |
| -------------- | ---------------------------------------------------------------- |
| `format:check` | 受格式化工具管理的文件与 `.oxfmtrc.json` 一致。                  |
| `lint`         | 代码、样式、存储、架构、依赖、项目契约、导出和清单规则全部通过。 |
| `build`        | 每个可构建工作区都生成其支持的产物。                             |
| `typecheck`    | 每个工作区都满足其 TypeScript 编译器契约。                       |
| `test`         | 契约检查器测试、自定义 lint 规则测试和每个工作区测试套件都通过。 |
| `test:exports` | 每个库的打包导出、运行时格式和声明均可被使用。                   |

构建先于类型检查，因为工作区库公开构建产物，验证和生产使用方不会编译另一个包的源码。递归构建采用拓扑顺序，因此全新检出会先生成依赖产物，再让依赖它们的工作区解析包导出。

应用开发不依赖库的 `dist` 目录。Rsbuild 的 source-build 插件会把已声明的工作区源码入口解析到开发图中，因此 `pnpm verify` 可以清理并重新构建包输出，而不会中断正在运行的应用开发服务器。验证和生产路径继续验证并使用按拓扑顺序构建的包产物。

## CI 契约

`.github/workflows/verify.yml` 安装冻结的 lockfile，并在针对主分支的 Pull Request、向 `main` 推送以及手动运行时执行同一个完整 `pnpm verify` 门禁。配置仓库 ruleset，要求工作流的 `verify` Job 通过后才能合并。

CI 会在验证后运行 `git diff --exit-code`。如果格式化工具、生成器或构建时一致性检查修改了已跟踪文件，验证就会失败，直到生成后的状态被提交。

工作流使用只读仓库权限。新增凭据、写权限、发布操作、外部检出或其他副作用都需要单独人工审查，不能隐式加入必需 Job。

## 外部来源审计

需要外部源码检出、凭据、服务、设备或其他未声明环境输入的包专属审计，继续作为由所属包记录的显式维护命令。它们不属于 `pnpm verify`。

只有当独立 CI Job 固定并配置了每个外部输入、拥有稳定所有者，并且不会给必需合并门禁添加副作用时，才能把这类审计提升到该 Job 中。

## 扩展阈值

只要必需门禁仍然快速，仓库就运行完整的工作区任务。只有在至少存在三个可独立变更的工作区，或者冷启动 CI 关键路径持续超过 30 秒后，才引入受影响任务编排。先测量瓶颈；即便包任务改为仅运行受影响项，全局策略检查仍需要显式输入。
