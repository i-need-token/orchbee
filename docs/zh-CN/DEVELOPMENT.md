# 开发

## 权威与范围

每项变更都从本标准开始。本标准管理范围授权、风险分级、审查与完成。当前权威管理已有行为；已接受的变更同步更新所属标准、契约、源码和证据。提案在整合前描述未来设计。

有权决策者的明确请求即授权范围内的完整结果，包括必要的调研、设计、实现、验证、常规修复和文档。要求执行一项可识别建议的指令即接受该建议。从对话与已有任务分配中还原此范围，不要重复请求同一项许可。

工具或模型能力不能替代正确性证据。根据受影响声明和失败风险，按照 [`MODELING-AND-CORRECTNESS.md`](MODELING-AND-CORRECTNESS.md) 选择建模和证据。它扩展本生命周期，不另建授权流程。

| 术语         | 契约                                                                                             |
| ------------ | ------------------------------------------------------------------------------------------------ |
| 当前权威     | 管理已有事实的所属标准、包内参考、源码契约或测试                                                 |
| 语义所有者   | 对某项行为、状态、契约或规则负责的工作区、包、模块或边界                                         |
| 决策所有者   | 由仓库所有权、任务分配或当前请求授权，可接受受影响结果或风险的个人或群体                         |
| 变更授权     | 约束一个完整结果的已接受结果、范围、限制、保留决策和证据义务                                     |
| 变更处理级别 | 根据行为、所有权和后果变化选择的工程处理强度                                                     |
| 受治理工件   | 影响行为、交付或证据的源码、测试、运行时资产、schema、迁移、配置、生成契约或当前权威文档         |
| 声明         | 可独立证伪的可观察规则或不变量                                                                   |
| 证据         | 能够判断一项声明的检查，以及它的环境、边界、假设和排除项                                         |
| 保留决策     | 已接受授权之外，会改变产品结果、公共边界、信任、持久数据、兼容性、外部副作用或必需证据的实质选择 |
| 委托决策     | 已接受结果、边界和风险限制内的实现选择                                                           |
| 可逆         | 替换时无需迁移、已发布兼容性变更，且不会留下外部副作用或持久数据后果                             |
| 接受         | 决策所有者对结果、建议或保留决策提出的可识别请求或批准                                           |
| 实质差异     | 对已接受结果、语义所有者、公共边界、风险、证据义务或排除项的改变                                 |
| 收敛         | 将完成的实现与证据同已接受结果及当前权威进行比较                                                 |

沉默、未回答的问题和现有代码模式不能授权新的保留决策。调研请求授权调研，不授权执行正在调研的变更。宽泛目标不能解决未提及的破坏性副作用或不兼容产品取舍。

从已有治理规则、任务分配和当前对话中确定决策所有权。仅当必要的保留决策无法确定有权所有者或已接受结果时才询问。暂停依赖该决策的工作，继续独立且已获授权的工作。

在现有对话、issue 或审查中保存范围、待决事项和证据，提供足以让其他读者还原已接受结果及限制的细节。不要仅为此流程创建受版本控制的授权文件、批准 manifest、平行规格框架或任务台账。持久提案遵循 [`DOCUMENTATION.md`](DOCUMENTATION.md) 和 [`REPOSITORY-HYGIENE.md`](REPOSITORY-HYGIENE.md)。

## 变更分级

首次受治理编辑前完成分级；新事实改变风险时更新分级。使用最高适用级别。级别决定工程处理方式，不会让已有授权失效，也不因实现进入下一阶段就要求重新批准。文件数量、作者信心和模型能力不能证明风险或正确性。

| 变更处理级别 | 触发条件                                                                               | 所需处理                                                           |
| ------------ | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| 机械性       | 结果由当前权威确定且不改变行为的编辑                                                   | 已知范围和相关检查                                                 |
| 有界         | 在已有所有权和契约内改变局部行为或展示，且后果有限、可逆                               | 明确请求结果、受影响行为和聚焦证据                                 |
| 建模         | 相互作用的转换、排序、共享状态、持久化、进程边界、所有权重分配，或需要明确不变量的协调 | 范围授权、最小有用行为模型，以及按风险选择的证据                   |
| 后果性       | 实质公共契约或兼容性变化、依赖方向、迁移、数据丢失、安全、隐私、外部成本或不可逆副作用 | 接受受影响取舍与风险，提供适用模型和证据，以及相关的发布或恢复方案 |

缺陷按补救措施的风险分级。当所有权、排序策略和副作用已有规定时，简单的局部异步完成或取消可以保持有界；异步语法本身不要求形式化模型。竞争性转换或新设计的恢复机制需要建模处理，后果性失败风险仍使用最高级别。

保持职责和契约的私有重构维持有界或机械性。移动文件、更新配套投影或涉及多个工作区，本身不会改变级别；改变其所有权、交互策略或公共契约才会。

## 变更授权

询问更多细节前，先从请求和现有权威中还原已接受决策。只记录影响结果、风险、协调或验收的字段。有界工作可以由请求加上简短的方法与检查说明满足要求。

| 字段     | 适用内容                                           |
| -------- | -------------------------------------------------- |
| 问题     | 角色、触发条件、可观察结果，以及当前行为不足的原因 |
| 范围     | 包含的行为、受影响所有者和非目标                   |
| 声明     | 相关不变量、失败、取消、无操作和兼容行为           |
| 边界     | 状态所有者、公共契约、依赖、外部能力和允许的写入者 |
| 决策权威 | 已接受取舍、真正未解决的保留决策，以及委托选择     |
| 证据     | 映射到声明的检查、假设、边界、环境和排除项         |
| 交付     | 适用时的集成顺序、迁移、发布、恢复和回滚           |
| 未知项   | 可能改变已接受结果或风险的问题，以及解决方式       |

存在多个合规实现方案属于正常委托工作。自行选择并解释合适方案，无须暂停。当选择引入授权未覆盖的实质产品、架构、兼容性或风险决策时，才展示替代方案。

## 受治理写入阶段

阶段描述交付所需的信息和工作，不是强制分开的回合或批准检查点。在已接受范围内可以合并或重新进入阶段。明确请求可能已经提供完成分级后继续执行所需的结果、接受和限制。

| 阶段       | 工作                                   | 受治理写入                                   |
| ---------- | -------------------------------------- | -------------------------------------------- |
| 分级       | 定位权威、范围、所有权和风险           | 建立适用范围与决策后允许                     |
| 调研       | 检查行为、复现缺陷并解决实现未知项     | 已接受范围内允许                             |
| 规格与设计 | 定义缺失声明、所有权、替代方案和证据   | 已接受范围内允许；未决保留决策仍阻塞相关工作 |
| 接受       | 与有权所有者解决新的保留决策           | 仅允许不依赖该未决事项的工作                 |
| 切片       | 在拆分有帮助时安排独立结果与真实依赖   | 已接受范围内允许                             |
| 实现       | 完成已接受行为、证据、适配器和常规修复 | 已接受范围内允许                             |
| 收敛       | 审查结果、更新权威、验证最终输入并清理 | 已接受范围内允许                             |

集成依赖的生产行为前，先明确行为和不变量。类型和测试可以承载建模记录，并与实现一起演进；不要求单独文档或先行的纯文档切片。未接受的设计草案不得成为当前权威。一次性实验在其结果被接受、审查并按相同生产要求验证后可以整合，不必仅因来源而重写。

调研发现新的保留决策时，只暂停依赖它的写入或副作用。继续独立且已授权的工作。已接受声明内的正常调试、测试修复和局部设计纠正，不重新启动授权。不得为未授权副作用补写批准，也不得把结果变化隐藏为实现细节。

## 决策权威

保留结果与风险选择，将交付已接受选择所需的实现委托出去。

| 已有授权之外需要接受的事项                                 | 已接受边界内的委托工作                                         |
| ---------------------------------------------------------- | -------------------------------------------------------------- |
| 实质产品结果、范围或用户可观察取舍                         | 满足请求结果的局部交互和实现选择                               |
| 公共契约、状态所有权、依赖方向、新包或依赖准入             | 算法、私有类型、辅助函数位置和内聚的局部重构                   |
| 持久数据、迁移、兼容性、安全、隐私、外部副作用、成本或删除 | 保持已接受风险限制的 fixture、适配器、失败处理、清理和常规修复 |
| 实质不同的架构或行为策略                                   | 在合规实现之间选择                                             |
| 后果性证据限制、信任假设或削弱必需检查                     | 按所属验证契约选择聚焦检查和复用有效证据                       |

实现者可以建议保留决策并提供证据，但必须在依赖工作前获得所需接受。现有标准可以约束多个有效实现；在这些实现之间选择，不会因此成为新的批准要求。

## 可审查拆分

默认工作单元是完整的可观察结果。同一所有者可以连续完成调研、设计、实现、测试、文档和修复。只为独立结果、真实依赖、分开的写入归属，或有助于交付的审查边界拆分。

每个切片在现有任务状态中指明结果、所有者、依赖和必要证据。把无关决策排除在范围之外，并留下已验证或明确分阶段的结果。直接继续下一个已授权切片；提交、检查、进度报告或内部阶段切换不要求新的指令。

区分分阶段基础能力和已集成的用户结果。扩展基础能力前，指明实际消费者和下一条可观察的集成结果。不要创建推测性基础设施或第二份进度台账。任务图服务于真实依赖，小型内聚任务无须人为拆分。

结构变化时应用[语义模块设计](MODULE-BOUNDARIES.md#语义模块设计)。执行切片不定义源码模块边界。

实施新的后果性决策前，必须进行一次新的只读设计挑战。对于建模工作，只有当具体未解决的所有权、交错或精化风险会导致后续纠正成本高昂时，才增加实现前挑战；否则在收敛前审查完整候选结果。只有相关事实变化时才重新审查已接受决策。

向挑战审查者提供范围、权威、拟定声明和证据计划，不提供作者的隐含推理。审查者报告发现，不批准保留选择。有独立上下文时使用它；否则披露限制并进行明确的对抗性阅读，不将其称为独立证据。

## 实现纪律

- 按 [`INTERFACE-DESIGN.md`](INTERFACE-DESIGN.md) 同时面向 GUI 和 TUI 设计产品能力。在实现任一投影前明确共同语义与适配映射；对于明确限定范围的例外或分阶段交付，记录所有者和完成条件，不得静默把单端完成视为整体完成。
- 只检索当前结果需要的权威和源码，复用未变化的材料。摘要用于指引检索，不替代必需的指令阅读或受影响文档对的语义审查。
- 组合准入范围内的产品界面前，遵循 [`frontend/experience-components.md`](frontend/experience-components.md) 的发现与复用要求。已有授权可以覆盖可见结果；新的保留产品决策仍需接受。
- 当 [`MODELING-AND-CORRECTNESS.md`](MODELING-AND-CORRECTNESS.md) 选择该方法时，独立于框架集成建立领域决策，并保持 [`frontend/react.md`](frontend/react.md) 的所有权边界。
- 交付最小完整结果。解决范围内结构风险，不引入推测性抽象、扩展点、包或无关工作。
- 在有用的反馈边界运行聚焦检查。相关输入未改变时复用有效结果；报告、提交或交接本身不构成重跑检查的理由。
- 保留并调查失败。不要用回退行为、宽松类型、禁用检查、重试到通过或扩大实现来掩盖范围或证据缺口。

与实现一起编写的测试只支持其声明和 oracle。通过不会让它们成为独立确认。针对实际风险增加所选择的性质、模型、系统或差异证据。

## 审查

在收敛前审查完整候选结果或可独立交付切片。重点关注变化的声明、所有权、公共边界、后果性副作用、证据缺口和剩余实现风险。根据结果调整细节，不重复未变化的设计审查。

说明哪些经过审查、机器检查、抽样或排除。不得暗示实际未发生的逐行审查或独立性。在同一任务内解决发现，只针对受影响风险增加审查或检查。在现有对话、issue 或审查中保存决策与结果，不创建受版本控制的流程工件。

## 收敛与完成

将结果同已接受结果及当前权威比较。为每项受影响声明指明实现和有意义的证据；只有建模契约要求时才保留详细可追踪性。发现不一致时，修复最早的错误所有者。

完成前：

1. 解决影响交付结果的偏离与新保留决策。
2. 更新事实发生变化的当前权威；类型和测试已拥有事实时复用它们。
3. 回收消费者已经结束的提案、研究、重复模型和临时工件。
4. 针对最终输入运行聚焦证据，以及 [`VERIFICATION.md`](VERIFICATION.md) 中适用的根门禁。如果必需门禁遗漏分配给它的证据，应报告验证契约缺陷，并在宣称完成前解决。
5. 报告交付结果、有意义的检查、限制和未解决风险。

完成要求授权结果、当前权威、实现和证据一致。代码数量、作者断言或不相关检查通过不能证明完成。
