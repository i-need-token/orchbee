# 开发

## 权威与范围

每项变更都从本标准开始；本标准是唯一的开发生命周期入口。每项变更都必须在编辑受治理工件前完成分级。本标准管理变更授权、分阶段写入权限、可审查拆分与收敛；它不定义产品或包的行为。当前权威继续管理已有事实。提案可以承载已接受的未来设计，但在其决策被整合进所属标准、契约、源码或测试前，绝不会成为当前权威。

当变更处理级别或当前权威要求行为建模或正确性证据时，应用 [`MODELING-AND-CORRECTNESS.md`](MODELING-AND-CORRECTNESS.md) 中所有匹配的要求。该标准在当前变更授权中补充模型和证据；它不会另行定义一套授权、写入阶段、审查或完成路径。

| 术语         | 契约                                                                                                                 |
| ------------ | -------------------------------------------------------------------------------------------------------------------- |
| 当前权威     | 管理已有事实的所属标准、包内参考、源码契约或测试                                                                     |
| 语义所有者   | 对某项行为、状态、契约或规则负责的工作区、包、模块或边界                                                             |
| 决策所有者   | 由仓库所有权、任务分配或当前请求授权，可以接受受影响结果、契约、边界或风险变更的个人或群体                           |
| 变更授权     | 约束一次变更的已接受问题、范围、非目标、声明、受影响语义所有者、限制、保留决策、证据义务与排除项                     |
| 变更处理级别 | 根据变更的行为、状态、所有权与后果触发条件选择的工程处理强度；它决定所需授权、建模、审查与证据                       |
| 受治理工件   | 影响行为、契约、交付或证明的源码、测试、运行时资产、schema、迁移、构建或验证配置、生成的契约或描述当前事实的权威文档 |
| 声明         | 变更必须建立或保持的、可独立证伪的可观察规则或不变量                                                                 |
| 证据         | 能够判断一项声明的检查，以及该检查的环境、边界、假设与排除项                                                         |
| 保留决策     | 会改变可观察行为、所有权、公共边界、依赖方向、持久数据、信任、兼容性、不可逆副作用或证据的选择                       |
| 委托决策     | 已受接受的变更授权与当前权威约束的可逆实现选择                                                                       |
| 可逆         | 可以在同一语义所有者内替换，且不需要迁移、已发布兼容性变更，不会留下外部副作用或持久数据后果                         |
| 接受         | 所需决策所有者作出的明确决定，其中指明被接受的变更授权或保留决策                                                     |
| 实质差异     | 会改变已接受声明、语义所有者、公共边界、风险、证据义务或排除项的差异                                                 |
| 收敛         | 将完成的实现与证据映射回已接受变更授权和当前权威的比较过程                                                           |

只有所需决策所有者明确接受后，变更授权才成立。接受必须能识别决策所有者，以及被接受的授权或保留决策。任务分配、沉默、未回答的问题、现有代码模式、最容易的实现，或者无法识别决策对象的笼统批准，都不代表接受。当前权威约束变更，但不授权改变它所管理的行为。

从仓库治理规则，或当前请求、issue、审查或提案中的明确说明确定决策所有权。语义所有权不能确定决策所有权。如果两者都没有确定所需决策所有者，则要求工作指挥者或仓库维护者在当前记录中确定该所有者。在此之前，保留决策仍未解决，受影响的受治理写入保持阻塞。

只有当不了解任务历史的读者可以从记录中还原已接受决策、决策所有者、未决问题和排除项时，当前对话、issue、审查或提案才能承载已接受的变更授权。满足这一条件时，不要强制创建受版本控制的授权文件。只有在满足 [`DOCUMENTATION.md`](DOCUMENTATION.md) 和 [`REPOSITORY-HYGIENE.md`](REPOSITORY-HYGIENE.md) 所要求的持久所有者与生命周期时，才把未来设计记录到 `proposals/`。任务过程、批准记录和临时计划留在仓库之外。

使用现有权威和当前协作状态。不要仅仅为了满足本标准而引入平行的规格框架、按变更生成的目录、批准 manifest 或流程依赖；这样做本身属于保留的架构决策。

变更处理级别的选择见[变更分级](#变更分级)，写入权限见[受治理写入阶段](#受治理写入阶段)，审查时机见[可审查拆分](#可审查拆分)与[审查](#审查)，完成条件见[收敛与完成](#收敛与完成)。

## 变更分级

只读调研期间，先根据当前信息选择所支持的最高变更处理级别，并在首次受治理编辑前定稿。调研或实现发现其他触发条件时，必须提高变更处理级别。最高处理级别控制授权门槛；所有适用的建模与证据义务仍会累积。表面上的简单程度、作者信心和变更规模都不能降低处理级别。

| 变更处理级别 | 触发条件                                                                                                     | 受治理编辑前所需的授权                                                                                         |
| ------------ | ------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------- |
| 机械性       | 结果已经由当前权威确定的精确且不改变行为的编辑                                                               | 已确认的范围、受影响当前权威和验证                                                                             |
| 有界         | 在一个现有所有者内改变可观察行为，加上由权威确定的配套所有者投影，但不新增公共边界、长期状态模型或后果性风险 | 已接受的紧凑变更授权，包含结果、非目标、声明、语义所有者、决策所有者和验证                                     |
| 建模         | 多状态、排序、层级、异步工作、取消、手势、持久化、进程边界、结构所有权变更或跨所有者协调                     | 已接受的变更授权，以及由 [`MODELING-AND-CORRECTNESS.md`](MODELING-AND-CORRECTNESS.md) 选择的适用建模记录和证据 |
| 后果性       | 公共或跨工作区契约、依赖方向、迁移、数据丢失、安全、隐私、外部成本或副作用、兼容性或不可逆风险               | 决策所有者对替代方案、后果、证据限制、发布和回滚或恢复的明确接受，以及每项适用的模型或检查                     |

缺陷不会仅仅因为预期结果明显就成为机械性变更。应根据补救措施改变的行为、所有权、状态和风险进行分级。不改变行为的重构在重新分配职责或创建新边界时转为建模处理级别。只呈现当前权威已有状态的展示变更保持为有界处理级别，除非它引入新策略、转换、写入者或可观察的状态含义。只有当当前权威分别确定每项投影，而且无需设计新的交互、共享状态、顺序、策略或契约时，跨配套所有者的日常编辑才保持为有界处理级别。

只有当当前权威无需作者判断就能确定确切结果及其验证时，才可以使用机械性处理级别。否则使用有界或更高处理级别，并取得相应接受。

## 变更授权

使用具体领域名称，并省略不可能影响已分级变更的字段。建模或后果性授权必须明确所有适用字段。

| 字段     | 必需决策                                                             |
| -------- | -------------------------------------------------------------------- |
| 问题     | 角色、上下文、触发条件、可观察结果，以及当前行为不足的原因           |
| 范围     | 包含的行为、受影响的语义所有者和精确非目标                           |
| 声明     | 可观察规则、不变量、失败、取消、无操作和兼容行为                     |
| 边界     | 权威状态所有者、公共契约、依赖方向、外部能力和允许的写入者           |
| 决策权威 | 所需决策所有者、由其接受的保留决策，以及留给实现的委托决策           |
| 证据     | 映射到声明的检查、信任假设、边界、环境和排除项                       |
| 交付     | 独立切片、集成顺序，以及适用时的迁移、发布、恢复和回滚               |
| 未知项   | 在受影响的受治理编辑前必须解决的未决问题、可行性风险和所需实验或决策 |

接受仅覆盖声明的变更授权。当仍有多个实质不同的有效结果时，应展示选项、后果和建议，而不是静默选择。

## 受治理写入阶段

写入权限由当前阶段决定，而不是由实现者生成代码的能力决定。

| 阶段       | 允许的工作                                                                       | 受治理写入 |
| ---------- | -------------------------------------------------------------------------------- | ---------- |
| 分级       | 定位当前权威、完成变更分级、识别语义和决策所有者，以及风险触发条件               | 禁止       |
| 调研       | 检查行为、依赖、历史、参考和测试；识别未知项、复现缺陷并运行只读检查             | 禁止       |
| 规格与设计 | 起草或修订变更授权、提案、未发布的建模记录、替代方案和证据计划                   | 禁止       |
| 接受       | 解决保留决策并记录所需决策所有者的接受                                           | 禁止       |
| 切片       | 构建依赖有序的任务图，每个单元只包含一个语义结果和独立证据                       | 禁止       |
| 实现       | 只编辑已接受的切片；适用时先添加其最低层证据，并在每项语义变更后运行聚焦检查     | 范围内允许 |
| 收敛       | 比较声明、设计、任务、实现和证据；更新当前权威、移除临时工件并运行适用的合并门禁 | 范围内允许 |

机械性工作在确认范围和验证后可以从分级直接进入实现。其他所有处理级别都需要接受的变更授权。在规格与设计阶段，把授权草案与建模记录保留在当前协作状态或一次性工作区；只有在仓库文档规则允许时，提案才可以受版本控制。在接受前，不得把草案发布到当前权威。对于建模工作，把已接受的建模记录持久化到其所属位置，作为第一个实现切片，并在此之后才能编辑依赖它的生产行为。调研 spike 必须保持一次性并位于受治理路径之外，除非后续接受的授权有意重新实现其结果。

当实现暴露新的保留决策、错误所有者、不受支持的声明或实质不同的风险时，必须立即停止受治理写入。返回拥有该问题的最早阶段，在那里修订权威、取得所需接受，然后使用新切片继续。绝不能补写计划来合理化已经编写的代码。

## 决策权威

审查注意力用于高语义杠杆决策；实现和证据工作保持在已接受边界内。

| 保留决策                                                                     | 委托的实现工作                                           |
| ---------------------------------------------------------------------------- | -------------------------------------------------------- |
| 产品结果、范围、非目标和用户可观察取舍                                       | 仓库调研、当前状态重建和歧义发现                         |
| 状态所有权、公共契约、跨所有者组合、依赖方向、新包和新依赖                   | 已由当前规则确定的私有命名、局部类型、辅助函数位置和实现 |
| 持久数据、迁移、兼容性、安全、隐私、外部副作用、成本、删除、恢复、发布和回滚 | 已接受边界内的确定性实现、fixture 和映射到声明的测试     |
| 在实质不同的架构或行为策略之间做出选择                                       | 保持已接受行为与所有权的可逆重构步骤                     |
| 后果性工作的声明、信任假设、证据限制和接受的排除项                           | 运行检查、缩减反例并报告证据，而不扩大受支持的声明       |

实现者可以建议保留决策并为其提供证据；在所需决策所有者接受前，建议不会成为权威。歧义不等于委托。只有当现有标准只允许一个合规结果时，它们才决定该问题。

## 可审查拆分

每个实现切片必须：

- 交付一个领域声明、转换组、契约边界、适配器能力或保持行为的结构步骤；
- 指明输入、输出、所有者、依赖、受影响声明和完成证据；
- 把不相关的保留决策排除在范围之外；
- 可被独立审查，并使仓库保持已验证或明确分阶段的状态；
- 在下一切片前停止，而不是顺便完成相邻工作。

按语义职责和反馈边界拆分工作，而不是按行数、文件数或框架类别。不要使用“实现功能”“重构 Hook”或“修复测试”这样的任务。任务图是执行状态，除非它有独立的持久消费者，否则应保留在当前工具、issue 或审查中。

建模和后果性工作在切片之后、实现之前需要一次新的只读挑战审查。审查变更授权、模型、任务图和证据中的歧义、矛盾、缺失声明、所有权泄漏、不受支持的假设，以及会引入新决策的任务。审查者报告发现；它不会静默重写权威或批准为决策所有者保留的选择。

只向挑战审查者提供已接受的权威和审查工件，不提供作者的隐含推理或可编辑的实现上下文。当无法使用独立上下文时，披露这一限制并执行明确的对抗性阅读；绝不能把它称为独立证据。

## 实现纪律

- 只检索当前切片需要的权威、模型、源码和证据。
- 在组合符合 [`frontend/experience-components.md`](frontend/experience-components.md) 准入信号的产品界面前，查询体验目录，检查可能匹配的 Manifest 与 Story 证据，并选择复用、扩展、替换或新建。新的或替代性的用户可见结构在决策所有者接受前仍是保留决策。
- 当 [`MODELING-AND-CORRECTNESS.md`](MODELING-AND-CORRECTNESS.md) 选择模型优先方法时，在框架集成前实现确定性领域操作。
- 组件和 Hook 必须遵守 [`frontend/react.md`](frontend/react.md) 的所有权边界；生产 UI 绝不能成为第一个或唯一的行为模型。
- 选择满足当前声明的最小完整变更；不要添加推测性的抽象、扩展点、包或兼容行为。
- 每项语义变更后运行最小的相关检查，并在继续前保留缩减后的失败。
- 立即报告发现的范围、权威和证据缺口。不要用回退行为、宽松类型、禁用检查、重试或扩大实现来隐藏它们。

与实现一起编写的测试，其证据强度只等于其拥有的声明和 oracle。测试通过并不会让它们自动成为独立确认。对于高风险逻辑，使用 [`MODELING-AND-CORRECTNESS.md`](MODELING-AND-CORRECTNESS.md) 所选择的额外性质、模型、系统或差异证据。

## 审查

按以下顺序展示审查材料：

1. 保留决策和未决问题；
2. 可观察声明、不变量、状态转换和所有权；
3. 公共边界、依赖变更、迁移、发布和回滚；
4. 声明到证据的映射及已知限制；
5. 仍涉及信任、并发、不可逆副作用或非显然精化关系的实现热点；
6. 由已接受契约和可执行证据覆盖的机械性实现。

绝不能暗示实现已经被逐行审查。应说明哪些内容经过审查、哪些由机器验证、哪些被抽样，以及哪些仍被排除。如果一个审查单元必须重建多个不相关所有者才能理解，应返回设计阶段拆分职责，而不是继续添加代码。

在最终收敛前，或在合并每个可独立交付的切片前，执行实现审查。把接受、挑战审查发现与完成报告记录在当前对话、issue 或审查中；不要仅仅为了保存这些记录而创建受版本控制的流程工件。

## 收敛与完成

收敛是先读取再比较的过程，不是扩大实现的许可。对每项已接受声明，识别其所有者、实现、可执行见证、结果、边界和排除项。把每项不一致分类为权威、规格、设计、任务、实现、适配器或证据缺陷，并修复最早的错误所有者。

完成前：

1. 解决每项偏差和新的保留决策，或取得相应接受；
2. 当所属当前权威管理的事实已改变或权威不完整时更新它；否则报告无需更新权威；
3. 满足每项提案或调研工件的退出条件，并删除持久职责已经结束的工件；
4. 移除临时计划、脚本、报告、fixture、标志和重复模型；
5. 运行聚焦证据和 [`VERIFICATION.md`](VERIFICATION.md) 中适用的根门禁；如果当前权威把选中的证据分配给某项必需门禁或 CI 检查，但配置后的检查实际没有运行它，则报告验证契约缺陷并阻塞完成，而不是削弱证据计划；
6. 报告已检查声明、决策、证据、边界、排除项和剩余风险。

完成意味着当前权威、实现和证据在有明确边界的声明内一致。仅有 lint 通过、代码数量、文件检查、截图或作者断言绝不能证明收敛。
