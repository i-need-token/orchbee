# Windows Worktree operations

This record owns native CLI Worktree creation, opening, removal and recovery. Git effects belong to the Windows Worker; the Server owns retained operations and canonical Workspace association. The CLI waits for observations and never runs Git itself. `worktree list` supports source-based discovery and preserves its existing registered-directory query contract.

## Commands and defaults

Git checkout creation suppresses progress. Bounded stderr retains the final 2048 bytes so the failure cause survives large diagnostics. A failed partial Create resumes by observing its original path, never by replaying `git worktree add`. If that observation proves the checkout absent, the operation becomes nonresumable. Inspect the retained branch and Git error, then submit a new Create after correcting the cause; the CLI does not delete the branch or silently retry effects.

```powershell
orchbee worktree create --project demo --cwd C:/code/demo --branch feature/example
orchbee worktree open --project demo --cwd C:/code/demo --branch feature/example
orchbee worktree remove --workspace example --confirm
orchbee worktree status <operation-id> --format json
orchbee worktree resume <operation-id> --generation <attempt> --confirm
```

Create and Open accept either `--workspace <target>` or `--cwd <path>`. Without either, source selection follows the Client/caller rules below; CLI cwd is used only when neither exists. A partial, stale or invalid caller identity never falls back to cwd. Only Directory sources accept optional `--project <target>`; Workspace sources and Remove always submit required-nullable `projectId: null`. The server atomically creates a Project for an ungrouped Workspace source and the new peer, or reuses its existing group. Linked source Workspaces create peers too. A Directory source without an explicit Project creates an ungrouped Workspace. No CLI Project setup phase runs.

Create accepts optional `--branch`, `--base`, `--path` and `--label`. The default branch is `worktree/<full-operation-id>`, base is `HEAD`, and path is `<main-repository-parent>/<main-repository-name>-worktrees/<branch-slug>`. The slug replaces characters outside ASCII letters, digits, `_` and `-` with `-`; an existing path is never overwritten. Existing local branches ignore the base. Open requires exactly one `--path` or `--branch`; ambiguous branches require a path. Both main and linked checkouts may be opened. An existing single Workspace associated with the selected checkout is reused globally; `--label` also renames it. A new association creates a Workspace and launches its first default-shell terminal. The optional four geometry flags follow `tab create`; a committed Workspace with failed or unknown terminal startup remains visible in the result.

Remove requires `--workspace` and `--confirm`. It checks registration, common Git directory and dirty state before closing the Workspace. `--force` explicitly permits Git to discard checkout changes. Main/bare checkouts and checkouts associated with another known Workspace are refused. Successful removal preserves the branch. There is no recursive filesystem deletion fallback.

`--trust-repository` grants command-local Git trust without changing global or repository configuration. Windows Worktree `--cwd` and create/open `--path` accept absolute drive paths, relative paths anchored to the final executing CLI current directory, and a leading `~`, `~/` or `~\`. Absolute spellings are preserved. Home expansion selects nonempty `USERPROFILE`, then `HOMEDRIVE` plus `HOMEPATH`, then `HOME`; a selected malformed home fails and never falls back. Complete grammar and machine routing precede context resolution. The sender and relay preserve raw operands; only the final executing CLI reads these variables for an explicit home operand, never the Worker. Resolution failures precede request identity, configuration, signal ownership and runtime access. Inputs and expanded UTF-8 paths are bounded at 4096 bytes. No file is opened or canonicalized during path resolution, so a new checkout path need not exist. Unsupported UNC/device namespaces and drive-relative paths are refused. Invalid raw path syntax is refused before reading home or current-directory context. Shell, wildcard, `$VAR` and `%VAR%` substitution never occurs; those characters in ordinary components remain literal. Other commands retain their declared path policies. Source paths may point inside a checkout. Reference operands are nonempty, at most 1024 UTF-8 bytes, and cannot start with `-` or contain ASCII controls. Git validates branch syntax. Create and Open optionally focus an existing Client with `--focus`; the default is `--no-focus`. Mac/Linux mutation execution and Desktop command exposure are outside this Windows implementation.

## Waiting and machine output

All operations emit `orchbee.worktree.operation` v5, with nullable original requested Project metadata and no `setup` phase. `Available.projectId` describes the original request, not the Workspace's current grouping. Known/unknown operation identity and partial Git/terminal truth survive later failure. See the [Workspace creation model](windows-workspace-creation.md).

Create, Open and Remove accept a caller-provided nonzero 32-lowercase-hex `--request-id` or generate an operation identity before submission. Exchange request IDs are separate. Equal identity and intent observes the retained operation; changed intent conflicts. `--detach` returns the first accepted observation. Default CLI waiting is 120000 ms; `--timeout` accepts 1–3600000 ms. Each exchange is bounded at two seconds and polls are separated by 50 ms. Timeout, Ctrl+C or connection loss stops waiting; accepted Server work continues. The CLI submits Start or Resume once and follows only with Read. An uncertain handoff is never automatically replayed.

`worktree status` is a pure read with a five-second total budget and does not activate the Session or start maintenance. `worktree resume` requires the exact `attempt` from a resumable failed status, supplied as `--generation`, and `--confirm` because the retained intent can remove user work. Attempt numbers range from 1 to 64. Records survive Client disconnection but not Server restart.

The `orchbee.worktree.operation` v5 envelope is registered in `api schema` catalog v143. It contains the operation ID, local Session identity when known, a correlated Server reply or explicit unavailable/unknown observation, and a separate nullable waiting disposition. Pending and detached observations exit 0; terminal launch failures retain their own nonzero exit; Git or association failures exit 3, unavailable admission exits 4, lost connection exits 5, internal or inconsistent observation exits 1 while retaining the last reply, timeout exits 7, physical/submission uncertainty exits 8, and cancellation exits 130. Parsing and pre-submission target failures use the existing CLI failure envelope. Raw bounded Git diagnostics remain byte arrays in JSON and are escaped in localized text.

## Source and post-open focus model

Source-form List, Create and Open accept an exact `--client`. An explicit Workspace/cwd takes precedence and ignores unrelated caller environment. Otherwise an explicit Client overrides the caller; without it, use a validated caller, then a unique current ready Client, then CLI cwd only when both caller and Clients are absent. Invalid callers and stale, unavailable or ambiguous Clients fail before Git, without cwd fallback.

The CLI prepares the source; Server remains the only Worktree/Workspace writer. Every Workspace source retains its globally stable Workspace ID, and Server validates its canonical primary Directory. Missing identity or directory fails before Git; a Panel's process cwd cannot substitute for Workspace ownership. Explicit Directory sources may choose an existing Project; no group is inferred from a sole Project. Remove retains its explicit Workspace contract. Configured checkout paths belong to [Windows CLI configuration](windows-cli-configuration.md).

Create and Open accept mutually exclusive `--focus` and `--no-focus` (default). Focus rejects `--detach`, requires an existing ready Client, and never launches a TUI. Remove, Status and Resume reject Client/focus flags.

| Transition                                                         | Guard and observable result                                                                                                                            |
| ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Preflight                                                          | Pin one ready Client and its semantic selection before Git                                                                                             |
| Known Opened with Started terminal or reused Workspace             | Read fresh same-Session snapshot and exact Client; require unchanged semantic selection and global Workspace membership independent of current Project |
| Submit focus                                                       | Use fresh view revision and canonical revision for one existing Context intent; wait for rendered/seen acknowledgement                                 |
| Selection changed, disconnected, rejected, timeout or cancellation | Stop focus; retain canonical operation and Workspace identity; never roll back or replay Git                                                           |
| Uncertain focus handoff                                            | Preserve Client receipt; never automatically resubmit                                                                                                  |
| No focus requested                                                 | Keep v5 output and canonical waiting behavior                                                                                                          |

Semantic selection is context, Tab, Panel and zoom identity; derived panel counts and ordinary revision refreshes are not navigation changes. Focus shares the invocation deadline and bounded exchanges. Explicit focus uses `orchbee.worktree.operation` v5 with a separate `postOpen` receipt: Client ID, stage, focus receipt, failure, and completed/incomplete outcome. Canonical success survives focus failure, which produces a nonzero exit. This is not an atomic Git/UI transaction. Server work survives CLI disconnection; focus is invocation-owned and is not resumed by `worktree resume`.

Deterministic source/guard cases, grammar conflicts, versioned schemas and scripted Windows IPC traces cover precedence, missing cwd, ambiguous/stale selection, changed views, post-submit uncertainty and partial outcomes. Disposable real Windows Git queries cover the unchanged Worker boundary. Full two-TUI acceptance is separate; bounded same-author checks do not prove every live race. Reference: Herdr `e0507237ad8d41f60aece10d00ef29ce2339ca34` Worktree source/focus semantics.

## Retained continuation

| State or event     | Admission and next step                                                                              | Retained truth                                                                         |
| ------------------ | ---------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| Start              | Exact Session grant, optional Project, source and Worker incarnation; one pending operation globally | Intent and operation ID before Worker handoff                                          |
| Create             | Observe source, create with Git, verify checkout and branch, attach Workspace                        | Candidate path and possible Git effect survive failed verification                     |
| Open               | Observe the selected checkout, reuse or create its Workspace                                         | Canonical Workspace identity and terminal launch outcome                               |
| Remove             | Inspect first, hold Workspace publication, dispose terminals, remove with Git, publish Close         | Canonical layout survives Git failure; verified recovery launches fresh default shells |
| Resume             | Same intent and Worker incarnation, exact failed attempt, explicit eligibility                       | New fenced attempt; old callbacks cannot overwrite it                                  |
| Read or disconnect | Read retained state only; disconnect does not cancel continuation                                    | No duplicate Git or Workspace creation                                                 |
| Session stop       | Stop and join the retained submitter before Close maintenance and Worker freeze                      | Cancellation is not rollback; Worker owns physical settlement                          |

The Server retains at most 64 operations and permits at most 64 attempts per operation. Worker jobs have their separate retained 64-admission bound. A continuation has a cooperative 120-second work budget; each Git step is bounded at 40 seconds, while the Worker owns its 30-second execution and five-second physical cleanup budgets. Reads and duplicate observations remain available when fresh admission fills. Unknown physical or transport settlement is not resumable. A Create with possible Git effects resumes by observing its retained path and branch rather than issuing another Git add. Remove retains canonical layout until known Git success. Its exact Close publication is held after terminal disposal and cleanup; Unknown deletion retains that hold and the existing structural fences. A known Git failure starts the shell recovery below. Resume re-inspects from the retained repository root; it reuses a held Close or captures a fresh Close after shell recovery. After a failed Worktree, explicit ordinary Workspace Close can release the hold without Git; while pending it returns busy. A known successful Git removal is retained before releasing publication, so retries of final Close never repeat Git. Workspace, Tab and Panel identities survive recovery; Presentation and physical terminal identities are replaced together.

## Shell restoration after failed removal

After a returned Git removal failure, a read-only inspection must prove the original checkout path, common Git directory and repository root still match. A failed verification retains the closed terminal bindings and publication hold; no shell starts. After successful verification the Server restores each captured native primary presentation, with a fresh default-shell binding, checkout cwd, empty custom environment and initial 80×24 geometry. Existing layout, labels and navigation identities remain unchanged. Old Agent commands, custom programs and launch profiles are never replayed. Existing native Close still rejects child presentations and grouped/pinned Tabs before effects; restoration does not broaden that membership contract.

Each replacement is reserved in the canonical projection and TerminalCoordinator before IPC. The old Close remains fenced while serial launches settle. Completion records known success, known failure or uncertainty without repeating a launch. The old Close then ends with nonresumable `workspace-retained`; its old-binding tombstones remain, while current structure becomes usable and a new Close captures fresh bindings. A partial recovery can leave unattempted disposed bindings or failed new shells. Unknown launches forbid Remove Resume. Other eligible failures can explicitly retry deletion, including closing the restored shells first. Session shutdown preserves partial truth; it does not resurrect disposed processes.

All new progress observations use `orchbee.worktree.operation` v5; the schema keeps closed v1–v4 documents for older consumers. The separate `progress.restoration` receipt contains `total`, `attempted`, `started`, `failed`, `unknown` (each 0–4096) and nullable `failure`. Completed counts cannot exceed attempted, attempted cannot exceed total, and at most one serial launch is pending. Final receipts have no pending launch. The original Git error remains the operation failure; verification/preparation failures stay inside restoration. Exact per-presentation binding and Create outcome are available from the canonical and terminal queries rather than copied into this bounded 96 KiB operation document. Text output reports all counts and the extra failure in both locales. Any unknown restored launch exits 8; known Git failure remains exit 3.

Registry-to-Session locking protects admission and canonical checks; IPC occurs outside both locks. While Remove is pending, new Workspace launches and primary-directory admissions are reserved globally. Existing associations are rechecked before close and deletion. These checks do not exclude arbitrary external Git/filesystem writers or constitute a filesystem transaction. Terminal outcomes are immutable once published. Maintenance owns its thread and explicitly joins on Session shutdown; Drop only requests cancellation.

## Source-based discovery

`worktree list --workspace <target>` and `worktree list --cwd <path>` select one source, with optional `--trust-repository`. With neither selector, the Client/caller rules above apply. An exact `--client` is also accepted. Invalid caller identity never falls back. Listing needs no Project, creates no Workspace and changes no focus. The registered-directory form is now `--directory <id>` alone and uses `orchbee.worktree.list` v2 without Project identity; the source form uses `orchbee.worktree.query`.

Source queries use a five-second total CLI budget, do not activate a Session, and never replay an exchange. The source and legacy selector sets are mutually exclusive. JSON emits `{schema:"orchbee.worktree.query",version:2,result:<typed-reply>}` from catalog v143; a Server failure remains a typed reply. Exits are 0 for Found, 3 for missing/denied/changed source or Git failure, 4 for unsupported/unavailable, 5 for transport/malformed listing, 7 for timeout, and 1 for I/O/spawn/output-limit failure. Pre-admission/transport failures use the generic CLI failure schema; Ctrl+C exits 130 after releasing the signal owner. Human text escapes untrusted paths/labels and labels main/linked, detached/bare, locked/prunable and Workspace identities.

The Server resolves the source and live Worker incarnation, releases all gates during Git IPC, then rechecks both before publishing. One read-only Worker job observes the common Git directory, source checkout root and porcelain listing. Command-local trust applies only to the selected canonical repository, without persistent configuration changes. Admission checks only drive-path syntax. Filesystem canonicalization and trust preparation run inside the owned task, followed by cancellation/deadline checks before child creation; missing directories return a typed preparation failure. OS filesystem calls are cooperative, not forcibly preempted. The read owner retains its five-second budget, one physical slot, bounded output and sixty-second receipt; it consumes no mutation-operation capacity. Windows Git drive paths pass the same absolute-path validation as other Worktree entries.

The result reports the main repository root, common directory, source checkout, Git entry facts and known canonical Workspace associations. Multiple associations remain explicit, never an arbitrary first Workspace. Each association has required-nullable `projectId`; text displays ungrouped Workspaces explicitly. Explicit source-Workspace membership is supported by its own Git observation; other associations require a known matching checkout path. This is an observation of Git followed by a canonical membership check, not an atomic filesystem transaction or proof about unknown path aliases.

| Transition                          | Requirement                                   | Result                                          |
| ----------------------------------- | --------------------------------------------- | ----------------------------------------------- |
| Admit                               | Valid read policy, source and live Worker     | Capture source membership and Worker generation |
| Observe                             | No coordinator/registry gate held             | One bounded read-only Git job                   |
| Recheck                             | Same source membership and Worker incarnation | Join current known Workspace identities         |
| Source or Worker changes            | Do not reuse the old observation              | Explicit failure                                |
| Timeout, cancellation or disconnect | Worker retains physical cleanup ownership     | No mutation and no inferred success             |

Strict request/result and binary-frame checks, shared Rust/TypeScript fixtures, source subdirectory/linked-checkout cases, denied trust, source/Worker changes and real Windows CLI reads provide evidence. Legacy listing remains covered independently.

The Windows path adapter is a bounded pure transformation over explicit environment and current-directory inputs. A resolved relative or tilde operand is normalized lexically, as Windows does: `.` is dropped, `..` removes one earlier component but never the drive root, and no trailing separator remains; absolute literals are kept verbatim. Text output shows Git-reported paths with native separators, and a probe-stage Git failure says the directory is not a Git repository or Git does not trust its owner. Tests cover unused environment/cwd isolation, UTF-8 and 4096-byte bounds, ambiguous roots, no filesystem probing, and redacted resolution errors before configuration or runtime access. Pure parsing retains all four explicit path slots; injected capabilities verify target-before-source resolution and unchanged selection, identity, geometry and wait policy. `cli_windows_machine_routing` checks raw routed operands, grammar-before-context, machine-selection and relay admission. `cli_windows_worktree_context` checks complete typed Create/Open intents and List source under separately supplied final-process home and cwd. Actual Windows Git query/create/open exercises relative and tilde operands. This is bounded parity evidence, not a claim about every Windows filesystem alias.

## Project close-all

Ordinary `workspace close <target> --confirm` closes only the selected Workspace, including a main-checkout Workspace with linked peers. It does not delete a checkout or branch. `project close-all <target> --confirm` explicitly closes the current members of one organizational Project, even when they span repositories. The Project remains after closure; `project dissolve <target>` is a separate metadata action that ungroups and retains all Workspaces.

Admission freezes at most 256 exact Workspace IDs in global navigation order. Empty Projects are valid. Newly added Workspaces are not silently included. Each captured child is handed to ordinary Workspace Close; grouping and checkout ancestry do not broaden that scope. A changed or unavailable member produces retained partial truth. Closed terminals are not resurrected.

The native `workbench.workspace-group-close` operation now means one Project. Start carries `operationId` and `projectId`; results carry `projectId`, attempt, status and members, each with `workspaceId`, label and a required-nullable child Close. No source Workspace or per-member Project ID is present. Child request identity is retained before waiting; null `close` means unsubmitted, while null child `observation` means accepted but unobserved. Unknown or unobserved effects never authorize replay. Results are bounded at 1 MiB, membership at 256, and attempts at 64. Equal identity/scope observes retained truth; changed scope conflicts.

```powershell
orchbee project close-all <project> --confirm [--request-id <id>] [--detach] [--timeout <ms>]
orchbee project close-status --request <operation-id>
orchbee project close-resume --request <operation-id> --generation <1..64> --confirm [--detach] [--timeout <ms>]
```

Start/Resume use one total budget (default 120000 ms, allowed 1–3600000); status is a five-second read. CLI submits one mutation and then only reads, checking the same attempt and captured child identities. Detach, timeout and Ctrl+C stop waiting while Server continuation remains responsible for accepted work. Resume is explicit and only available for a known eligible failure. Records survive CLI disconnection, not Server restart.

`orchbee.project.close-all` v1 separates retained Server truth from nullable wait disposition. Pending/Closed exits 0, known refusal/failure 3, unavailable/Worker loss/Session stopping 4, unknown 8, inconsistent/internal observation 1, and interrupted waiting transport/timeout/cancellation 5/7/130 with the last reply preserved. It is distinct from ordinary `orchbee.workspace.close-status` v2, whose stable Workspace selector no longer needs Project identity. Offline help, completion and `--skill` declare both forms; retired `workspace close --group` is rejected.

Grammar, exact-effect process tests, empty-membership and partial/unknown schema tests cover the CLI contract. Server and real-terminal acceptance own captured membership execution, physical terminal cleanup and preservation of Git paths/branches. These bounded tests do not claim an atomic Git/UI transaction or exhaustive races.
