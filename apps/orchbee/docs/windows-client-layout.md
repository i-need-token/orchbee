# Windows Client Panel geometry

This reference owns native Windows CLI inspection of a live TUI Client's Panel layout. The TUI owns viewport, chrome, focus and zoom. Server routes requests and retains bounded observations; canonical Workbench topology remains authoritative for membership. A layout read never selects a context or Tab, attaches a terminal, changes zoom, or resizes a terminal.

## Observation

A query names an exact Client, TerminalContext, Tab and source Panel and a minimum Workbench revision. The existing authenticated Client lane reads one cancellable canonical Snapshot before handing the request to the UI. An unavailable Snapshot or missing target produces an explicit failure. The UI uses that Snapshot to project the target without installing it as the active context. It rejects a Snapshot older than the requested minimum. For the selected Tab, geometry uses the current rendered membership cache and its revision; if that cache has not reached the requested minimum, the read fails explicitly rather than refreshing membership and causing terminal resize effects. Inactive targets use the fetched Snapshot as an explicitly unselected projection.

The result identifies the target and canonical revision, the sampled cell viewport and terminal area, whether the target Tab is selected, its local zoom flag and required nullable focused Panel. Unvisited and inactive contexts are readable. Inactive targets use the Client's surviving remembered Panel, falling back to the first member, as defined by [selection memory](native-context-selection.md#client-selection-memory). This local focus does not make the Tab selected; the `selected` flag retains that distinction. An inactive Tab's geometry is a projection into the sampled viewport, not a claim that it is currently painted.

Every canonical Panel has required nullable unzoomed outer, unzoomed terminal-content and displayed terminal-content rectangles. Null means the renderer does not place that Panel in that layer. Zoom preserves unzoomed geometry and gives only the focused Panel a displayed full-content rectangle. Minimal viewports expose the renderer's single-Panel fallback. Too-small viewports return no fabricated geometry. Splits report stable split/slot identities, orientation, the rendered ratio and required nullable area/divider rectangles. Canonical traversal order is retained.

All rectangle positions and sizes are integer cells. Chrome, frame lines, the shared divider, minimum-size collapse and odd-cell rounding come from the same projection used for drawing and terminal sizing. Terminal pixel dimensions do not affect cell adjacency.

## Neighbors and edges

Navigation uses unzoomed outer leaf rectangles, not content rectangles shortened by titles and not normalized topology coordinates. Candidates must lie completely in the requested direction and overlap positively on the perpendicular axis. Ordering is smallest edge distance, largest overlap, smallest doubled-center distance, then canonical traversal order. Arithmetic widens before adding coordinates. Empty or hidden source geometry is explicitly unavailable.

The observation carries four nullable source neighbors. Directional edges compare the visible unzoomed source rectangle against the terminal area boundary, matching the reference physical-edge handler. No-neighbor and physical-edge are distinct facts. A hidden source has no edge claim. Zoom does not erase an otherwise valid unzoomed neighbor. The adopted navigation ordering is pinned to Herdr `e0507237ad8d41f60aece10d00ef29ce2339ca34`, `src/layout.rs::find_in_direction`; native chrome and degradation remain Orchbee's contract. Orchbee widens doubled-center arithmetic across its admitted coordinate range; the reference's u16 center saturation at very large coordinates is not adopted.

## Routing, lifetime and bounds

Layout is a read intent on the existing Client control route, with a distinct layout-read completion and retained status. It inherits exact Client/caller selection, operation identity, freshness, one delivery, queued expiry, disconnect settlement and caller timeout/cancellation behavior from [Client view control](windows-client-control.md). A read result cannot acknowledge a navigation or zoom command, and ordinary applied success cannot acknowledge a layout read.

The UI captures its observation in one tick after validating the target Snapshot. The result describes that point in time; later resize, input or topology changes do not rewrite the receipt. No successful draw is claimed for an inactive Tab. Local interruption before observation rejects the query. Snapshot I/O remains off the UI thread, has an owned deadline and wakeable shutdown, and never performs an automatic retry.

Dedicated OBWP frame kinds 27/28 carry layout completion/results and are bounded to 1 MiB before allocation; ordinary Client frame kinds 25/26 retain their 16 KiB/64 KiB pre-allocation limits; existing ordinary request and small-result bounds remain enforced for their actions. Combined Panel and split entries cannot exceed the canonical 4096-node context bound; identities are unique and all focus, source and neighbor references must resolve. Rectangles stay inside the sampled viewport and the relevant content area.

Server reserves 1 MiB from a 16 MiB encoded-layout budget before queuing each query. Completion replaces that reservation with the bounded encoded observation size. Rejection, disconnect without a result and receipt expiry release the reservation. Existing 256 total receipts and 60-second completed retention still apply. Capacity refusal occurs before delivery; pending or unexpired results are never evicted to make room.

## CLI and evidence

`panel layout`, `panel neighbor --direction left|right|up|down` and `panel edges` accept a positional Panel or exclusive `--panel` / `--current`, with the existing Client selection rules for geometry. Explicit `panel layout <panel>` without
`--client` instead reads canonical topology and ratios headlessly (`orchbee.panel.structure` v1,
`scope:shared`); it contains no viewport, focus or zoom claim. Add `--client` to request geometry.
All three reads reject `--request-id` and `--detach`. Parsing finishes before connection or effects. Machine output preserves the full layout observation and a required nullable `projection`: neighbor results carry direction, source availability and a nullable neighbor ID; edges carry source availability and four nullable physical-edge booleans. Projection is null until a layout result arrives; hidden source edge booleans are null. Text output presents the requested projection without hiding unavailable geometry.

Evidence covers exact chrome/rounding/minimum geometry, nested and degenerate trees, independent neighbor-order vectors, generated hierarchy invariants with reduced replay, inactive and unvisited targets, no selection/attachment/resize side effects, two-Client isolation, stale membership, snapshot failure, bounds, capacity, interruption and shutdown. Rust, TypeScript and JSON Schema share a conformance corpus but have independent validators. Controlled Windows TUI traces connect these contracts to a real display. Shared ratio commit/publication/draw checks use the implementation evidence below; no separate layout workflow TLA model remains. Same-author checks do not constitute independent review.

Directional focus uses this projection before navigation, as specified in [Client view control](windows-client-control.md#directional-panel-focus). Ratio mutation follows the contract below; swaps and layout import/apply remain separate capabilities. The extension is additive within exact cohort admission; shared ratios use the upgraded durable admission boundary; view/control observations and receipts remain volatile.

## Split ratio adjustment

`panel resize` adjusts the nearest eligible split around an exact or current source Panel. It requires a cardinal direction; the finite amount defaults to `0.05`, becomes absolute and is capped at `0.5`. `layout set-split-ratio` accepts exclusive `--tab`, `--panel` or `--current` targeting, a binary split path (`root` or dot-separated `0`/`1`, at most 16 steps), and a finite ratio clamped to `0.1`–`0.9`. `panel resize` uses the existing exact Client route, operation identity and deadline.
Explicit `layout set-split-ratio --tab/--panel` without `--client` uses the Server CAS directly,
returning `orchbee.layout.ratio` v1 with shared scope and retained request/result. It requires no
Client and preserves unknown mutation outcomes; `--request-id` is optional, `--detach` is rejected.
Implicit/current targets or explicit `--client` retain the Client route and draw acknowledgment. Parsing precedes connection or effects. Missing paths and hidden resize sources fail explicitly. Setting a ratio may target a hidden split without inventing focus.

Server owns each split's nominal ratio in the canonical Workbench tree. Every Client projects the same ratio at its own viewport size; focus, zoom and terminal control remain local. New splits default to `0.5`; retained subtrees keep their ratios. See the [shared ratio contract](../../orchbee-server/docs/shared-split-ratios.md) for atomic mutation and current version 1 checkpoint/catalog admission.

Drawing, terminal sizing, pointer regions and layout reads consume one weighted tree projection. Each split resolves its nominal ratio once against the axis extent minus the shared divider cell, rounds the first extent to the nearest cell (half upward), and clamps it so both children's documented minimums fit. Otherwise the existing active/first-leaf collapse applies. The nominal ratio remains observable even when minimums or integer rounding constrain the cell result. Border titles, zoom and chrome retain their existing owners.

Resize uses visible unzoomed source cells. Eligible dividers share the requested axis, positively overlap the source on the perpendicular axis and lie within one cell of the requested edge. The nearest distance wins, with canonical traversal breaking ties; if none exists, inspect the opposite edge. Right/down adds the amount, left/up subtracts it, then clamp to the supported ratio range. No eligible split is an explicit no-op. This policy adopts Herdr `e0507237ad8d41f60aece10d00ef29ce2339ca34`, `src/layout.rs::resize_focused`; native cell chrome, minimums and widened arithmetic remain Orchbee's. Native numbers use finite f64 rather than the reference's f32. Reference comparisons cover the border choice on native geometry, not identical reference rendering or persistence.

The UI resolves one adjustment against its rendered cache and an admitted full Snapshot. Explicit paths and resize borders must address the same split, ordered slots and previous ratio. An optional `expectedSplit` additionally pins all three identities for creation workflows. The worker submits one canonical `layout.set-split-ratio` command with the exact revision and previous ratio. Server rejection is explicit; neither Client nor CLI retries automatically. No optimistic local ratio write occurs.

`splitRevision` now reports the full-width canonical Workbench revision of the Client's projected cache. It advances when shared publications arrive, including unrelated metadata changes. It is neither a separate ratio counter nor evidence that an inactive target has been drawn. A retained completion keeps its captured observation.

| Condition                                                                | Commit and acknowledgement                                                                                                                |
| ------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------- |
| No eligible resize split or unchanged ratio                              | `layout-adjusted` without a canonical write, terminal resize or requested draw                                                            |
| Changed inactive or unvisited Tab                                        | Await Server commit, then acknowledge without selecting, attaching or drawing that Tab                                                    |
| Changed selected Tab                                                     | Await commit and shared publication, re-observe geometry, invalidate pointer regions, then acknowledge after a successful compatible draw |
| Validation, capacity, stale revision/previous ratio or replaced identity | Reject; preserve current state and require a new explicit operation                                                                       |
| Unknown submission, interruption, expiry or failure after submission     | Incomplete; no rollback claim or automatic replay                                                                                         |

The existing frames 25/26 retain the bounded `layout-adjusted` receipt with exact target, revision, selected state and `no-split` or identified `split` change. Only resize may report `no-split`. A setter reports its normalized requested ratio; resize reports its clamped signed delta. Selected success requires the original selection/zoom and committed ratio in a successfully drawn cache at or beyond the committed revision; the receipt captures that drawn revision. An inactive target's receipt captures its commit revision without advancing the unrelated selected view. Successful drawing does not claim Host resize completion.

Deterministic and generated Server traces cover bounds, nested hierarchy, CAS, exact identity, replay, no-op and non-target preservation, with deletion shrinking and serialized replay. Native controller and worker traces cover one submission, inactive purity, publication/draw ordering, rejection, unknown outcome and shutdown. Independent Rust, TypeScript and JSON Schema validation plus normal Windows ConPTY traces connect shared ratios to actual two-Client geometry and controller dimensions. Human Windows Terminal and physical reboot evidence remain separate.

The terminal-size owner admits each visible controlling pane by exact attachment incarnation when unzoomed.
