# Windows native plugins

## Catalog model

The native plugin catalog is shared user configuration, independent of a Site lifetime. Windows `plugin link PATH`, `unlink ID`, `enable ID`, `disable ID`, `list [ID]`, `config-dir ID` and `action list [ID]` use the catalog without starting a Site. Linking records a manifest; it does not execute build or startup commands. Unlinking removes registration and retains the linked source and user configuration/state directories.

The local-site-runtime plugin boundary owns bounded TOML validation and the persistent catalog. A directory resolves `orchbee-plugin.toml`, or `herdr-plugin.toml` when the native filename is absent. An explicit manifest file is also accepted. Herdr metadata import does not imply compatibility with Herdr-specific executables or API calls. Identifiers are trimmed, case-sensitive ASCII, at most 120 characters; plugin IDs admit letters, digits, colon, dot, underscore and hyphen, while action IDs exclude dots. Arguments stay separate argv elements. Unknown fields, duplicate entry IDs, invalid commands and invalid platform names fail before registration.

Manifest files are limited to 128 KiB, catalogs to 32 entries and 1 MiB. Entries retain canonical source paths, enabled state and the last valid manifest. Reads refresh manifests; unavailable or invalid sources retain inspection metadata with an explicit warning and cannot authorize command execution. Entry platform lists override the plugin platform list; absent lists admit Windows. Other platform labels are metadata only.

## Persistence and transitions

Catalog storage lives under the admitted user configuration parent in `plugins`; the existing private Windows cache supplies ancestor validation, exclusive writer locking, flushed atomic replacement and interrupted-write cleanup. Reads never create directories. Mutations reread under the lock, validate the complete next catalog and increment its safe-integer revision only on a change. Corruption, contention and capacity limits are errors; they never become an empty catalog. Unlink of an absent ID is a no-op; enabling an absent ID fails. Hashed, prefixed ID path components keep config/state directories stable and safe for Windows reserved names. User directories remain after unlink.

## Runtime actions and logs

`plugin action invoke ACTION [--plugin ID] [--client ID] [--context JSON]` submits one local or qualified `plugin.action` ID to an existing Site. `plugin log list [ID] [--plugin ID] [--limit 1..200]` reads the newest retained logs, default 50. List and action-list also accept `--plugin` as an alternative to their positional filter. All commands accept `--format text|json`; runtime commands never activate a Site. Context is a closed camelCase object with optional workspace/tab/Pane display fields, worktree, selected text, invocation source, correlation ID, clicked URL and link-handler ID. The aggregate encoded context is at most 16 KiB and selected text at most 8 KiB. It carries no authorization. An omitted invocation source becomes `cli`; correlation defaults to the invocation operation ID.

Invocation infers context before submission under the same ten-second deadline. An explicit Client overrides inherited caller identity; otherwise an exact canonical caller binding selects its terminal member, or one current Client selects its observed member. Multiple current Clients require `--client`; no caller and no current Client means a global invocation without invented selection. Ready and stable Busy views are readable. Canonical membership, metadata, Client selection and member generation must remain consistent through enrichment or no action is submitted. Runtime cwd and Agent observations belong to that exact member; its explicitly reported Agent name and non-unknown state take precedence, otherwise a unique observed provider and aggregate state supply the values; a missing observation stays absent. Workspace cwd prefers observed Pane cwd, then the Workspace directory. Worktree information uses the existing read-only query with no trust override and native fields `workerId`, `repositoryRoot`, `commonDirectory`, `repositoryName`, `checkoutPath` and `linked`. Unavailable worktree observations stay absent. Explicit non-null context values override inferred display fields without selecting or authorizing any target. API invocation does not scrape Client selection text; callers provide `selectedText` explicitly, as in the reference API.

Server requires read, terminal-creation and lifecycle grants before resolving an invocation. It checks Site identity, an unambiguous available enabled action and effective Windows platforms, then freezes argv, source cwd and environment. Worker executes separate arguments from the plugin root; explicit shell commands retain their own shell semantics. Relative programs resolve against the plugin root, then Windows PATH/PATHEXT. Native context is exposed in `ORCHBEE_PLUGIN_CONTEXT_JSON`, plus plugin ID/root/action/config/state paths, `ORCHBEE_BIN_PATH`, optional workspace/tab/Pane IDs and link fields. Managed Worker overrides runtime base/scope with its own Site routing. These are Orchbee variables and API semantics; Herdr-specific scripts may need changes. Inherited plugin/terminal identities are removed before the current invocation's fields are installed.

Worker owns at most 32 concurrent commands and 200 logs per Worker lifetime. Each command has a retained thread and Windows Job; it survives CLI disconnect. Identical retained operation IDs return the existing receipt, changed intent conflicts, and expired logs are not durable replay records. CLI never resubmits a mutation after an uncertain reply. A start receipt confirms admission, not command success. Logs carry sequence, start/end time, exit code, typed failure, stdout/stderr and explicit truncation flags. Each raw output stream retains 64 KiB while continuing to drain; text decodes invalid UTF-8 with replacement. Text rendering escapes control characters. Completed logs are evicted oldest first; running commands retain ownership. Output becomes available when the command finishes.

Runtime log reads page four records at a time under one ten-second CLI deadline, retaining the exact Worker/generation and descending sequence cursor. New commands do not shift subsequent pages; a changed Worker rejects the old cursor. Invocation uses `orchbee.plugin.runtime` v1; history uses `orchbee.plugin.logs` v1 with one flattened `logs` array, ordered oldest to newest within the latest requested records, matching the reference default of 50. Internal cursor pages remain descending. Both retain the normal 8 MiB output bound. The older runtime schema remains available for historical receipts. A log query reports process failure as data, rather than making every history query fail. Private get/cancel requests target an exact Worker and job ID. Cancellation and Site shutdown settle the root and descendants, drain output and join their owners; uncertain Job cleanup blocks new execution and cannot become successful cleanup on retry. No hidden helper window, detached pipe-reader thread or arbitrary command-duration timeout is introduced.

## Managed source installation and removal

`plugin install owner/repo[/subdir] --yes [--ref REF] [--timeout MS]` runs without a Site. It requires Git on Windows PATH. `--yes` explicitly authorizes executing the downloaded source's build commands; the native CLI does not prompt or read a terminal. The default work deadline is 600000 ms, range 1..3600000; a running Windows Job has a separate maximum five-second settlement budget after interruption or deadline. `plugin uninstall plugin-id|owner/repo[/subdir]` removes registration and only a managed source, preserving user config/state and locally linked source files. Both accept text or JSON output.

The shared private catalog holds its writer lock for the finite checkout/build/commit/cleanup workflow. Reads remain available. A fresh generation is recorded before its directory is created under `plugins/managed/i-<operation-id>/checkout`. Git initializes that directory, fetches one branch/tag/commit (default HEAD), checks out the exact fetched commit, and records its hash. Effective Windows build argv run from the manifest root. Git hooks are disabled and symlink checkout is disabled; build commands run as the current user, without a sandbox claim. Build subprocesses inherit the user's tool environment, with `ORCHBEE_*` runtime context removed and interactive Git credential prompts disabled. The synchronous CLI owns every Job, bounded output drain and interruption; these processes do not survive that owner's exit by contract.

The manifest must remain unchanged after building. A linked local ID refuses replacement; a managed replacement retains the enabled state. Only an atomic catalog replacement publishes the new source. A failed build retains the previous registration and removes the staged source. A committed replacement or uninstall queues obsolete generations for cleanup; a cleanup failure cannot undo that commit or turn it into a precommit refusal. Cleanup derives paths from generated IDs, pins private ancestors and rejects reparse points, foreign ownership or hard links. The next explicit install/uninstall resumes recorded cleanup without rerunning previous builds; possible physical ownership is persisted before creation and cleared only after known settlement, so a crash during execution or an uncertain physical owner blocks automatic cleanup. A current catalog reference, including an explicit local link into a generation, prevents its deletion. Unlink keeps source files and does not schedule their cleanup.

Storage v2 preserves managed GitHub provenance and a bounded recovery list. Existing v1 catalogs remain readable and migrate on a mutation; old binaries reject v2 rather than discarding its state. `orchbee.plugin.registry` v2 adds a nullable managed source while its v1 schema stays closed. `orchbee.plugin.provision` v1 reports the operation identity, phase, committed change, failed command/exit/output, truncation and pending cleanup paths. Install/update source commitment is separate from build-created external effects, which cannot be rolled back by deleting a checkout. Exit 7 means work deadline, 8 physical uncertainty, 130 interruption, and other provisioning failures use 1.

Startup/event hooks, link handlers and plugin Pane lifecycle still require integration before complete plugin parity. Catalog acceptance is not an execution receipt. ## Overlay lifecycle model

Windows overlay placement uses a canonical horizontal split of the selected live Client's active Panel, forces focus and zoom, and retains that Client's previous focus and zoom. It does not activate an OS window. Popup geometry belongs to a separate capability. Caller environment cannot redirect an overlay to a different Panel. Explicit Workspace, target and direction overrides are refused before creation. One deadline covers creation and the Client handoff; known creation survives an interrupted or uncertain handoff without another launch. Creation v5 explicitly records the overlay request; v2–v4 remain closed to it.

The Client owns at most 32 transient overlay records keyed by exact context, Tab, Panel, Presentation and binding. Admission pins both created and return members and checks the original selection before changing focus. The record is installed before the first focus/zoom effect; interruption after that point retains it. Records survive local navigation while their canonical members survive, but are not durable or reconstructed after Client restart. Nested overlays unwind from the newest removed member. Removing a return member collapses its return chain while preserving the outermost prior zoom; an unavailable or rebound return member is never selected.

| Transition         | Guard and result                                                                                                                                     |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| Open               | Exact current Client, source selection and canonical members; reserve a bounded record before focus/zoom                                             |
| Observe            | Read-only Host inventory against the full physical identity, with bounded pages and deadline; no lifecycle mutation or exclusive close ownership     |
| Auto-close         | Known exited/failed terminal and unchanged plugin membership; submit one canonical revision-fenced Panel Close, retaining its identity               |
| Lost close answer  | Retain uncertainty and stop automatic close submission; a read or disconnect never proves cleanup                                                    |
| Canonical removal  | Restore previous focus/zoom only while this overlay still owns that Tab's focus; preserve another selected context/Tab and manual focus/zoom choices |
| Source/member loss | Drop invalid view records, keep existing deterministic selection repair and never select a recycled identity                                         |
| Client shutdown    | Interrupt and join the isolated lifecycle lane; Server retains accepted Close ownership and canonical terminals                                      |

Server owns serial temporary observation viewers and uncertain cleanup until exact detach/disposal or physical Site shutdown; it refuses another observation while cleanup is unresolved. The lifecycle lane owns one finite read/close job at a time, never blocks rendering, and never retries an uncertain mutation. Tests must distinguish natural settlement, explicit close, unavailable reads, nested removal, navigation and rebind, and must exercise actual rendering and Windows CLI transport. Same-author focused evidence does not establish OS-emulator or deployed Host acceptance.

## Terminal Pane creation

`plugin pane open --plugin ID --entrypoint ID [--placement tab|split|zoomed|overlay]` creates a real terminal Tab or split through the canonical creation workflow. The manifest supplies the default placement and title; `--target-pane` selects a split target, `--direction right|down` controls its orientation, and `--workspace` selects the destination for a Tab. Focus defaults on; `--no-focus`, `--client`, `--cwd`, repeated `--env`, geometry and timeout options use the existing creation controls. The default directory is the Server-resolved plugin root, independent of configured shell cwd policy. The manifest program is resolved relative to that root even with a cwd override. Native receipts use `orchbee.creation.result` v3 and distinguish canonical creation from Client focus; v2 remains closed to the new `plugin-root` directory policy. Zoomed placement forces focus, including with `--no-focus`, through one revision-fenced Client Zoom intent; its v4 receipt adds `postCreate.requested.zoom=true` and retains the combined focus/zoom answer in `postCreate.focus`. A changed selection or lost Client reply preserves the creation receipt and never recreates the terminal. Legacy v2/v3 receipts cannot contain the new zoom request. As in Herdr, split/zoomed ignore `--workspace`, and tab ignores `--target-pane`.

The CLI submits catalog identifiers rather than executable authority. Server admission rechecks enabled, available Windows entrypoints and freezes argv, cwd and protected plugin environment before terminal reservation. Replay uses the retained canonical request. Explicit executable/profile selection and plugin Pane selection are mutually exclusive; Workspace launch and child-terminal creation reject this selector. The CLI and Server preserve program/argv identity. Absolute `.cmd`/`.bat` entrypoints are admitted and executed by the Host through the system command processor with AutoRun and delayed expansion disabled; batch argument encoding protects metacharacters and percent literals, while the script owns any expansion it performs. NUL/CR/LF arguments, unsupported verbatim path spellings and encoded command lines over 8191 bytes fail at Host launch before a PTY/process exists; the canonical creation receipt still records that accepted launch. Independent popup placement uses the separate popup lifecycle below. `plugin pane focus <pane-id> [--client ID] [--timeout MS]` and `plugin pane close <pane-id> [--timeout MS]` first read Server-owned membership. The exact Presentation/binding and canonical revision must agree with the CLI snapshot; ordinary, rebound or stale targets fail before an effect. Close submits one revision-fenced native Panel close and reports its retained lifecycle receipt; focus uses normal Client selection and view fences. Unknown delivery is never retried. A late cancellation preserves an acquired receipt with a nonzero exit.

Membership is transient Server state committed with terminal reservation, bounded to 4096 entries and keyed by exact Presentation/binding. It follows moves and is pruned when the member disappears or rebinds. A pending, failed or physically unknown launch remains associated with its canonical Pane for normal lifecycle cleanup. Unlinking the offline catalog does not prevent closing an already created plugin Pane. Restart/checkpoint restoration does not manufacture plugin membership.

Overlay pins the source Client’s actual selected primary or child Presentation through a passive read before creation. Its v5 receipt adds `postCreate.requested.overlay=true` alongside the forced focus/zoom request; a known Overlay answer is Client control v8. Older creation/control variants keep their previous contracts. Server observations detach their temporary viewer before returning settlement; an uncertain detach retains one cleanup owner and blocks replacement. The Host inventory walk has one two-second budget, at most eight pages of 128 entries, stable generation/cursors and duplicate/full-identity checks. The Client lane uses a ten-second cancellable job and schedules records fairly; existing Server attach/detach bounds remain separate, so this is not a ten-second physical service-shutdown guarantee. Manual plugin Pane close uses the same canonical removal/restoration path.

## Pane launch source context

Plugin Pane creation may carry `LaunchOptions.pluginContext`, a bounded display observation using the existing plugin invocation context contract. It is admitted only with a plugin Pane selector on Tab creation or Panel split. The CLI observes the original source before creation through canonical membership and passive Client/caller, primary/child, physical Agent/cwd and Workspace worktree reads. One creation deadline covers these reads and later creation/handoff; stale source or Client observations refuse before submission. Empty, headless, unbound or unavailable observations do not fabricate a focused terminal or selected text.

Server validates source membership and canonical labels, fixes `invocationSource` to `plugin-pane` and the correlation to the actual creation request, and freezes the context in the existing protected launch environment before reservation. Context describes the placement-selected source before creation. It never supplies executable, directory-policy, Worker or terminal authority. Existing requests without this field retain their legacy admission. No separate context store or replay lookup is introduced; frozen launch intent owns the context lifetime. Rust, TypeScript and JSON peers must be deployed together. Independent popup geometry, reservation, exposure, input and close use the lifecycle below.

The frozen Herdr baseline at `e0507237` selects the explicit target Pane for split/zoomed context and the destination Workspace's remembered focus for Tab context. The CLI derives this source from the already resolved canonical creation command, never from a display label or a pending navigation intent. Overlay retains the original selected primary/child member. The existing private context uses native invocation source/correlation conventions. Pane launch does not automatically copy selection text in either baseline.

| Creation source               | Observation and absence policy                                                                                                                                                     |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Split or zoomed               | The exact target Panel and its canonical Tab/Workspace; use the actual caller/Client primary or child only when it belongs to that target, otherwise observe the canonical primary |
| Tab in the current context    | The caller or selected Client's actual focus and primary/child member                                                                                                              |
| Tab in an inactive context    | The exact observing Client's read-only remembered active Tab and layout focus; verify canonical parent membership, then observe that Panel's primary                               |
| Empty or headless destination | Canonical Workspace label, cwd and worktree when available; omit unknown Tab, focus and physical facts rather than guessing the first tree member                                  |

Client owns remembered Tab/focus; Site owns canonical membership and labels; the existing physical collector owns corroborated cwd/Agent observations and temporary viewer cleanup. A background layout probe uses a canonical Panel solely as its query anchor, never as a focus fallback. Native child-terminal selection in an inactive context is not exposed by these read-only memory contracts, so the background source is the canonical primary, matching Herdr's one-terminal-per-Pane model.

The source workflow is resolve canonical target, observe exact memory/member, collect physical facts, re-read background Tab/focus and original Client, then submit the existing single creation request. All phases share the creation deadline and cancellation owner. Wrong parents, stale revisions, changed remembered Tab/focus or original Client fail before creation; no read navigates, focuses, zooms, launches or retries a mutation. The source context remains display data and cannot change plugin-root cwd, program/argv or Worker authority. Focused evidence must cover different explicit targets, inactive destinations whose remembered Tab and Pane are not first, current/caller child preservation, empty/headless absence, and refusal on changed or invalid memory. These checks establish native Windows CLI transport and owned read projections, not deployed Host/emulator acceptance.

## Independent terminal popup

Windows supports independent plugin popup terminals and a native close facade. The frozen Herdr baseline creates one independent terminal above the current pane surface, leaves canonical Tab/split membership unchanged, defaults each outer dimension to half the available surface, supports cell counts and 1–100 percent, and closes on terminal settlement. The popup receives keys and paste before normal bindings: Escape and the configured prefix belong to its program. Outside mouse events cannot activate the underlying layout. Native header close is an additional explicit close affordance.

The existing terminal coordinator owns identity allocation and independent Terminal Create; the popup never reserves a hidden Tab, Panel or Presentation. A dedicated authenticated Client connection owns at most one popup, and the Site retains at most 32 popup owners including uncertain cleanup. Server resolves an enabled Windows catalog entry and freezes argv, plugin-root cwd, protected environment and validated source display context before reservation. Caller input contains only the selector, bounded context, optional cwd and normal launch environment; it cannot supply protected environment or physical identity. The UI separately admits one popup against the exact selected Client/view revision and source member. Source identity reuses the full Client Presentation selection: bound attachment generation/incarnation or unbound selection generation; frame and scroll updates do not change member identity. Dimensions are typed cell counts or percentages; omission uses manifest defaults, then half-surface defaults. Geometry is centered and clamped to at least 6 by 4 outer cells; the native bordered content is two cells smaller in each dimension. Too-small viewports suspend popup input and resizing without resizing it to zero.

| State / transition          | Ownership and guard                                                                                                                                     |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Absent to opening           | One UI reservation; exact source/view fence, sufficient surface, no conflicting dialog; Server connection reserves its owner before one launch dispatch |
| Opening to active           | Correlated known immediate launch, attach by exact create reference, acquire controller, accept a drawable bounded projection                           |
| Active input / resize       | Dedicated serial lane, exact attachment/controller/frame fences; keys and paste target only the popup, mouse uses its last completed painted rectangle  |
| Terminal settlement         | Read-only exact physical lifecycle observation; schedule one close, without interpreting a missing frame or disconnect as exit                          |
| Explicit close / disconnect | Withdraw input first; Server transfers close responsibility to the existing Site maintenance lane                                                       |
| Known disposal              | Full Worker generation, binding fence and Host identity; release the popup binding and owner only after known physical disposal                         |
| Unknown launch or close     | Retain the bounded Server owner and stop mutation replay; do not claim cleanup or start a replacement on the same connection                            |
| Client shutdown             | Cancel and join the dedicated lane; connection drop transfers any accepted terminal to Site cleanup                                                     |
| Site shutdown               | Existing physical Site/Worker shutdown settles the retained uncertain owners; retained state is not persisted or reconstructed                          |

`plugin pane open --placement popup [--width CELLS|PERCENT%] [--height CELLS|PERCENT%]` uses manifest size defaults unless overridden. Popup placement rejects canonical geometry, target, Workspace and direction overrides before effects. `popup close [--client ID] [--timeout MS]` addresses a Client even from a terminal without a canonical Pane. Both use `orchbee.popup.result` v1; generic Client control uses v9. Open completion requires an accepted frame and completed drawing; Close completion waits for known physical disposal. Closing when no popup exists reports `hadPopup=false` and preserves unrelated dialogs. Older creation and Client-control CLI schemas remain closed.

The private Workbench plugin contract provides connection-scoped popup open, lifecycle-read and close actions with closed typed results. Open requires read, create and lifecycle permission; Read requires read; Close requires read and lifecycle permission. Natural settlement observation attaches by the exact independent create reference and does not claim the exclusive lifecycle close owner. Explicit close withdraws input and fences the binding, then Site maintenance submits Force, observes an exited/failed target through bounded inventory, and submits Dispose. Inventory observation uses a cooperative five-second window, at most eight pages per traversal and 32 lifecycle steps; an in-flight Worker exchange retains its independent transport bounds. Only known Dispose releases the retained binding. Lost launch or close receipts park uncertainty without mutation replay; the UI displays a restart-Site notice before permitting replacement. Known refusal before launch permits retry. Rust/TypeScript peers deploy together; this does not claim Herdr RPC-name or Desktop feature parity. No new Host capability, dependency, process framework or durable store is introduced.

Tests own their roots, pipes, threads and Jobs until their last consumer ends. Focused fixture evidence does not establish deployed Host/emulator acceptance; final integration requires the broader Windows acceptance flow.
