# Windows CLI notifications

`notification show <title> [--body TEXT] [--position top-left|top-right|bottom-left|bottom-right] [--sound none|done|request] [--format text|json]` submits to an existing Site. Title/body normalization collapses whitespace, removes controls and truncates to 80/240 Unicode scalar values; an empty normalized title fails before submission. Position defaults to bottom-right; sound defaults to none. The wire bounds each normalized string by its scalar count and UTF-8 size.

## Delivery model

The existing Server Workbench service owns an ephemeral notification registry. Each listener belongs to its authenticated connection generation, expires after five seconds without a poll and has one pending message with a five-second lifetime. At most 32 listeners and 256 request receipts are retained; receipts expire after 60 seconds. A successful Show queues to every currently accepting live main-TUI listener and starts the one-second rate limit. Busy, rate-limited and no-foreground-client outcomes perform no delivery. Exact retained request replay returns its original result without enqueueing; conflicting request identities fail. No mutation is retried after transport uncertainty. A successful receipt describes queue admission, not physical display or audible playback. Listeners consume once; disconnection and expiry release pending state. No work is retained across Site restart.

A cancellable Client-owned connection polls independently of input/rendering. Only the UI owner installs notifications. One five-second transient card uses the requested corner within the content region, never covers the status row, captures no keys or mouse, moves no focus and changes no layout. Existing notices, dialogs and overlays make the listener temporarily unavailable; a race is resolved by discarding the incoming card rather than replacing a user-owned surface. Expiry schedules redraw while idle. Display text escapes terminal and directional formatting controls and clips using terminal display width. A successfully drawn card may issue one safe Windows sound cue: information for done, exclamation for request, no cue for none. System sound policy may suppress playback. Notification delivery does not promise OS toasts, native-window activation or Agent target navigation.

## Boundaries and evidence

Herdr reference is `e0507237ad8d41f60aece10d00ef29ce2339ca34`, especially `server/headless/notifications.rs`: Client delivery policy is distinct from Server fallback policy. Native main-TUI cards implement this entry point; the broader toast configuration family (including omitted-position inheritance from each Client) and other notification transports remain separate alignment work. Matched private cohorts upgrade/roll back together. No new persisted format, dependency version or unbounded queue is introduced.

Focused evidence covers sanitizer boundaries, independent protocol validation, registry expiry/replay/fanout/backpressure, actual Windows CLI pipes, shutdown, Unicode corner rendering, idle expiry and preservation of input ownership. This does not establish authenticated provider, physical Windows visual/audio or final full-regression acceptance.
