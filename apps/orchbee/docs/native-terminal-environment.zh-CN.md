# 原生终端环境

## 范围与归属

本参考治理 Orchbee 在运行时拥有的原生宿主终端环境：每个新的 Windows 子进程环境、保留的
Windows 端点、raw 记录输入与 Unicode VT 输出、面对瞬时零几何的视口观测、每个绘制帧的同步
更新包裹，以及指针捕获模式对。它与 Terminal Host 的 `windows_environment.zig` 适配器、
`terminal_device.rs`、`terminal_device/windows.rs`、`windows_console_input/records.rs`、
`startup_wait.rs`、`terminal_lifecycle.rs`、`tui_backend.rs`、`tui_shell.rs` 及所属的
`crates/windows-console-host` 边界共同维护。准入验证 TTY
身份与描述符安全（两个流上的交互 TTY、同一终端身份、几何查询本身可用）；获得可绘制的
单元格几何是独立的就绪关注，由 [`native-startup-wait.md`](native-startup-wait.md) 治理。
宿主以零报告的像素几何被如实报告为 "pixel 未知"——一种正常状态，绝不伪造。
指针能力 settle 还须与 `terminal_pointer_admission.rs` 及 `terminal_input/` 下的外层宿主
解码器共同维护。

## Windows 输入归属

Windows 适配器把准入后的标准输入与输出句柄各复制一次，交给
[`orchbee-windows-console-host`](../../../crates/windows-console-host/README.zh-CN.md) 提供、以
`OwnedHandle` 为后盾的 `ConsoleInput` 与 `ConsoleOutput` 端口。模式操作、raw 记录摄取、输出
窗口观测和 Unicode 输出全都使用这些精确保留的句柄；适配器不会重新打开 `CONIN$` 或
`CONOUT$`，也不会在准入后再次解析进程标准端点。边界 crate 的私有 `sys` 模块是这些 Win32
调用与带 tag union 读取经过评审的 unsafe 边界；Client 使用它提供的安全记录与端口。

准入后的继承控制台在启动等待、TUI 和直接 attach 之间拥有一个权威记录读取器。
它在阶段切换时保留 UTF-16 代理项和有界重复状态；没有竞争读取的 Crossterm 事件读取器或
后台输入线程。每次读取最多交付 4096 字节，活动排空预算为四毫秒。虚拟键码为零的 VT 字符，
包括 C0 和 bracketed-paste 边界，原样进入语义解码器。物理键盘与鼠标记录复用已有字节编码；
raw Ctrl+C 仍是应用输入。原生就绪计数与随后的一条记录读取是两个独立的 Win32 调用，并非
针对外部消费者的原子预留。因此，有界读取契约要求外部读取器不得在两者之间排空同一控制台
输入缓冲区；Client 的权威读取器在进程内部保证这个条件。

UTF-16 文本先完成组装，再编码为 UTF-8。高代理项跨读取边界及无字符的键盘记录保持待定，
包括修饰键和 IME/process-key 记录；ConPTY 携带字符的 Alt 释放记录与零虚拟键码文本共用
同一组装路径。完整代理对按其重复次数输出一个标量，绝不输出两个替换字符。
孤立低代理项、高代理项之后出现另一个文本／按键边界，或重复次数／修饰键元数据不一致时，
读取以 `InvalidData` 拒绝，并走已有的本地化界面失败路径；非法输入不会成为保存的标签或
Shell payload。空闲轮询不会完成或替换待定高代理项。用户直接输入的 U+FFFD 仍是普通文本。
`windows_console_input/records/tests/unicode.rs` 覆盖原生记录分段、无字符记录交错及有界 UTF-8
重复尾部；`terminal_session/ui/tests/input_provenance.rs` 和
`terminal_session/state/tests/location_labels.rs` 覆盖精确重命名请求、字素编辑、取消及位置标签
发布。这些受控实现见证不提供穷尽 TLC 保证，也不能证明真实窗口的字形渲染效果。

raw mode 保持 `ENABLE_VIRTUAL_TERMINAL_INPUT` 开启并关闭 cooked 处理。关闭 VT 输入会让
ConPTY 丢弃粘贴边界；用键盘布局查询解释零键码 ESC 也会丢失边界。指针租约单独拥有原生
鼠标输入位及 VT 上报写入，因此 `--mouse off` 的 raw 准入不捕获鼠标。
恢复时还原保存的原始控制台输入／输出模式。参见微软的
[控制台模式契约](https://learn.microsoft.com/en-us/windows/console/setconsolemode)与
[粘贴边界过滤说明](https://github.com/microsoft/terminal/issues/18094)。

## Windows 子进程环境

每个新的 Windows terminal 都会在 Terminal Host 的进程创建边界读取当前 Machine 与 User 环境
值。确定性投影从一份新环境开始，只先纳入闭集内继承的 volatile Windows runtime 与 identity 值
以及每驱动器 current-directory 项，再以大小写不敏感名称应用 Machine 与 User 注册表字符串。
Machine `USERNAME` 会被排除，因为 HKLM 通常记录 `SYSTEM` 而非交互用户。任意 process-only 名称
不会被继承：从注册表删除后，它会从下一个 terminal 消失；必需的 process-only 值应放入 launch
profile。注册表 unnamed default value 会被忽略。缺失范围视为空；不可读或 malformed 范围以
unavailable 失败，越界范围以 too-large 失败，且都发生在取得 PTY 所有权前。

只有 `REG_EXPAND_SZ` 值会展开 `%NAME%`。依赖先从 User 优先于 Machine 的 raw 快照解析，再从
已准入的继承 runtime 与 Orchbee private 值解析，且不受注册表枚举顺序影响。Machine `PATH` 会先
完成投影，因此可展开 User `PATH` 中的 `%PATH%` 引用新的 Machine phase，而非 Host 的过时
`PATH`。未知名称与其他环中的递归 token 保持字面内容；深度与大小限制按关闭失败处理。有效
`PATH` 依次为展开后的 Machine `PATH` 与 User `PATH`，大小写不敏感的精确重复片段按首次出现
顺序移除。若两个范围都不拥有 `PATH`，则不会合成继承的 `PATH`。

继承的 `ORCHBEE_*` 会在注册表投影后重新应用。已授权启动环境项与删除项随后应用，每个 creation
私有的 Orchbee overlay 再随后应用。因此 live Session 与显式启动输入的优先级高于注册表数据。
Deferred creation 仅在尝试创建进程时读取注册表，重试会读取新快照。运行中的 terminal 保留其
原始子进程环境。非 Windows terminal 维持既有的继承环境投影。

两个注册表范围合计最多准入 256 个枚举值，以及 512 KiB 存储后的 WTF-8 name、value 与 entry
separator。单个已准入注册表值、单次展开输出及合并后的 `PATH` 各自最多准入 256 KiB。最终投影
map 最多准入 1,536 项，以及 1 MiB 存储后的 WTF-8 name、value 与 entry separator。单次投影最多
执行 65,536 个 expandable-value visit 与 token resolution。`PATH` 去重最多扫描 4,096 个输入片段，
空片段及重复片段均计数。真实读取器与纯投影以 typed failure 拒绝越界输入，而不截断或继续无界工作。
确定性测试覆盖这些边界、名称匹配、展开依赖、User `%PATH%` phase 语义、未解析名称、环、
unnamed value、缺失和不可读范围、`PATH` 顺序与去重、继承准入、启动优先级及不同启动之间的刷新。
受控的原生 Windows 见证还须保持 Site 运行，修改一条可还原的 User `PATH` 项，并证明只有随后创建的
terminal 能解析新命令，然后还原该项。

## VT 命令输出

Windows 成功启用 VT 输出处理后，生命周期、启动等待提示与固定视口渲染器使用
`Command::write_ansi` 将 Crossterm 命令直接编码到调用方提供的写器。该路径不会运行
Crossterm 的进程全局 Windows ANSI 探测、打开 `CONOUT$`，也不会退回到可能针对另一控制台
的 WinAPI 操作。编码器不分配中间命令缓冲区，保留首个写器错误，而且不选择 flush 边界：
生命周期 effect 在命令后 flush，提示与渲染器只在原有的完整输出边界 flush。已报告的写入
错误可能发生在某个前缀已经发出之后；编码器既不重放该前缀，也不继续处理后续命令片段。

精确句柄 Unicode 适配器使用 `WriteConsoleW`。每个取得的写器独立拥有一个有序流的不完整
UTF-8 尾部、待写 low surrogate 与锁存故障。可信的原生短计数会映射回 UTF-8 前缀；拆开的
surrogate 会在同一个写器接受后续字节之前恰好补完一次。零计数或不可能的计数、非法 UTF-8
或原生错误会使该写器进入故障；之后对它的调用直接返回已保留错误，不再原生写入。原生错误
的 effect 未知，且可能发生在前缀已经发出之后，因此适配器与调用方都不会重放失败
payload。新写器以空编码状态开始，使有界生命周期清理能在帧写器故障后继续尝试完整 ASCII
控制序列；它不会修复失败流、证明没有前缀逸出，也不会让控制台输出成为原子操作。

直接编码由成功的原生 VT 模式变更门控。若该变更在尝试备用屏幕命令之前失败，恢复流程
不会发出可能显示为文字的 ANSI 备用屏幕清理。在已准入路径上，显示光标与离开备用屏幕
都在 VT 处理仍生效时尝试；还原保存的输出和输入模式字是最后一个原生步骤。两个原生恢复
独立 settle：两个待恢复模式字都会被尝试，其中一个恢复成功后，不会仅因另一个失败而再次
写入。模式捕获、VT 准入、输出、清理与恢复全都指向同一对保留的输入／输出端口；原始模式
恢复债由生命周期 owner 登记并 settle，而不是由边界 crate 拥有。

## 宿主外观查询

raw 终端准入后、首个 TUI 帧绘制前，生命周期写入器按顺序发送一次 OSC `10` 前景查询，随后发送
OSC `11` 背景查询。该写入不启用终端模式，也不产生恢复债。首帧立即绘制；外观探测在 350 ms
期限后 settle，不会让渲染路径等待。

普通与模态输入解码器都会识别 ESC `]` 和 C1 OSC 应答形式。只有精确的 `10;` 与 `11;` 选择器
会成为查询元数据。RGB（`rgb:rrrr/gggg/bbbb`，每个分量一到四位十六进制）与 `#RRGGBB` 值在
96 字节 payload 上限和一秒帧期限内解析。背景缩放为 RGB8 后按加权亮度阈值
`299R + 587G + 114B < 128000` 分类为深色；否则为浅色。只有前景、畸形、超长或不完整的应答
不会用于分类；探测会等待期限，以判断是否有有效背景。已识别应答及其排空内容绝不会进入 prefix、
模态、pane 或编辑器输入。探测 settle 后迟到的应答仍会被消费，不能更改主题。

若到期限时没有有效 OSC `11` 背景，Windows 就使用回退：Client 请求 `local-site-runtime` 读取当前用户的
`HKCU\Software\Microsoft\Windows\CurrentVersion\Themes\Personalize\AppsUseLightTheme`。
DWORD `1` 表示浅色，`0` 表示深色。缺失、不可读或非布尔值保持未知。只有前景应答、畸形、部分
或完全缺失的背景都会触发此回退。没有有效背景时，其他
平台保持未知；迟到应答不会改变已确定的回退。注册表只读取一次，不写入。此外观探测不会更改终端
默认色、Windows 个性化、pane 启动查询默认值或终端模式集，也不需要超出正常生命周期恢复的清理。

## 视口观测

对继承终端的运行时观测区分三种结果。区分基于类型化结果，绝不基于错误文本。

| 观测     | 含义                                        | 运行时效果                                                                  |
| -------- | ------------------------------------------- | --------------------------------------------------------------------------- |
| 有效几何 | 宿主报告了非零行列                          | 变化时应用 resize 并重绘；相同几何是 no-op                                  |
| 零或缺失 | 宿主瞬时报告了零行或零列                    | 不发送 resize、不清退 Session、上一有效几何保持生效，下一个有效几何正常恢复 |
| 检查错误 | 描述符或查询本身失败（权限、关闭、非法 fd） | 致命：故障传播，界面退出                                                    |

壳层同步本地实时分隔线草稿时，可以重复完全相同的上一有效视口观测。既有物理控制者对
相同的投影几何去重，因此重复观测不额外发送 Resize。自身布局变化与宿主观测分离，
不授予控制权。新的图形单元测量仅随非零宿主样本应用；缺失样本不能改变保留的行列或
像素尺寸。

像素宽高为零是正常观测而非错误：cell-pixel 对被报告为 `(0, 0)`——"pixel 未知"——字符
网格照常工作。当宿主只报告一个像素轴，或推导出的 cell-pixel 轴向下取整为零时，整个
对按未知报告，而不是虚构缺失轴。像素读数为零的单元尺寸变化同样绝不通过复用旧像素值
来解决——旧像素永远不是新尺寸的度量。已知 → 未知 → 已知 的转移走同一条几何路径；
每个状态都按实测报告，下游依赖像素的功能按"成对已知"门控，而非按任何估计值。

## 指针捕获生命周期

指针上报拥有一个 tracking level 加 SGR cell 编码。准入先关闭 any-motion（`?1003l`），
再启用 `?1002h` 与 `?1006h`，建立 button-event baseline。该完整 baseline 成功后，生命周期
控制的输出路径发出一次有序的 `?1003$p` DECRQM，并以 DA1 作为完成哨兵。只有
`Reset (2)` DECRPM 回复准入 any-motion。`Set (1)` 与已经建立的 baseline 矛盾，settle 为
unknown；`0`、`3`、`4` settle 为 unavailable；DA1 先到或有界 deadline 到期 settle 为
unknown。由于回复没有 query identifier，同一端点绝不再次探测：迟到或重复回复会被消费，
但不能改变已经 settle 的结果。

普通宿主解码器与 modal 宿主解码器以相同规则识别 ESC-CSI 和 C1-CSI 两种形式的精确回复。
DECRPM 只接受 `?1003;[0-4]$y`，DA1 回复必须由一个或多个非空十进制参数组成。完整 private
CSI 只有带 DA1 的 `c` 或 DECRPM 的 `$y` 回复 final 时才属于宿主元数据；畸形但具有回复
framing 的帧会被消费，绝不变成按键、编辑器输入或 pane 字节。其他完整 private CSI 仍是
generic non-decision input，并保留 raw passthrough。若一个 run 在回复 final 到达前触及时间或
大小上限，它同样回到有界 generic drain，不会无限延长元数据所有权。bracketed-paste payload
保持字面值，绝不在其中检查这些回复。

准入结果通过先关闭旧 level、再启用新 level，从 `1002` 切换到 `1003`。unknown 与
unavailable 保持 `1002`，因此 click、drag、wheel 可用，而下述菜单范围策略之外的 idle hover
如实缺席。全局捕获只选择一个 tracking level；`1006` 仍是其编码。捕获释放与重新 arm 复用端点已经
settle 的结果，不再发出查询。
只有完整 mode 写入成功后，已准入的切换才发布到指针交互状态。切换失败不发布 hover
权限，运行中的输入循环也绝不重试；致命路径直接进入完整生命周期清理。全局准入后的
any-motion 服务所有已绘制 chrome 控件，包括 action menu。菜单之外的 ButtonOnly fallback
具有 click、drag、wheel，但没有 idle hover。

捕获已启用的动作菜单在全局 any-motion 尚未准入时，还拥有菜单范围的 `MenuMotion` 请求。
它先写 `1002h`，再写 `1003h`，保留 `1006`：忽略 `1003` 的宿主仍保留按钮回退；只有实际
收到移动报告才出现反馈。此请求不改变一次性探测结果，也不假定物理送达。菜单退出时先恢复
`1003l`，再写 `1002h`；独立获准的全局升级取代菜单请求，退出后继续启用。捕获已释放时，
键盘打开菜单不写入模式。模式副作用完成后 dispatcher 才发布本地报告准入；写入失败为致命
错误且绝不重试，生命周期清理会清除所有自有模式。已有原生 ConPTY 见证覆盖该请求、通过继承
reader 的语义移动、返回无空闲移动的 button-only、全局准入及完整恢复；物理终端审阅另行完成。

tracking level 与编码共用一个 `ModeLease`；除非 `tui --mouse off` 拒绝，否则在启动时 arm。
每次原生或 VT 变更开始前都先登记待恢复义务。因此部分 enable 或 level switch 会进入
transition-unknown 状态，不能再尝试运行时 fallback；只有完整释放序列（`?1003l`、
`?1006l`、`?1002l`）能够 settle 它。经 `Ctrl+B m` 的运行时释放、重新 arm、启动 arming、
错误清理与 panic 清理共用该租约。手势路由、命中测试、降级或释放时的状态清理，以及 pane
透传属于[原生鼠标输入](native-mouse-input.zh-CN.md)；本节拥有能力 settle 与模式生命周期。

## 同步帧输出

每个绘制帧——完整的单元 diff 及其光标定位——被恰好一对同步更新包裹，并由一次 flush
发布。`terminal_lifecycle` 是该对的唯一所有者：它定义 begin 与 end 序列、在共享租约上
追踪"对仍开启"的义务，并负责恢复。backend 仅通过该租约参与：它在尝试 begin 标记之前
登记义务，因此即使 begin 只部分写入仍欠一个 end；只有当 end 标记与帧 flush 都被写器
接受后才清除该义务。凡无法确认送达时，该对保持待恢复。

| 状态            | 效果                                                                   |
| --------------- | ---------------------------------------------------------------------- |
| 更新已关闭      | draw 操作登记义务、发出 begin 标记并进入更新开启                       |
| 更新开启        | 单元、属性与光标写入在对内累积                                         |
| 更新关闭        | flush 发出 end 标记并对写器执行一次 flush；两者都成功才确认关闭        |
| 更新开启 + 失败 | 保留首个失败；之后的 flush 仍尝试 end 标记                             |
| begin 写失败    | 义务保持登记；下一次 flush 仍尝试 end 标记                             |
| end 未确认      | 该对保持待恢复；下一次成功的 flush 重发 end 标记，或由恢复流程终结该对 |

失败保留其首因。flush 失败仍尝试 end 标记；end 标记自身失败在尝试后报告，绝不在一帧内
静默重试。draw 失败则放弃该未完成帧：错误路径上帧写器在其被 drop 前先被围断，其缓冲
残量连同 drop 时的重试均不再送达终端。已写出的字节无法撤回；仍开启的对由恢复时经控制
通道终结。shell 在返回致命绘制错误前，还会撤销上一帧的命中图与已武装控件。
未完成的候选帧和旧帧都不能再授权交互。该循环直接退出，不重放输出；若实现恢复，
必须先建立新的终端基线并完成一次全量重绘。

恢复由 lifecycle 拥有并按固定次序执行：先阻断后续帧输出，再经由终端控制通道在与其他
模式相同的有界重试预算内终结仍开启的对，之后才关闭 bracketed paste、关闭指针捕获、
显示光标、离开备用屏幕并恢复 raw 模式。在 Windows 上，VT 输出在光标与备用屏幕清理期间
保持启用，之后 raw 恢复再还原两个已保存的原生模式字。帧写器带恢复门控：恢复一旦开始，
缓冲的帧字节被丢弃而不再送达正在恢复的终端，这也覆盖了 panic 展开时的 unwind flush。
输出失败后，同一围断在帧写器被 drop 前先行生效，使其 drop 时的重试同样无法发出被放弃
的帧。干净关闭不欠任何东西，也不多发任何字节。本契约既不承诺每帧一次操作系统写，也不
承诺在不支持同步更新模式的宿主上获得视觉原子性。

## TUI 计时观测

`tui_shell/measurement.rs` 拥有被动的循环与写器计时。只有进入实际 TUI 时才读取
`ORCHBEE_TUI_MEASUREMENTS`；它校验绝对文件路径，并在获取 TUI 模式前以 create-new 创建文件。
父目录必须已存在；已有文件保留并拒绝覆盖。变量缺失时不创建 journal 或文件，热路径也不采样时钟。
被选文件归调用者所有，最后一个诊断消费者结束后由其释放。

启用后预分配存储，最多保留 65,536 个固定结构样本。循环期间不进行诊断文件 I/O、序列化、后台工作或终端输出。
现有输出缓冲区和恢复围断之下的装饰器把每次写器操作原样转发一次，返回原始计数或错误。
它不增加 flush、drop 时写入、重试、帧确认或调度决策。Lifecycle 模式效果继续使用原有写器，
只增加调用耗时观测。

循环结束后，shell 先围断失败帧、drop 帧写器及表面，再完成终端恢复，最后才序列化诊断。
运行失败后仍尝试恢复；诊断失败不能取代原有运行或恢复首因。早期初始化失败、panic 或强制终止
可能留下空文件或不完整文件；缺少有效且完成的 JSON 表示测量中止，绝不是成功的零耗时运行。

机器文档使用 schema `orchbee.tui.measurements`、版本 `1`，包含进程 ID、可用时带区间的 UTC／
单调时钟对齐、生命周期结果、样本上限、丢弃／放弃／未完成／失败计数、无效时钟或计数标志、
`complete` 以及样本。样本使用相对运行起点的单调 `started_ns`／`ended_ns`。
UTC 对齐把其墙钟值置于 `monotonic_before_ns` 与 `monotonic_after_ns` 之间，不把它当成精确的
墙钟起点。样本按完成顺序存储，因此嵌套的写器调用记录先于其所属帧记录。样本不携带输入字节、
终端内容、命令、路径、环境值或凭据。源码、tree、构建模式和可执行文件摘要来自独立校验的 cohort 来源记录。

| 事件               | 观测及边界                                                                                                                                                   |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `input_read`       | 一次输入轮询区间、ready／idle／failed 结果及字节数；每个完成且就绪的数据包拥有不同 `batch`。轮询包含主动等待与排空，不只是队列停留。                         |
| `dispatch`         | 按 `batch` 关联该已完成应用数据包的分派。其开始减去读取完成是应用就绪后等待；一个包可能解码零个或多个事件，拆分序列也可能在之后的轮次才 settle。             |
| `frame`            | 帧 ID、最近观测输入批次、buffer 开始／准备完成节点及 draw 完成结果。批次只是上下文，不证明该帧包含期望反馈或有用终端内容。                                   |
| `writer_call`      | 原样转发的 `write`、`write_all` 或 `write_vectored` 区间以及请求／接受字节数。失败调用可能已发出效果未知的前缀；调用墙钟耗时包括转换、CPU 和原生／宿主阻塞。 |
| `flush`            | 原有写器的 flush 区间与结果。成功完成不等于物理宿主已经绘制。                                                                                                |
| `terminal_control` | 现有 lifecycle 效果的调用区间与结果，不包含 payload 或用户控制的文本。                                                                                       |

帧与写器区间是嵌套观测，不是可以相加的独立成本。缓冲准备可能占据被测帧的大部分，
却不一定占据完整运行的大部分。应计算已记录区间的并集及其占首个已记录样本开始到最后一个
已记录样本结束范围的比例，而非整个进程或 Session 生命周期；未覆盖的墙钟时间保持未分类，
不能自动归为 idle、CPU 工作或阻塞。若没有额外观测，准备完成后的帧尾部仍包含
diff、编码、记账与输出。

成功短写表示已接受一个前缀。现有缓冲区随后提交剩余后缀时，累加请求计数会重复计算后缀字节。
解释字节总量前应核对每条完整转发链；请求量减去接受量既不表示输出丢失，也不证明背压。
调用耗时与成功 flush 仍不能证明宿主绘制。

Windows 控制台记录不提供到达时间戳。这些样本不测量操作系统控制台队列停留、用户设备时间、进入 TUI
之前的激活过程、首个有用内容或 canonical Ready 确认。真实窗口的期望反馈探针按
[TUI 验证](../../../docs/zh-CN/tui/verification.md#响应与空间稳定性)提供独立的可见响应区间。

`complete` 要求运行与恢复成功，没有丢弃、放弃、未完成或失败样本，且时钟及计数有效。
达到上限、身份或计数耗尽、未结束区间、调用失败或序列化错误，都不能证明完整延迟分布。
解码 no-op 或帧的最近输入批次不等于反馈确认。比较运行时保留失败及超时观察，并在同一 cohort
和场景下测量启用／禁用采集带来的扰动。

相邻计时测试覆盖禁用时无时钟采样和存储、上限及不完整计数、实际循环中的数据包／帧关联、
短写／错误／vectored／默认方法边界、真实缓冲与恢复围断，以及恢复先于序列化和首因保留。
非 TUI 进程证据还必须证明该环境输入不会在 TUI 执行之外产生路径副作用。
这些都是采集器的主张，不证明响应预算，也不决定新的写器或调度架构。

## 外层标题恢复

[Windows 标题发布](windows-terminal-title.zh-CN.md) 拥有独立生命周期 lease。首次写入标题先捕获继承标题；恢复在结束同步输出之后、禁用括号粘贴之前偿还该 lease。捕获或写入失败显示本地化状态提示，TUI 继续可用；已登记的恢复义务仍然保留。恢复开始后不再写标题。有效配置标题或显式标题送达前不会捕获或写入标题。
