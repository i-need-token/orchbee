# Native terminal command submission

## Command and ownership

`orchbee terminal run <target> <command>` submits one quoted, nonempty UTF-8 command to an existing Terminal. Use `--` before operands resembling options. Command bytes, whitespace, quotes and newlines remain unchanged; separate command operands are rejected. The argument envelope is bounded to 64 KiB and paste to 256 KiB. The selected terminal's current program interprets the command. With `--wait` or `--capture`, `--file <path>` or `--stdin` supplies the command instead: UTF-8 text whose trailing line breaks are dropped, read under the run's own deadline before anything is sent, so a caller never quotes the command for its own shell.

Without `--wait` or `--capture`, one snapshot resolves the target and one input request sends paste followed by Enter. The five-second send budget and `orchbee.terminal.send` receipt govern this path. A receipt confirms input progress only. Partial or unknown delivery is never replayed. No viewer, controller, resize or focus is acquired.

## Correlated completion

`--wait [--timeout <ms>]` uses a read-only viewer and the managed shell integration: managed PowerShell on Windows, and on macOS and Linux the managed zsh or bash that the Host starts ([prompt-gated input](../../terminal-host/docs/runtime-model.md#prompt-gated-input)). Its total deadline defaults to 30000 ms, including discovery, readiness observation, submission, polling and cleanup. Unsupported or unready integration refuses before input. The caller must own an empty editable command line; concurrent user input is not excluded by a viewer.

Orchbee `cmd` marks its prompt and input start for the Host's prompt gate, but never its commands, and mints no run token. `--wait` therefore refuses before input in `cmd`, and an Agent run started from `cmd` is never `confirmed`.

The CLI generates a random invocation ID and sends one paste/Enter request with a comment prefix. The verified PSReadLine wrapper strips exactly that prefix and returns the original command to PowerShell without evaluation in a new scope. The prefixed line enters neither PSReadLine history nor `Get-History`, so Up-arrow recall never resubmits a stale ID. Private APC markers echo the ID at command start and completion. The wrapper exports the ID as `ORCHBEE_RUN_TOKEN` to that command only, and the prompt removes it on completion. A named Agent start reuses this prefix with a Server-minted run token; see [Windows Agent startup](windows-agent-start.md#launch-receipt). An unrelated OSC 133 completion cannot finish this wait. The Host retains only the latest correlated invocation; missing or overwritten evidence can time out and never authorizes replay. This is cooperative shell evidence, not an authentication boundary against the terminal process.

On macOS and Linux the CLI sends the same single paste/Enter request with the `: orchbee-run:<id>; ` prefix instead. Managed zsh strips it in its line editor and keeps the line out of history; managed bash runs it as a no-op and deletes the history entry. Both echo the ID in the same private start and finish markers and export it as `ORCHBEE_RUN_TOKEN` to that command. The prefix follows the host: on Windows only managed PowerShell advertises readiness, and on macOS and Linux only managed zsh and bash do, so any other shell still refuses before input.

JSON uses `orchbee.terminal.run` v1. `submission` preserves the complete input receipt; `completion` separately carries `exitCode`, `statusKind`, and physical output coordinates. With `statusKind: powershell-success` (Windows), PowerShell status is 0 for `$? = true`, 1 otherwise; it is not a guessed native process exit code. With `statusKind: shell-exit-status` (macOS and Linux), `exitCode` is the zsh or bash `$?` after the line: the last command's exit status, 128 plus the signal number for a command a signal ended. The output range's `retained` field is false after generation/origin changes. `failure` retains timeout, cancellation or transport facts without erasing accepted input or observed completion. `cleanup` records the viewer obligation. Cancellation does not stop the shell command. JSON is the recovery format; choose it before submitting scripted work.

## Typed-run boundaries

The same wrapper marks every other nonblank line PowerShell accepts from the user. It mints a random 32-digit lowercase hexadecimal token in the shell, exports it as `ORCHBEE_RUN_TOKEN` to that command only, and echoes it in the same private start and finish markers. The line, PSReadLine history, `$?` and `$LASTEXITCODE` stay unchanged, nothing visible is printed, and no OSC 133 completion is added, so command feedback is the same as before. A prefixed line keeps its submitted ID, so Agent start and `--wait` behave as before. A typed command can replace the Host's latest invocation, as any later command already could.

After each process sample the Server reads the Terminal's open invocation from the frame captured after that sample. An Agent run is `confirmed` while the invocation it appeared in stays open, provided the invocation started its anchor: every process from the anchor up to the shell, the sample's Job root, was created after the Host read that invocation's start marker. Samples cannot prove this: a frame names only the latest invocation, and an Agent left by an earlier command can appear between a sample and the next start. The Host therefore reads its real-time clock when the marker arrives. The shell exports the token before it writes the marker, so the anchor inherits it. A process an earlier command left running can still start an Agent during a later invocation, which is why the whole chain counts and not the anchor alone. Without the Host's time, with a missing or older process in the chain, or once the invocation finishes, the run stays `recognized`. The Agent's hooks inherit the token and bind its session exactly, as described in [Windows Agent integrations](windows-agent-integrations.md). cmd, an unverified PSReadLine, and unmanaged shells mint no token and stay at `recognized`.

- A token reaches only the command that the wrapper marked, and the prompt removes it on return.
- Typed tokens are shell-minted and never submitted as input; only the Host's echoed markers carry them to the Server.
- The grade never rises without an open invocation whose start precedes every process between the shell and the anchor.

## Captured output

`--capture --shell <syntax>` needs no shell integration, so it serves cmd, SSH sessions and any other shell at an empty prompt. One paste/Enter request submits a begin-marker statement, the command, and an end-marker statement that prints the command's status. The markers are the lines `[orchbee run <runId>]` and `[orchbee end <runId>] <status>`. The submitted text spells each marker in pieces that only the running shell joins (`'[orchbee' ' run <id>]'` for sh, `'[orchbee'+' run <id>]'` for PowerShell, a caret inside the word for cmd), so the echoed input never contains one. The shell prints each marker after a line break, so a marker matches only from the start of a row: that row and the rows that continue it, spaces ignored, must be exactly one of this run's markers, and an end marker takes every digit of its status. Spaces are ignored because a soft wrap can drop the space it falls on. Whether the marker's row seems to continue the row above, or its last row the row below, is ignored: under ConPTY, every row that PSReadLine's prediction of a longer earlier line took below the input stays marked as a soft wrap, padded with spaces to the edge, after the shell prints over it.

The command travels as one quoted string that the shell parses only when it runs it, so a syntax error is the command's own failure and the end marker still follows, and a line editor that takes each line break as Enter keeps reading until the closing quote. posix and fish pass the string to `eval`, so the status is `$?` or `$status`. PowerShell dot-sources `[scriptblock]::Create(...)` inside `try` in the current scope; a statement-terminating error therefore ends the command instead of moving to its next statement, and the status is 0 when `$?` holds, the native exit code when one is set, and 1 otherwise. cmd has no quoted evaluation and parses a whole line before it runs any of it, so it takes one line. After `(call )` clears ERRORLEVEL the line runs as written, so a `)` in it or in a value it expands, such as `C:\Program Files (x86)`, stays literal. `if` and `for` take the rest of their line as their own command and would take the end marker with it, so a line that uses either word outside double quotes runs as a parenthesized block instead, where a `)` outside quotes, including one a variable expands to, ends the block and needs `^)`. The posix and fish lines start with a space, which keeps them out of history where the shell ignores such lines.

After submission the read-only viewer watches each applied frame's visible rows for the end marker. When it appears, the CLI reads that frame's retained rows from the bottom upward, in windows pinned to the frame's revision, until the begin marker; a pin that ages restarts on the next frame. The output is the rows strictly between the markers, one line break per printed line and none across a soft wrap. The end marker begins with its own line break, so output that ends with a line break keeps it and output without one gains none, and the row above it never wraps into it. Nor can the begin marker's row wrap into the next one, so when it seems to, the rows below it were taken by such a prediction: while they too seem to wrap after a blank cell, each ends its line. A long first line that wraps at a space among them is then split there. Rows are rendered screen text: color, tab stops, blank cells after a line's last character, cursor-addressed redraws and carriage-return progress are not reproduced. Output past 1 MiB keeps its newest whole lines and sets `truncated`, and the scan of a finished command stops there. When a finished command's begin marker is no longer retained, because the screen was cleared, the history evicted it or the terminal was reset, its echoed input is gone with it, so every retained row above the end marker was printed after it: `output` keeps those rows within the same bound and sets `truncated`. A kept row holding part of the run ID is the echoed input. When that input remains but the begin marker does not, as when the command overwrote the marker's row, `output` is null rather than attributing earlier rows to this command; a command that still runs has no output without its begin marker.

Observation stops one fifth of the remaining time, at most two seconds, before the deadline. One last scan then keeps the output printed so far and can still find an end marker that arrived after the last observed frame; half of that allowance stays for releasing the viewer. On timeout or cancellation JSON keeps the partial output with a null `exitCode`; the command keeps running, and `terminal wait-output <target> --match "[orchbee end <runId>]" --source recent-unwrapped` continues waiting without replay.

The caller owns an idle, empty prompt, as with `--wait`. A full-screen program refuses before input, and the alternate screen is never read. A command that exits the shell, waits for input, or hands the rest of the screen to a pager prints no end marker before the timeout. zsh reads `#` as a comment only with `interactivecomments`. Other shells, such as tcsh, are not supported.

## Fresh output boundaries

`terminal read --format json` supplies an opaque cursor when the Host can identify the primary screen's row origin. Pass it to `terminal wait-output <target> --after <cursor> --match <text>`, or use `--after now` to begin at the first observed frame. Only later physical rows participate; the occupied boundary row and prompt/input rows are excluded. Existing output is never counted as fresh.

Host restart, generation changes, history eviction and gaps beyond the chosen window reject the cursor. Select a sufficient `--lines` window and an explicit `--timeout`. A new cursor is a new observation boundary, not recovery of lost output. See [terminal output](native-terminal-output.md).

## Evidence and compatibility

Help, completion adapters, the offline Agent guide and schemas evolve together. Older binaries
reject new options; existing sessions need a newly initialized managed PowerShell, zsh or bash for
correlated waiting.
